# テストアーキテクチャ

アプリの振る舞いに対して「この変更は安全か」を自動で答える仕組みの設計。ある振る舞いを検証するテストは、それを確かめられる最も速い種類に 1 つだけ置き、複数の種類で重複検証しない。

## テストの種類

### 静的解析

- **テスト対象**: 型整合性、並行処理の安全性、コード整形、および静的ルール（モジュール境界、テスト隔離、自動テストコードでのウィンドウ表示・前面化 API 呼び出し禁止（ウィンドウを画面の外へ並べるテスト支援の 1 か所を除く）、固定時間の待機禁止）。

### ユニット

- **テスト対象**: 純粋関数の入出力規則（変換・分類・バリデーション）、パーサ、状態機械、設定の解決、通知・メニューバー・更新の判断ロジック、エディターの文書操作・構文解析・検索・差分計算・スクロールの物理計算、通知音合成、CLI および MCP の引数解釈・リクエスト組み立て・スキーマ整合、画面モデルのキー入力および状態遷移、複数コンポーネントを連携させる業務処理（ワークスペース・タスク・自動化・ソース管理・PR の状態調整）。ファズテストは固定シードかつ小規模なステップ数で短時間に終わる範囲のみここに置く。
- **依存の扱い**:
  - データベース（SQLite）: インメモリ実行（本番と同じエンジン）。
  - エディター描画サーフェス・Git 実行・ファイル監視・サブプロセス・通知音再生・OS 通知・自動更新・時刻・タイマー・乱数: Fake。
  - GitHub API・外部エージェント CLI・外部 URL 起動: モック。
  - OS クリップボード: テスト専用の名前付き領域へ隔離。

### 永続化・マイグレーション

- **テスト対象**: SQLite データベースのスキーマ整合、旧版からの段階移行、破損ファイルの退避、複数プロセス間の排他ロック。設定・ワークスペース・タブ・タスク・アプリ状態・セッション履歴の各永続ファイルについて、保存→復元→再保存の往復、旧形式からの移行、破損時の退避。
- **依存の扱い**:
  - ファイルシステム・SQLite: 本番と同じ実装（テスト 1 件ごとに隔離した一時ディレクトリ上で実行）。
  - アプリ全体の起動・ウィンドウ・ターミナル: 依存させない（永続層単体で検証する）。

### 制御プロトコル契約

- **テスト対象**: 制御ソケット上の JSON-RPC 2.0 契約。メソッド名、パラメータと応答の構造、エラーコード、改行区切りのフレーミング、不正入力の拒否、イベント購読の履歴カーソル・フィルタ・タイムアウト。
- **依存の扱い**:
  - ソケット接続と JSON-RPC フレームのパーサ: 本番と同じ実装（インプロセスのソケットペア上で実行し、実ファイルパスの待ち受けソケットは作成しない）。
  - 操作対象（アプリ本体）: Fake。

### コンポーネント・ヘッドレス UI

- **テスト対象**: ユニット層だけでは検証できない UI フレームワーク境界。ビューのレイアウト数値契約（幅・高さ・折り返し・可視範囲）、フォーカスの移動とファーストレスポンダー・レスポンダーチェーン、メインメニューの編集コマンド配送、IME の変換・確定・キャンセル契約、スクロールバーや一覧の最小限のイベント接続。
- **依存の扱い**:
  - UI フレームワーク（ウィンドウ・ビュー階層・イベント配送）: 本番と同じ実装（ただしウィンドウを並べずに実行する。マウスのイベントを本物の配送で届けるテストだけは、テスト支援の 1 か所を通してウィンドウを画面の外へ並べる。どちらも、画面への表示、アプリの前面化、フォーカス奪取は行わない）。
  - IME 入力コンテキスト・ウィンドウのアクティブ状態・ポインタ位置・エディター描画サーフェス・時刻: Fake。
  - OS クリップボード: テスト専用の名前付き領域へ隔離。

### 統合（実依存・プロセス境界・描画）

- **テスト対象**: 本物の実行ファイル・外部プロセス・描画エンジンを跨いだときにしか現れない不具合に絞る。
  - **プロセス境界**: ビルド済み同梱 CLI・MCP・状態報告ツールと dev 専用の通知音 CLI の代表的な起動確認、終了コード、標準出力・標準エラー、およびターミナルタブに注入した環境変数を参照して状態報告ツールが制御ソケットへ報告を届けるまでの実経路。
  - **Git・ファイル監視・外部プロセス異常系**: 実 Git リポジトリでの worktree・diff・ステージング・コミット・サブモジュール、および認証プロンプトやエディター起動などの対話処理の抑止・ハング打ち切り。実ファイル監視のイベント通知、外部コマンドのタイムアウト・キャンセル・フォールバック。
  - **ターミナル入出力と補完**: 実ターミナルエンジンと疑似端末（PTY）を介したキー入力の変換・IME 確定文字の到達・クリップボード制御・フォーカス通知、およびシェル補完エンジンの候補生成・キャッシュ・タイムアウト動作。
  - **アプリ結合**: 起動時の状態復元、設定変更のライブ反映、非アクティブなワークスペースの常駐維持、ウィンドウと通知の連携。大半の連携は依存を軽量なものに差し替えて検証し、実ターミナルを含む完全起動の検証は最小本数に留める。
  - **エディター描画サーフェスの GPU 描画**: エディター描画サーフェスのグリフ、行番号、Git 変更マーカー、選択・検索のハイライト、ミニマップ、インライン差し込み要素のオフスクリーン描画とスクロール追従。
- **依存の扱い**:
  - 制御ソケット・ビルド済み同梱 CLI 実行ファイル・ファイルシステム・Git・ファイル監視・ターミナルエンジン・疑似端末・シェル補完エンジン（JavaScript 実行環境）・オフスクリーン GPU 描画: 本番と同じ実装（隔離された一時ディレクトリ・テスト専用ソケット・テスト専用クリップボードを使用して実行）。
  - GitHub API・外部エージェント CLI・スピーカー再生・OS 通知センター・自動更新配信: モックまたは Fake。
  - ゴミ箱移動: 隔離用一時ディレクトリへ差し替え。

### 生成物

- **テスト対象**: 配布用 `.app` バンドルの静的構成（署名整合、dev/release チャネルごとの `Info.plist` 設定値〔バンドル識別子・表示名・バージョン等〕、同梱 CLI 実行ファイル、外部フレームワーク、構文解析文法バンドル群、ターミナルリソース、フォント）、エージェントプラグインの構成整合、多言語カタログの網羅、デザイントークンの定義と実装が過不足なく 1 対 1 で一致すること。
- **依存の扱い**:
  - ビルド済み `.app` バンドルとリポジトリ内カタログ: 本番と同じ成果物（アプリを起動せず静的に検査する）。

### 長時間ファズ・隔離実証

- **テスト対象**: 大量ステップのランダム操作列（編集、複数カーソル、IME、インライン差し込み、構文解析、編集可能な差分ビュー上での直接編集に伴う差分状態の更新、PR レビューコメントの書き込み順序）での不変条件維持。自動テスト全量の実行を通じて開発者の実環境（設定ファイル・状態ディレクトリ）へ一切書き込まず、実行後に OS の一時領域へ残骸を残さないことの実証。
- **依存の扱い**:
  - 隔離実証の監視対象: 本番と同じ実環境パスと OS の一時領域（テスト実行前後で差分が 0 であることを検証）。
  - 長時間ファズの対象: 各領域の本番実装または Fake（フィーチャー PR で回すテスト群から分離して実行）。

## テスト容易性の規則

- **画面を表示せず、フォーカスを奪わずにテスト可能にする**: ウィンドウのアクティブ判定（キーウィンドウ・アクティブアプリ判定）と前面化操作は抽象境界の背後に閉じ込め、実画面へウィンドウを表示したりアプリを前面化したりせずに前面・背面に応じた分岐を検証できるようにする。
- **画面モデルの入力を UI フレームワークから切り離す**: キーボード操作・ショートカット・フォーカス遷移の判断ロジックは、UI フレームワーク固有のイベント型ではなく値型として入力を受け取り、ウィンドウやイベントループなしで単体検証できるようにする。
- **コンポジションルートと業務ロジックを分離する**: ウィンドウコントローラ等の巨大な初期化処理に永続データの読み込み・ターミナル起動・データベースの初期化・自動更新・業務判断を詰め込まない。依存をコンストラクタまたは引数で受け取り、業務ロジックは独立した型へ分離する。
- **共有シングルトンと可変グローバル状態を排する**: 制御サーバ、補完エンジン、補完学習ストア、ユーザー設定（UserDefaults）、ワークスペース単位の状態レジストリ、クリップボード、リソース解決先をインスタンス化・注入可能にし、テスト間の状態持ち越しと並列実行の競合を構造的に防ぐ。
- **描画エンジンと状態モデルを分離する**: エディター描画サーフェスの編集・選択・IME・複数カーソル・インライン差し込み要素の状態遷移は GPU 描画スレッドに依存させず、描画契約（インターフェース）を通じて描画エンジンを上位層からも Fake に差し替えられるようにする。
- **CLI と MCP の実行ファイルは薄いエントリポイントに保つ**: 引数解釈・検証・リクエスト組み立て・ツール定義はライブラリ層へ分離する。ライブラリ層ではプロセスを直接終了させず、結果を戻り値またはエラーで表現し、実行ファイル側が終了コードへの変換だけを担う。
- **時刻・タイマー・猶予時間・外部プロセス境界を注入可能にする**: 現在時刻、遅延実行、定期タイマー、プロセス終了猶予時間、Git・GitHub・ファイル監視の実行境界は引数またはインターフェースで受け取り、実時間待機なしで境界条件と異常系を検証できるようにする。
- **テスト専用の裏口を本番コードに入れない**: テストのためだけの公開範囲拡大、条件分岐、専用エンドポイントを本番コードに追加せず、責務分離と依存注入という設計上の正しさでテスト容易性を確保する。

## CI の段階

- **コミット前（ローカル）**: 静的解析（lint・format）。
- **フィーチャー PR**: 静的解析、ユニット、永続化・マイグレーション、制御プロトコル契約、コンポーネント・ヘッドレス UI、統合。数分で結果を返し、並列実行と依存キャッシュで待ち時間を抑える。
- **main マージ後・定期実行**: フィーチャー PR の全テストに加え、生成物（`.app` 静的検査を含む）、長時間ファズ、隔離実証。
- **リリース時（公開前・公開後）**: 公開前の署名・公証・Gatekeeper 検証と、開発者の実環境から分離した状態ディレクトリでのアプリ手動起動確認を行い、公開後に更新配信フィードの応答と旧版からの実アップデート経路を確認する。
- **ジョブの分け方**: 実行環境と再実行の単位で分ける（静的解析／ユニット、永続化、制御プロトコル契約、コンポーネント・ヘッドレス UI の高速テスト群／実プロセス・実 Git・実ターミナル・GPU 描画の統合／`main` マージ後・定期実行で行う生成物・長時間ファズ・隔離実証の各ジョブ）。落ちた単位だけ再実行でき、テストごとの実行時間を毎回記録して長時間化を検知する。

## 運用の規則

- **flaky**: 無条件の自動再試行で失敗を隠すことは禁止する。不安定なテストが発生したら原因（固定時間の待機・外部状態漏れ・並列競合・環境差）を特定して修正する。即時修正できない場合のみ、追跡 Issue と修正期限を紐付けたうえで一時的にスキップ（無効化）し、無期限のスキップを残さない。
- **テストデータ**: 一時ファイルと作業ディレクトリは全テスト共通の隔離ハーネスのみが発行し、テストの成否や異常終了にかかわらず自動削除する。テストが開発者の実環境（設定ファイル・状態ディレクトリ・ユーザー設定（UserDefaults）・GitHub 資格情報・ゴミ箱・OS クリップボード・スピーカー・OS 通知センター）へ絶対にアクセスしない状態を、テスト単位で隔離を自動適用して維持する。重いフィクスチャ（実 Git リポジトリ・疑似端末・シェル補完エンジン）はテンプレートのコピーや、ケース間でリセットしての再利用を基本とし、テストごとにゼロから構築しない。
- **テストの品質規律**: 振る舞い（呼び出し側や利用者から見える結果）だけを検証する。本番コードの定数表をテストへ書き写して値が一致することだけを確かめる検証、UI 文言やプロンプト文面の部分一致、ハードコードしたピクセル座標や RGB 値によるアイコン・文字判別、内部プライベート状態の検査、固定時間の待機（sleep や固定秒数ループ）はテストに含めない。テストクラスの説明には、その検証が落ちたとき利用者に何が起きるかを書き、弱めてよいか・消してよいかの判断材料にする。アサートを持たない画面キャプチャツールや手元性能計測は、自動テストスイートから明確に分離する。

## 自動テストの対象外

- **`.app` の実起動経路・アプリデリゲートによる起動時初期化と各コンポーネントの接続・補完エンジンの実機 JIT 動作**: 実環境から分離した状態ディレクトリでアプリを起動するスクリプトを用いた、手動およびリリース前の確認で担保する。
- **画面の見た目（色・余白・フォント・影の視覚的品質）**: 静止画面・操作フローのキャプチャツールとデザインシステム基準を用いた視覚確認フローで担保する。
- **エディターの実機での操作感・実画面フレーム計測・性能ベンチマーク**: 開発者が実画面で操作感を試すための検証用ウィンドウランナー、およびエディター変更時に手元で実行するリリースビルドでの計測で担保する。
- **OS 権限（アクセシビリティ・入力監視）の実環境挙動と dev/release チャネル併存**: 分岐ロジックのみユニットで検証し、実環境挙動は手動・リリース前確認で担保する。
- **公証・Gatekeeper・旧版からの自動更新の実経路**: リリース時の公開前・公開後ゲートで人が確認する。
