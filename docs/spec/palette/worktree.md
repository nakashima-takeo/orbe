# worktree パレット（⌘T）

新しいタブを開く唯一の入口。どの worktree で・何を起動するかを選ぶと、必要な worktree の用意からエージェント起動までがワンアクションで済む——Orbe の中心価値である「手順の簡略化」を最も濃く担う面。⌘T とタブ行の「＋」で開く（入口を 1 つにそろえる。素のシェルのタブがすぐ開くのは、初回起動で復元するものが無いときだけ）。開いた直後は今の worktree の行が選ばれ、起動先は既定の agent なので、**⌘T ↵ で「今の worktree で既定の agent」のタブが開く**。素のシェルは ⇥ で切り替える。

他パレット（[settings](settings.md)・[workspace](workspace.md)）と同じ提示経路だが、描画は共有パレット基盤を使わず専用の View／モデル／非同期データプロバイダが持つ。行の解剖と実データ供給が、共有基盤の 1 行リスト前提に載らないため。

## 器と構成

scrim ＋ ガラスパネル。上端アンカー・窓幅に追随する上限幅。カード高は窓高に束縛し、リスト部は実測内容高と上限の小さい方で定高化して超過分を内部スクロールへ回す（低窓・多件数でも末尾行・フッターに到達できる）。行が千を超えても、↑↓・打鍵・ホバー・スクロールの反応は数十行のときと変わらない。

カードは**一覧・[clean](#clean--worktree-の掃除)・[最新化](#最新化--遅れたブランチを追いつかせてから開く)・[ベースを選ぶ](#ベースを選ぶ画面) の 4 モード**を持ち、器（枠・焦点・高さの契約）は共通で中身だけが入れ替わる。掃除・最新化・ベース選びのために別のパレットを開かせない——同じ器の中の遷移なので、覚える近道が 1 本増えない。

一覧モードは上から:

- **ヘッダー**: `❯`＋実 `TextField`（検索、または新しいブランチ名）＋右端に開いたキーの札 `⌘T`。chrome 入力欄のプレースホルダは共通モディファイアで描かれ、**フォーカス中に IME 変換がある間は非表示**になる——未確定文字は binding へ流れず空欄と区別できないため、field editor の marked text を監視して抑制する（確定・取消で空へ戻れば再表示。抑制はフォーカス欄のみ）。
- **起動先の行**: 「起動先」＋名前の長さのボタン（既定の agent に「既定」の札、shell、残りの検出 agent を検出順）＋右に `⇥ 切り替え`。選択中のボタンは accent の枠と淡い地。
- **ベースの行**: 「ベース」の後に、[作成行](#新しいブランチ)を選んでいる間だけ選択肢のボタン（前回 / 既定 / 現在 / ほか…）と右に `⇧⇥ 切り替え`。それ以外の行を選んでいる間は、破線の枠の中の言葉で、その行の ↵ が新しいブランチを切らないことを言う（worktree の行「なし — 作らずに、既存の worktree を開く」／ブランチの行「なし — 新しいブランチは切らず、<名前> を worktree にする」／clean 行「なし — 作らずに、要らなくなった worktree を掃除する」／非 git の行「なし — このディレクトリをそのまま開く」）。ベースのバーはいつも同じ場所にあり、作成行でだけ選べる。
- **リスト**: 打った名前が作れるときだけ先頭に「新しいブランチ」の欄（作成行 `＋ <名前> を作る` 1 行）。続いて「WORKTREES · <リポジトリ名>」（main を含む全 worktree。行は名前と `~` 短縮のパス。今の worktree の行に「現在」の札。末尾に掃除への入口の `clean` 行）と「BRANCHES」（worktree の無いローカルブランチの後に、ローカルで追跡されていないリモートブランチ。リモートは `origin/…` と作者・相対日時）。見出しは選択対象外・空の欄は出さない。ブランチの行の右端は、origin を追跡するローカルブランチの upstream との差の同期ピル（`↑N` と `↓N` は別ピル・0 の側は出さない・提示時の `fetch --prune` が着地した後の値だけ）、無ければ `checkout → worktree`。絞り込みで既存の行が 1 つも合わなければ「WORKTREES・BRANCHES」の見出しと「一致する worktree・ブランチはありません」を出す。**行はカードの幅を超えない**——狭い窓では名前・補足が先に縮み、札・同期ピル・候補件数は縮めない（数字が欠けるため）。縮んだ文字は、末尾省略で読める形（先頭 1 文字＋…）になる幅があれば出し、無ければまったく出さない。起動先・ベースのボタンは、並びきらない窓では名前が中ほどで縮む。選択行のみ着色し、選択は移動時に可視域へスクロール追従する。
- **フッター**: 選択行の ↵ が何をするかを言う（対象名・ベース名は明るく、起動先は accent）——worktree の行「↵ <名前> で <起動先> を新しいタブで開く」／ブランチの行「↵ <名前> を worktree にして <起動先> で開く」／作成行「↵ <名前> を <ベース> から作り、<起動先> で開く」（ベースが「ほか…」なら「↵ ベースを選ぶ」）／clean 行「↵ 要らなくなった worktree を選んで掃除する」／非 git の行「↵ <パス> で <起動先> を新しいタブで開く」。右端キーヒントは `esc 閉じる`、選べる行が 2 つ以上のときだけその前に `↑↓ 選択`。実行失敗時はこの行に失敗理由を赤で出す。worktree 作成待ち中は `↵` もキーヒントも出さず、スピナ＋「作成中…」のみを出す——操作が無効な間は効かない案内を残さない（優先度は 作成中 → エラー → 実行説明。[最新化](#最新化--遅れたブランチを追いつかせてから開く)モードでは同じ部品が「最新化中…」を出す）。

## データ供給（プログレッシブ）

パレットは**開いた時点の workspace に結び付く**。対象リポジトリはその workspace のアクティブタブの cwd から探し、0 タブならその workspace の root path から探す（新タブの開始地点と同じ基点）。タブを開く先・前回のベースの読み書きも、この同じ workspace に対して行う——作成中（fetch の着地待ちで数秒かかりうる）に制御 API 等でアクティブな workspace が替わっても、別の workspace にタブが開いたり、別の workspace の「前回」が書き換わったりしない。その workspace が作成中に閉じられたら、タブは開かず前回も書かない。

cwd が git リポジトリの外なら、一覧は「このディレクトリ」の 1 行だけになる（見出しなし）。⌘T ↵ の意味（今いる場所で既定の agent を開く）を git の有無で変えないため。作成行は出ない。

パレット提示と同時にデータロードが走る。git（worktree/branch 列挙・数十 ms）が着地した時点で描く。初回ロードまでは候補行の形をしたスケルトン行を出し、開いた瞬間の空フレームを埋める（[clean](#clean--worktree-の掃除) の選択画面も、分類が 1 行も出ていない間は同じスケルトン行で埋める）。git の列挙が着地するまでは、gh の着地があっても描かない——空の一覧を「ロード済み」として出すと、開いた直後の ↵ がその空の一覧で決着して空振りする。git・gh とも子プロセス PATH（[shell-path](../platform/shell-path.md)）でサブプロセス実行し、completion をメインで受ける。gh の結果は一覧には出さず、clean の判定材料（ブランチの PR）にだけ使う。

- **git 列挙**: worktree 一覧・local/remote branch 一覧（`<remote>/HEAD` のノイズ除外）・デフォルトブランチ。ブランチがどの worktree で checkout 中かは worktree 一覧だけから取り、checkout 中のローカルブランチはブランチの欄に出さない（worktree の欄に出る）。remote branch は即時読みに加え、裏で `git fetch --prune origin` を**独立レーン**で走らせ、成功時に読み直して一覧を組み直す（失敗時は手元の値のまま UI 非破壊）。独立レーンにするのは、共有 queue の barrier チェーンに載せると無関係な git 操作までこの数秒の fetch を待たされるため——待つかどうかは実行基盤ではなくパレットが経路ごとに決める。**fetch 後の値に依存する経路——ベースから新しいブランチを切る worktree 作成（作成行・リモートブランチの行）と、origin を追跡するローカルブランチの行の Enter——だけは、この fetch が走っている間はその着地を待ってから行う**——待たなければ、提示直後の Enter が fetch 前の古い `refs/remotes/origin/*` から worktree を切り、Local branch 行では速く押した人だけが最新化を選べない。**着地は fetch プロセスの完了ではなく、その後の git 列挙の引き直しまで揃った時点**を指し、ベースの名前（既定ブランチ）も fetch 後に解決した値を使う——fetch は `origin/HEAD` を作ることがあるので、ref の中身だけを待つと、`origin/HEAD` を持たないリポジトリで既定ブランチからの作成がフォールバックの固定名を指したまま撃たれる。着地の成否は問わない（失敗したなら手元の origin ref が最良で、分類と同じ「失敗は据え置き」に揃える）。作成の直前に別の fetch は撃たない——同一リポジトリで fetch を並走させると `refs/remotes/origin/*` のロックで片方が落ちる（git はロックを待たず即失敗する）。既存ブランチを checkout するだけの経路（worktree の行・upstream を持たない／origin 以外を追跡するローカルブランチの行）は fetch で動く値に依存しないので待たない。ローカルブランチの行の同期ピルも着地後の値だけを出す——着地は列挙の引き直しまでを指すので、fetch 前の差が描かれる瞬間は無い。
- **GitHub の可用性**: `notGitHub`／`ghMissing`／`ghUnauthed`／`ready` に分類する（origin URL が github.com か → ローカルの認証情報の有無）。判定は**ネットに触らない**——疎通不能を「未認証」と誤分類しないため。`ready` のときだけ remote の正式名とブランチの PR を問い合わせる。それ以外は clean の PR の事実を「確かめて 0 件」として畳む（下の分類レーン）。
- **gh 結果のキャッシュ**: remote の正式名とブランチの PR はリポジトリ（`git-common-dir`）単位でプロセス内に保持し、次に開いたときは前回の答えで先に判定したうえで裏で取り直す。worktree 間で共有され、アプリ終了で消える。
- **remote の台帳**: worktree の行が「GitHub のどのリポジトリのどのブランチか」を決める唯一の置き場。clean の PR の突き合わせは、ここで求めた行の同一性と PR の head の等しさだけで決まる。PR の head は自分が push したブランチなので、ローカルブランチの同一性は push 先の remote（git 自身が解決する `branch.<名前>.pushRemote` → `remote.pushDefault` → `branch.<名前>.remote`。push 先が無い行とローカルブランチを追跡する行は origin とみなす）のリポジトリと、ローカル名の組——既定の `push.default=simple` で push されるのはローカル名で、base（`origin/main`）を追跡して作った作業ブランチも、base から出た無関係な PR（main→release のリリース PR 等）と取り違えられない。リポジトリまで含めて比べるのは、他人の fork の同名ブランチから出た PR を自分の行の PR とみなさないため。remote の名前と fetch の URL（`insteadOf` 展開後）は git 列挙と同じ束で読む。読むのは git の機械向けの出口（名前の一覧と remote ごとの URL）——人が読む表示は行末に装飾が付く（部分クローンではフィルタ名）ので、部分クローンでも通常の clone と同じに読めるのは機械向けの出口だけ。ローカルブランチの push 先も git の機械向けの出口（`for-each-ref` の push 先の remote 名）から読み、push 先の解決順は git が持つ。URL から読んだ `owner/name` は、remote ごとに GitHub に問い合わせて正式名に揃える——GitHub は改名後も古い名前から新しい名前を返すので、origin の URL が改名前のままでも PR の head と同じリポジトリと分かる（揃えないと、clean が自分のレビュー中の PR を見落としうる）。問い合わせは remote 一覧と認証確認の両方が揃ってから、1 つずつ撃つ（1 つの「存在しない」で他の remote の答えまで失わないため）。GitHub かどうかは可用性の判定と同じ 1 つの規則「URL に github.com を含むか」で決める（SSH のホスト別名も GitHub として拾う）。

  **remote ごとの値は「正式名」「GitHub でない」「確かめられない」の 3 つ。** 確かめられないのは、GitHub が正式名を返さない（存在しない・今のアカウントから見えない private——GitHub は両者を区別せずに答える——・問い合わせの失敗）、GitHub の URL からリポジトリ名を読めない（gist 等）、remote の一覧を読めない、のとき。答えはどちらもリポジトリ単位でプロセス内に持ち、次に開いたときは最初のフレームからその扱いで描く。正式名は問い合わせ直さない。「確かめられない」答えは描いたまま裏で問い直し、正式名が返れば clean の PR の事実が揃う——`gh auth switch` で見えるアカウントに切り替えた後は、開き直せば直る。答えを一度も得ていない GitHub の remote がある間は台帳は未確定で、clean の PR の事実は「まだ分からない」になる。

  **「確かめられない」は「GitHub でない」と読まない**——読むと clean が PR の事実を「確かめて 0 件」と読み、レビュー中の PR を持つ worktree が安全群に入りうる。確かめられない remote へ push する行は、clean で PR の事実が「取得に失敗」になる。粒度は remote 単位で、消えた fork の remote が 1 本残っているだけで、ほかの行やリポジトリ全体を止めない。

  push 先が無い行を origin の同名ブランチとみなす規則は台帳が持ち、fetch を信頼する remote（origin）の定義とは別に持つ——前者は push 先とみなす remote という同一性の関心、後者は鮮度の関心で、片方を変えてももう片方は変わらない。ローカルブランチを追跡する行も push 先が無い行と同じ扱い。台帳に無い名前の push 先（URL を直接書いた remote・存在しない remote）は origin とみなさず「確かめられない」にする——git が origin 以外へ push すると言っている行を、origin の同名ブランチと取り違えないため。
- **分類レーン**: [clean](#clean--worktree-の掃除) の 3 群判定に要る実測（worktree ごとの作業ツリーの汚れとその件数・停止中の git 操作・消してコミットが世界に残るか）を走らせる。**撃つのは `fetch --prune` の後だけ**（prune の成否は問わない——失敗しても手元の ref が最良で、撃たなければ分類が始まらない）。到達性の判定は prune 済みの `refs/remotes/origin/*` を前提にするので、prune 前の origin から到達性を読むと「消してもコミットは origin に残る」が偽になりうる。一覧の `clean` 行の候補件数もこの分類が着地して初めて出る——prune 前の到達性で出ることはない。PR 軸が着地していない行は安全群に入らないので、件数はその着地でも動く。git を叩く部分は**独立レーン**（remote branch の裏 fetch と同じ理由——共有 queue の barrier チェーンに載せると直後の Enter で来る worktree 作成と、clean の削除実行を待たせる）。clean が読む PR の事実（レビュー中か・マージ済みか・マージ先）は、worktree にあるブランチ（main を除く。detached は対象外）を `--head` で名指しした取得（`--state all`・ブランチごとに 1 往復で open / closed の両方）から来る——ブランチの名指しで引くので、古くにマージされた PR も古くから開いたままの PR も取りこぼさず、「マージ済みなのに merged チップが出ない」「レビュー中なのに安全確認を素通りする」が起きない。掃除の事実はこの取得だけから来る。1 往復では gh の上限まで（作成日時の降順に 100 件）取る——往復コストは件数に依らないので絞る動機が無い。名指しするのは、同一性が GitHub のブランチと決まった worktree のローカル名。`--head` はブランチ名でしか絞れず他人の fork の同名ブランチの PR も返るので、**head が worktree の同一性と等しい PR だけ**を突き合わせ、その最新（open は最新の OPEN・closed は最新の非 OPEN）を採る。安全確認（レビュー中の PR があるか）と推定（merged チップ・比較先のヒント）は、この同じ絞った事実を読む。git レーン（worktree 一覧）・gh レーン（認証確認）・台帳の確定がすべて揃ってから引く。取得の入口は各着地点から叩かれ、揃う前に来た側は素通りする。PR の head のリポジトリは owner と名前から組む——古い版の gh でも同じ head になり、自分の PR を「確かめて 0 件」と見落とさないため。PR の事実は、probe 未完なら「取得中」、gh が使えないと確定したら「確かめて 0 件」、台帳が未確定なら「取得中」、行を確かめられないなら「取得に失敗」、GitHub の行でないなら「確かめて 0 件」、それ以外は取得の結果、の順で決まる（確かめきれていない状態はどれも安全群に入らない側に倒れる）。**取得は名指しするブランチ単位で、状態（取得中／取得できた／取得に失敗した）もブランチ単位に持つ**——1 本の失敗で全体を捨てると、取れたブランチの事実まで一緒に消える。まだ引いていないブランチだけを固定本数（4 本）のレーンへ静的に配って並列に撃ち、着地もブランチごとに反映する（直列だと worktree 本数ぶんの往復がそのまま積み上がる）。取得に失敗したブランチはそのセッション中は引き直さない（パレットを開き直せば再取得される）。今回の取得が未着地・失敗のブランチは、同一プロセスの前回結果があればそれで確定させる。gh が使えないと確定したリポジトリ（非 GitHub・gh 不在・未認証）では、どの worktree も「確かめて 0 件」として畳む——確認対象そのものが無いので、行は git の事実だけで判定される。gh の主張のうち安全確認に効くのは open PR の有無だけで、マージ済みか・マージ先かは推定と表示に閉じる——**消してもコミットが世界に残ることの証明はローカル git の事実だけで閉じる**。ただし merged PR の base は取り込み判定の**比較先リストへの 1 本のヒント**にはなる: gh 着地で base が判明したら、**比較先の顔ぶれが変わった行だけ**判定を引き直す（PR 名指し取得の顔ぶれ dedup と同じ規約——発行時点で比較先を記録し、着地は発行時の比較先が現台帳と一致するときだけ反映する）。git の事実が動いた着地（fetch --prune・削除後）は全行を引き直す。`fetch --prune` の完了後に git 列挙ごと打ち直すので、リモートで消えたブランチの `[gone]` は prune 済みの状態で読まれる——マージ直後という主用途で候補が空にならない。

## 操作

**絞り込み**: 打鍵で名前・補足（worktree の行はブランチ名も）を大小無視部分一致で全欄横断に絞る。空になった欄は消える。

**選択の規則**: 入力が空なら今の worktree の行（git でない場所では「このディレクトリ」の行）。入力があれば一致した既存の行の先頭、無ければ作成行。入力が変わるたびにこの規則で選び直し、ユーザーが選択を動かす（↑↓・ホバー・タップ）まではデータの到着や有効性の答えでもこの規則を当て直す。動かした後は、裏のデータ到着で欄が差し替わっても、直前に選択していた行を同じ実行ペイロードで探し直して選択を復元する（行数が変わっても選択が別の行を指さない。見つからなければ範囲に収める）。この復元は入力モダリティを奪わない。

**↑↓ / ⌘↑↓**: ↑↓ は可視の全行を平坦 index で巡回（wrap・見出しはスキップ）し、選択行へスクロール追従。⌘↑↓ は最初/最後の行へジャンプ。**行タップは決定**（↵ と同じ funnel を通り、作成中・範囲外では不発）。**マウスホバーで選択がその行へ追従する**（着色行は常に 1 つ・ホバーで決定は走らない）。追従の門は共有の入力モダリティ（[workspace パレット](workspace.md)）で、実ポインタ移動で pointer・キー移動や絞り込みで keyboard へ戻り、keyboard の間はスクロールで行がカーソル下へ来ても選択を奪われない。**カード内のクリックは焦点の宛先を確定させる**（共有 `PaletteCard` と同じ契約 → [workspace パレット](workspace.md)）——行タップ・ボタン・余白のいずれの後も、↑↓ と打鍵がそのまま効く。起動先・ベースのボタンは焦点を取らない。

**⇥（起動先の巡回）**: 起動先の行のボタンを順に巡回する（末尾から先頭へ）。ボタンのクリックでもその起動先を選べる。agent 未検出でも shell を選べるため袋小路は無い。

**⇧⇥（ベースの巡回）**: 作成行を選んでいる間だけ、ベースの選択肢を順に巡回する（末尾から先頭へ）。それ以外の行では何もしない。一覧ではいつも握る——握らないと焦点が入力欄から外へ逃げ、↑↓ と打鍵が効かなくなる。

### 新しいブランチ

打った文字列が新しいブランチの名前として使えるときだけ、リストの先頭に作成行が出る。条件は 2 つ:

- **git が有効なブランチ名と答える**（`git check-ref-format --branch`）。規則を手元へ写さず打鍵ごとに git に問うのは、写すと git の版の違いでずれるため。答えが届くまでは直前の答えで作成行を出すかを決め、行の名前は今の入力にする——打鍵のたびに行が消えて出直さない。古い入力への答えは捨てる。リポジトリを要さない問いなので、一覧が届く前に打った名前にも答える。
- **名前も作成先もぶつからない**。ローカルブランチ（worktree で checkout 中のものを含む）と同じ名前、リモートブランチの行が作るローカル名と同じ名前は出さない——後者はリモートブランチと同じ名前の別物を作ることになり、正しい入口はそのリモートブランチの行。作成先（`worktree-dir` のテンプレートで解いたパス）が既存の worktree と同じ場所になる名前も出さない（`issue-212` と `issue/212` は同じ slug で、作成は必ず失敗する）。

作成行の ↵ は、ベースのバーで選んだベースから、upstream を持たない新しいブランチを切り、その worktree を作って選んだ起動先で開く。

**ベースの選択肢**は 前回 / 既定 / 現在 / ほかで選んだ名前 / ほか… の順:

- **前回**: その workspace で前回新しいブランチを作ったときのベース（[workspace](../platform/workspace.md) に保存。再起動後も読み戻る）。今の列挙（ローカルとリモートのブランチ）にあるときだけ出す。
- **既定**: 既定ブランチ。表示名は今の解決値で、作成時は意図のまま渡して作成の直前に解決し直す（fetch の着地後の名前で切る）。
- **現在**: 今の worktree のブランチ。detached のときは出さない。
- **ほかで選んだ名前**: [ベースを選ぶ画面](#ベースを選ぶ画面)で選んだ名前。選んだ後だけ、「ほか…」の直前に出る。
- **ほか…**: 常に最後。ここに止まった ↵（またはクリック）はベースを選ぶ画面を開き、フッターも「↵ ベースを選ぶ」と言う。巡回で止まれる普通の選択肢なので、⇧⇥ を回し続けても別の画面に入らない。

同じ名前に解決する選択肢は 1 つにまとめ、前に来る役割の札を残す。初めの選択は前回、無ければ既定。**選択はインデックスではなく役割で持つ**——fetch の着地で選択肢が増減しても別のベースを指さない。選んでいない間は組み直すたびに初めの規則を当て直すので、着地で前回のブランチが現れれば前回が選ばれる。選んだ役割が組み直しで消えたら、選んでいない状態へ戻る。

**前回の保存**は、作成行の ↵ で worktree の作成に成功したときだけ、実際に使ったベースの名前で行う（既定ブランチで作ったときも解決後の名前。例: `origin/main`）。書くのはウィンドウだけで、パレットとデータ供給は workspace の永続値に触らない。workspace ごとに覚えるので、1 つの workspace で複数のリポジトリを扱うと、別のリポジトリで覚えたベースが今のリポジトリに無く、既定に落ちることがある。

### ベースを選ぶ画面

「ほか…」から入る、同じカードの中の画面。ヘッダーは入力欄（プレースホルダ「ベースのブランチを検索」）＋右に `esc 戻る`、起動先とベースの行は隠す。リストはローカルブランチ（checkout 中のものを含む）の後にリモートブランチを、それぞれ新しい順に、一覧のブランチの行と同じ見た目（グリフ・名前・相対日時）で並べる。打鍵で絞り込み（カーソルは先頭へ戻る）、↑↓ で選び、↵ か行タップで決めると一覧へ戻り、選んだ名前が「ほか…」の直前のボタンとして出て選ばれる（既にある選択肢と同じ名前なら、その選択肢が選ばれる）。esc は選ばずに戻り、ベースの選択は「ほか…」のまま。フッターは「↵ <名前> をベースにする」＋`↑↓ 選択` `esc 戻る`。

入力欄は一覧と同じ 1 本を使い回し、新しく mount しない（新しく mount した入力欄は `@FocusState` を取りこぼし、キーが効かなくなる）。モードに応じて入力の行き先と ↵・⇥・esc の意味だけを切り替える。⇥・⇧⇥ は握って何もしない。

### Enter（実行）

選択行の種別に応じて対象ディレクトリを解決し、選択中の起動先を、パレットを開いた workspace の**新しいタブ**でその cwd に起動する（agent は initialCommand で起動、shell は既定シェル）。起動後は次 runloop tick で新タブ surface にフォーカスを再確定する。

**行がまだ決まらない間の ↵ は預かる。** 決まっていないのは、初回の一覧が届く前と、今の入力への有効性の答えが無いまま作成行（または行が 1 つも無い状態）を選んでいるとき。預かっている間は作成中と同じ入力ロックをかけ、行が決まった時点の選択で実行する——開いた直後の ⌘T ↵ は今の worktree（git でなければ「このディレクトリ」）で開き、名前を打ってすぐの ↵ は名前が有効なら作成になる。名前が無効と分かって作成行が消え、選べる行が無ければ何もしない。一致する既存の行を選んでいれば、答えを待たずにすぐ実行する。

**対象ディレクトリの解決**:

- **worktree の行**: その worktree のルートをそのまま使う（非破壊）。今のタブのサブディレクトリは引き継がない——行が指すものと開く場所を一致させるため。
- **「このディレクトリ」の行**: そのディレクトリをそのまま使う。
- **ローカルブランチの行**: そのブランチを checkout した worktree を `git worktree add` で作る。origin を追跡する行は fetch の着地を待って判定し、fast-forward できる遅れ（ahead 0・behind > 0）なら作らずに[最新化](#最新化--遅れたブランチを追いつかせてから開く)の選択画面へ入る。それ以外（同期済み・分岐・↑ だけ・`[gone]`・upstream 無し・origin 以外）は即作成。
- **リモートブランチの行**: `origin/<名前>` から、それを upstream として追跡するローカルブランチを作って add。
- **作成行**: 選んだベースから、打った名前のブランチを upstream なしで切って add。

新しいブランチを切る経路（作成行・リモートブランチの行）は、提示時に走る `fetch --prune` の着地を待ってからベースを読む——ref の中身も、既定ブランチの名前も、着地後の値を使う（→ [データ供給](#データ供給プログレッシブ)）。ベースが「現在」（ローカルブランチ）のときも一律に待つ——待つ必要は薄いが害は無く、規則を 1 本に保てる。

**新規ブランチの upstream は経路ごとに決まり、git の既定（`branch.autoSetupMerge`）には委ねない。** リモートブランチの行は `origin/<同名>` を追跡する。**作成行のブランチは upstream を持たない**——ベースを upstream にすると `git push` がそのブランチへ向かって拒否され（`push.default=simple`）、upstream が既にあるので `push.autoSetupRemote` も発動しない。upstream が無ければ git 自身が `--set-upstream` へ導く。

**worktree の作成場所**は実効設定 `worktree-dir`（[settings](settings.md)・[config](../platform/config.md)）のテンプレートから解決する。語彙は `{repo_path}`（main worktree の絶対パス）・`{parent}`（その親）・`{repo}`（その basename）・`{slug}`（branch 名の `/`→`-`）の 4 語＋先頭 `~` のみで、既定は `{parent}/{repo}-worktrees/{slug}`。4 語はすべて `{repo_path}` 1 つから導く——`{parent}/{repo}` は定義上つねに `{repo_path}` と同値であり、その同値を呼び手が整合した値を渡すことに委ねない。置換 → `~` 展開 → **純字句の**正規化（`.`・`..`・重複スラッシュを畳む。symlink は解決しない——実在する repo root と、これから作る作成先を同じ土俵で比べるため）で確定する。語彙に語を足すときは検証の既知トークン集合と置換の両方に入れる必要がある（検証だけ通って未置換のまま残ると、その名前のディレクトリが実際に作られる）。

**共有 exclude の自動追記**: `git worktree add` は隔離ディレクトリを追加するだけで現在の作業ツリーのファイルには触れない。ただし**作成先が作業ツリー内に落ちる場合だけ**、作成に成功した後で共有 exclude（`$GIT_COMMON_DIR/info/exclude`。git は `info/exclude` を常に common dir から読むので全チェックアウトに効く）へ除外を冪等に追記する——repo 内配置を設定で選べる以上、`git status` が worktree ぶんだけ汚れる（`git add .` が gitlink 化する）のを注意書きでなく自動化で塞ぐ。契約は「**Orbe が作ったものだけを除外する**」: 対象は worktree の親ディレクトリ、ただし親が root 自身か**作成前から実在していた**なら worktree 自身（既存ディレクトリを丸ごと除外して、そこへ後から置かれたユーザーの新規ファイルまで `git status` から消さない）。既に無視されている（ユーザーの `.gitignore` 由来を含む）なら触らず、`.gitignore` は書き換えない。判定は解決済みパスだけで行い、UI の行（プリセット／カスタム）には紐付けない。除外は補助なので、失敗しても worktree 作成は続行する。

**失敗時**（パス衝突・checkout 済・ネット不通）: palette を閉じずフッターに失敗理由を赤で表示し、agent を起動しない。作成が失敗したときは除外も書かない——何も起きなかった操作がユーザーの repo を書き換えない。失敗理由は git stderr から実質行（`fatal:`／`error:` 行・無ければ最終非空行）を抜く——成功時にも出る進捗風メッセージで本当の理由を覆い隠さないため（この整形は git ラッパー層に閉じる）。

**作成中の進捗表示・入力ロック**: 非同期作成の完了を待つ間、フッターにスピナ＋「作成中…」を出す。この間は入力を受け付けない（Enter 再実行＝`git worktree add` 二重起動を弾く／↑↓・⇥・検索入力・Esc/scrim 閉じを握り潰す）。**fetch の着地待ちも同じ表示と同じロックに乗る**ので、fetch が長引くリポジトリではその間ずっとロックされ、中断はできない（`--progress` で進捗が流れる限り無応答の打ち切りも効かない）。既存 worktree 再利用など同期に済むケースは同一 tick で palette が閉じるため進捗は描画されない。

**無応答の打ち切り**: `git worktree add` は独立レーンで走り、無出力が続けば打ち切られる（→ [git](../platform/git.md)）。打ち切られたとき **worktree の実体が出来ていれば成功として開く**——post-checkout hook は worktree が完成した後に走るので、hook が返らないだけの状態を失敗として扱うと、実在する worktree を指したまま再実行が「ブランチが既にある」で詰む。実体が無いまま打ち切られたときは失敗理由として専用の文言（応答が無いため中断した旨）をフッターに出す。git が自分で理由を言えた場合はそちらを出す。

### 閉じる

Esc / scrim タップで閉じ、アクティブタブへフォーカスが返る。

## 最新化 — 遅れたブランチを追いつかせてから開く

ローカルブランチの行の worktree は、そのブランチをそのまま checkout して作る。upstream より遅れていれば古い地点から始まり、作った後に `git pull` することになる。worktree の作成は既存の ref・作業ツリーに触らない契約なので、黙って fast-forward はしない——**ユーザーが選んだときだけ進める**。

**入る条件は 1 つ**: origin を追跡するローカルブランチの行で、着地後の値が fast-forward できる遅れ（ahead 0・behind > 0）であること。Enter で同じカードの中身が 2 行の選択画面に入れ替わり、パレットは 2 行ぶんの高さに縮む。分岐（↑↓）・↑ だけ・同期済み・upstream 無し・origin 以外の upstream は即作成。

- **ヘッダー**: `❯`＋名前＋「— <upstream> より N コミット遅れています」＋右に accent の `↓N` ピル＋`esc 戻る`。入力欄と起動先・ベースの行は隠す。
- **本文**: 見出し「worktree の作り方」＋ 2 行——行 0「最新化して作成」（既定。説明 `fetch → fast-forward → <upstream> と同じ地点から`。右端は空）／行 1「そのまま作成」（説明 `ローカルの <name> のまま · <ブランチの相対日時>`）。画面はブランチの事実（遅れと相対日時）だけから組むので、どの行から入っても同じ姿になる。行頭は行 0 が ↓ 矢印（accent）、行 1 がローカルブランチのグリフ。
- **フッター**: 一覧と同じ実行説明で、前置句だけがカーソルの側を言う（「を最新化してcheckoutしたworktreeで」／「をそのままcheckoutしたworktreeで」）。右に `↑↓ 選択`（失敗時は `r 再試行` も）`esc 戻る`。
- **操作**: ↑↓ で 2 行をトグル、⏎ はカーソルの行を実行、行タップは一覧と同じくその行へ選択を移して実行（カーソルの位置に関係なく決定）、esc で一覧へ戻る（カーソルは入った行のまま）。⇥ は握って無効、⇧⇥ は既定の焦点移動に任せる。マウスホバーで選択がその行へ追従する（決定は走らない・busy では動かない）。門は一覧と同じ共有の入力モダリティで、実ポインタ移動で pointer・↑↓ で keyboard へ戻り、keyboard の間はポインタ下に行が来ても選択を奪われない。

**「最新化して作成」は fetch → fast-forward → worktree 作成 → タブ起動を 1 アクションで通す。** フッターが「最新化中… <upstream> を fetch → fast-forward」→「作成中…」と続き、作成後の worktree は upstream と同じコミットを指す。最新化中・作成中は esc を含む全キーと scrim タップを握り潰す——fetch は中断できないので、中断できる顔をしない。**この busy は一覧の作成中の旗とは別**で、選択画面のキーは画面の相だけで畳む。

ローカルの ref を進める git 操作は 3 段で、段ごとにレーンが違う（→ [git](../platform/git.md)）: remote からの fetch（独立レーン。remote も ref も upstream の事実から組み、`origin` を書かない）→ 祖先判定（読み取り。分岐は終了コードで知る）→ ローカルからの fetch でローカル ref を進める（直列レーン。ネットに触らず実質即時）。**ローカル ref の書き込みを git の fetch に委ねるのは、git 自身が書き込みの瞬間に「非 fast-forward」と「どこかの worktree で checkout 中」を検査して拒むから**——祖先判定と書き込みの間にローカルが動いても、提示時に worktree が無かったブランチが開いている間に裏のタブで checkout されていても、既存の作業ツリーを動かさない。完全 ref で名指しし、同名タグと取り違えない。

**失敗は同じ 2 行の画面に戻る。** 行 0 が失敗を名乗り（行頭 ✕・danger 面・説明 `<段> に失敗 — <理由>`・右端に同期ピル＋`r 再試行`）、ヘッダは「— 最新化に失敗（<理由>）」＋ danger の `✕ <段>` ピル、カーソルは「そのまま作成」へ落ちる（⏎ 一つで前へ進める）。`r` か行 0 の ⏎ で再試行。段は `fetch`／`fast-forward` の git 語で、理由は git が言い残した実質行（`fatal:`／`error:` 行）・打ち切りは専用文言・分岐は「<upstream> と分岐」。worktree は未作成でローカルの ref も無傷。

**最新化が済んだ後の worktree 作成が失敗したら、一覧に戻ってフッターに理由を赤で出す**（一覧の Enter の失敗と同じ畳み方）。fast-forward は済んでいるので一覧の行は同期ピルを失っている。「そのまま作成」の失敗も同じ。

「次回から確認しない」設定は持たない。

## clean — worktree の掃除

作った worktree を消せる面。マージ済みの作業も、リモートで消えたブランチも、放っておけば worktree はディスクに残って worktree の欄に並び続ける。作る側だけがあって消す側が無いと、掃除のためだけにターミナルへ降りることになる。

**入口は worktree の欄の末尾の `clean` 行 1 本**。Enter か行タップで clean モードへ入る。この行は**候補が 0 件でも残り**、行末の候補件数バッジだけが消える——同じ場所にいつでもある入口として、出たり消えたりしない。バッジは `fetch --prune` 後の分類が着地して初めて出る。フィルタは `clean` のほか `rm` / `prune` / `掃除` でもこの行にヒットする。

### 3 群 — 「要らないの推定」と「消して安全か」は別のレイヤ

clean モードは**全 worktree を出す**。危険なものを選択肢から消すのではなく、理由を添えて出したうえで初期状態では選ばれないようにする。判断はユーザーに残しつつ、勢いでは消えない。

| 群 | 意味 | 条件 |
|---|---|---|
| 安全 | 掃除して問題なし | 推定が 1 つ以上立ち、かつ安全確認をすべて通った |
| 確認 | 消えるものがある | 残り全部（推定は立つが安全確認で落ちた／そもそも推定が立たない） |
| 使用中 | 削除できない | main worktree である、またはそのパスを開いているタブがある |

- **推定**（どれか 1 つ立てば足りる）: upstream が `[gone]` ／ 紐づく PR が MERGED ／ `prunable`（実体のディレクトリが手で消されている）。
- **安全確認**（1 つでも落ちれば安全に入らない）: main worktree でない ／ そのパスを開いているタブが無い ／ locked でない ／ **レビュー中の PR が紐づいていないと確かめられた** ／ 作業ツリーが clean ／ **停止中の git 操作が無い** ／ **消してもコミットが世界に残る**。

レビュー中の PR を持つ行が安全に入らないのは、**安全群がブランチ削除を無条件に行う群だから**。レビュー中のブランチは既定で残すべきもので、消すなら明示が要る——その明示ができるのは確認群だけ。

2 つを別レイヤにするのは、**「リモートで消えた＝要らない」が偽だから**。upstream が prune 済みでも、PR がマージされずクローズされていれば、どこにも無いコミットがその worktree にしか残っていないことがある。推定だけで消すとそれが消える。

判定できなかった事実は「安全」と読まない。コミットが世界に残るかを確かめられなかった worktree は安全に入らず、独自コミット件数も名乗らない。**PR の事実も同じ扱い**で、レビュー中の PR が無いことを確かめられていない行（取得中・取得失敗）は安全に入らず、`PR #N open` も名乗らない——「無い」と「まだ分からない」を潰すと、確認前の状態が安全確認を素通りする。

**locked な worktree は「確認」に入る**。強制削除は locked を外さないので、安全に入れると「初期チェック済みなのに実行すれば必ず失敗する」罠になる。使用中に入れないのは、ユーザーが手で unlock して消せるから。

**タブの占有**は全 workspace × 全タブを走査して判定する（休眠 workspace のタブも含む）。パスは両辺を正規化して構成要素単位で前置一致を見る（macOS の `/tmp` `/var` は symlink で、素の文字列では一致しない）。子ディレクトリにいるタブも占有とみなし、worktree が入れ子なら最も長く一致したものへ帰属させる。

### 行の状態は 3 軸の直積

行が置かれた状況は独立した 3 つの軸の積で、単一のラベルの列挙では網羅できない。

| 軸 | 問い | 語彙 |
|---|---|---|
| A: worktree の中身 | 消すと何を失うか | 未コミットの変更／未追跡ファイル／停止中の git 操作／実体なし |
| B: ブランチの行き先 | 消すと世界に残るか | マージ済み PR（マージ先つき）／取り込み済み（merged → 実マージ先）／リモート反映済み／remote より進んでいる／未 push／レビュー中の PR／`[gone]`／独自コミット |
| C: 使用状況 | 誰かが使っているか | agent の稼働状態／タブで表示中／locked／main worktree |

軸A と軸B から**行末のラベルは最大 2 枚**まで。軸C はラベルではなく群の移動で表す（`locked` だけは確認群に置いたうえでラベルにも出す——強制削除でも外れないことが、その行が安全に入れない理由そのものだから）。**枠に載らなかった語は捨てず、展開したサブラインに同じ姿で並べる。** 片方の軸が黙っていれば、空いた枠はもう片方の 2 つ目で埋める。

**語が主張として偽になるなら、色を弱めるのではなく言わない。** コミットが世界に残ると確認済みのブランチは「未 push」「remote より進んでいる」を名乗らない——これらは「そのコミットがどこにも残らない」という主張であり、その行では嘘になる。失うものがある行では独自コミット件数がそれを名指す。

同じ原則が**取り込みの語を証明の種類で出し分ける**ことも決める。tip を含む比較先のある行と patch 等価の行は「merged → \<実マージ先\>」が真なので名乗る。到達性だけで安全が立った行は、単に完全 push 済みで未マージでも成立するため「merged」を名乗らせず、主張できる範囲だけを言う「リモート反映済み」を出す。

**「リモート反映済み」が語るのは「remote 上にコミットが存在する」という 1 つの事実**で、到達性が証明できた行と、upstream があって track が空（＝upstream と一致）の行のどちらでも立つ。後者は前者を含意する（upstream と一致していればコミットは必ず remote にある）ので、2 つを別の語に割っても読む側の判断材料は増えない。

**含意される語は重ねない。** マージ済み（「merged → \<X\>」または「PR #N merged → base」）が立つ行では「リモート反映済み」を出さない——マージされていれば remote に在ることは含意される。「remote +N」は一部しか remote に無いので「反映済み」が偽になり、そもそも立たない。結果として「merged → \<X\>」「リモート反映済み」「未 push · ローカルのみ」は排他になる。

**merged PR チップが立つ行では「merged → \<X\>」はピル枠を争わずサブラインへ降りる**——同じ「merged」を 2 枚並べず、空いた枠は次の事実（`[gone]` 等）が埋める。PR チップは判定には使わないが、表示上の安全根拠としては真の主張なので右クラスタに立つ。降ろすのは重複するこの語だけで、軸B の他の語は「merged」を名乗らないので枠を争ったまま残る。

**安全確認に使う事実（作業ツリーの状態・停止中の git 操作・取り込み判定・紐づく PR のどれか）を確かめられなかった確認行には判定不能チップ（「情報取得に失敗」・琥珀）が立つ**——基本起こらない異常系なので内訳は持たず、チップ 1 枚だけで語る。分類（群の振り分け）は変えない——判定不能を安全と読まない契約は分類側が持つ。prunable 行は作業ツリー側（status・停止中の操作）を意図的に問わないので、そこが取れなくても判定不能にはしない——失うものが無く、確認の対象ですらない。判定不能チップは損失の内訳（「〜も消えます」）には載せない——何が失われるかは不明で、消えると断定すれば嘘になる。取得**中**の事実はこのチップでは語らない——まだ失敗していないので、行頭のグリフ（下記）が「まだ動いている」を語る。

### 停止中の git 操作

rebase・merge・cherry-pick・bisect の途中で止まっている worktree は、**作業ツリーが clean に見えることがある**（コンフリクトの無い停止点）。status だけを見ていると安全確認を通ってしまい、初期チェック済みのまま消える。

判定は worktree の gitdir 直下に該当のファイルがあるかで行う。gitdir は worktree の `.git`（main worktree ではディレクトリ、リンク worktree では `gitdir:` 1 行のファイル）から解決するので、**git を新たに起動しない**。読めなければ「判定できなかった」として安全に入れない。

この確認は分類のときだけでなく、**削除を撃つ直前にも取り直す**。画面を開いた後に始まった操作を、強制削除が管理ディレクトリごと消さないため。

### 消してコミットが世界に残るかの判定

問うのは「既定ブランチに入っているか」ではなく「消してコミットが世界に残るか」。既定ブランチを比較先に固定すると、統合先が既定ブランチでないリポジトリ（git-flow の develop 統合など）で、統合先へマージ済みのブランチが「独自コミット +N 件」と誤表示され、この機能の主用途がそのまま外れる。

**3 段構えで判定する。**

**第0段（到達性）**: `git rev-list --count <tip> --not --remotes=origin --` が 0 なら、全コミットが `refs/remotes/origin/*` から到達可能で、worktree とローカルブランチを消してもコミットはそこに残る。比較先を推測せずに意味論を直接問えるので、統合先がどこであっても成立する。

信頼する ref を **origin に限る**のは、鮮度を保証できる範囲と揃えるため。prune するのは origin だけなので、fork や upstream の tracking ref は remote 側で消えた後もローカルに残り続ける。それを根拠にすると `[gone]` で安全群に入った行が stale な ref だけを頼りにブランチごと消え、後で全 remote を prune した時点でコミットが到達不能になる。origin に限れば「`[gone]` を作る prune」と「信頼する ref を掃除する prune」が同一操作になり、その組み合わせが構造的に消える。

`--` でオプションを終端するのは、`rev-list` が pathspec も取るため。終端しないとリポジトリ直下のエントリと同名のブランチ（`docs` 等）で `ambiguous argument` になり、その worktree だけ第0段が黙って失敗する。

判定に渡す名前は、ブランチのある行は `refs/heads/<branch>` の**完全 ref**・detached は oid（全段共通）。短縮名は refs/tags が refs/heads より先に解決されるため、同名タグ（`v1.0` をタグとブランチの両方に切る運用等）があるとタグの指すコミットを判定してしまう。

**第1段・第2段（比較先リストとの patch 等価）**: squash / rebase はマージで SHA が変わり到達性では見えないので、`git cherry` の patch-id 比較で拾う。比較先は**リスト**＝`[既定ブランチ] + 紐づく merged PR の base（origin/<base> がローカルに実在し既定と異なる場合）`。gh はリストへ 1 本足すヒントのみで**証明はローカル**——嘘の base は比較の不成立で確認群のままに倒れる（安全側）。これで squash 運用の git-flow（develop 統合・squash マージ・remote ブランチ削除）でも実マージ先との patch 等価が立つ。`git branch --merged` でも `git log <default>..<branch>` でも取れない——merge commit と squash が混在すると squash 済みブランチが未マージとして残るため。

ただし**素の `git cherry` 単独でも足りない**。cherry はコミット 1 個ずつの patch-id を比べるので、複数コミットを 1 つに畳んだ squash では畳んだコミットの patch-id が元のどれとも一致せず「未取り込み」と誤判定する。まず素の `git cherry` を見て未適用が 0 なら取り込み済み（fast-forward・merge commit・rebase・cherry-pick・単一コミットの squash がここで片付く）。残ったものについて、ブランチの累積差分を 1 個のダングリングコミットに合成してから再度 cherry にかけ、比較先側に同じパッチがあれば squash 取り込み済みと判定する。**2 段とも要る**——後段だけでは比較先の厳密な祖先であるブランチに対して偽陽性を返す（合成が空パッチになるため）。第1段は全比較先を先に回してから第2段へ移る（後続の比較先が 1 プロセスで立つとき 4 プロセスの後段を省くため。空パッチの偽陽性は同じ比較先の第1段が防ぐので、この順序でも防波堤は保たれる）。

合成は到達不可能なコミットオブジェクトを 1 つ書く（ref は触らず、いずれ gc で消える）。

**結論は 3 つ**: 到達性で立った（`リモート反映済み`、tip を含む比較先があるなら `merged → <実マージ先>`）／patch 等価で立った（`merged → <実マージ先>`）／どれも立たない（未取り込み）。名乗るのは**証明が立った比較先のローカル名**（先頭の `origin/` を落とした形）。複数立つときは**先に立った段**が勝ち、同じ段の中ではリスト順＝既定優先。到達性の行が名乗るのは tip を含む最初の比較先で、これはラベルの決定だけで安全事実そのものには関わらない。**判定できなかったときは 4 つ目の値**で、安全とは読まない——`.unmerged` は「どの比較先にも patch 等価でない」という主張なので、1 本でも確かめられなければ名乗らず判定不能に倒す。

未取り込みの行が「注意」の理由に出す独自コミット件数は、**到達不能数と、各比較先の patch 非等価数の最小との min**。どちらも「真に失われる数」の過大評価なので、min はより良い過大評価になる（既定ブランチが統合ブランチより遅れたリポジトリで「独自コミット +106」型の巨大数が実数へ縮む）。

### 選択と実行

安全群の行は**確定した時点でチェック済み**になり、確認群は未選択、使用中は選べない。↑↓ は選べる行だけを群順に巡回し、使用中と未確定行を飛ばす。space / Enter / 行タップでチェックを切り替える。⌘Enter で実行し、0 件では何も起きない。Esc は一覧へ戻る（パレットは閉じない）。ハイライトはカーソル行だけが持ち、**チェックは 2 値**で、その状態はチェックボックスの塗りだけが示す。

**行ごとに「必要な事実が揃ったか」を持ち、揃った行から使えるようになる。** 画面は開いている間ずっと最新の分類を映す。

- **入るのは即座**。分類が未着地でも clean モードへ入り、1 行も無い間はスケルトン行が埋める。分類は prune の後にだけ撃たれるので、行は prune 済みの ref を読んだ結果として生える。
- **揃っていない行は、表示はされるが選択の対象外**。行頭のチェックボックスは回転グリフで、カーソル巡回もタップも素通りする。使用中の行は行頭が空で減光する——**動きの有無と減光の有無**という 2 軸が「まだ選べない」と「削除できない」を分ける。
- 行が要求するのは、その worktree の実測（作業ツリー・停止中の操作・取り込み判定）と、その head の PR 取得の決着。detached は PR の head になり得ないので PR 軸を待たない。
- **揃った瞬間に選択可能になり、安全群ならその時点で 1 度だけ**チェックが灯る。以後その行のチェックはユーザーだけが動かす。行が再び未確定へ戻ってもチェックは覚えているが、**その間は件数にも ⌘Enter の実行対象にも入らない**——見えないチェックのまま消えることが無いよう、「チェックボックスが立って見えている行」と「実行される行」を同じ集合にする。
- カーソルは**行 id** で同じ worktree を指し続ける（前に並ぶ行が揃って増えても指す先は同じ）。指していた行が消えたら近傍へ落ちる。消えた worktree のチェックとブランチの扱いも一緒に落ちる。
- **選択が実行内容として確定するのは ⌘Enter の瞬間**で、そこで組んだ依頼だけが削除中・一部失敗の画面を駆動する。削除直前の作業ツリー・停止中の操作の取り直しと、ブランチ先端の照合はそのまま働く。

**ローカルブランチを消すかは、安全と確認で決まり方が違う。**

- **安全**: 実体があり、ブランチがあり、消してもコミットが世界に残ると確認済みの行だけがブランチも消す。実体が無い prunable 行は登録を消すだけでブランチに触らない。
- **確認**: チェックした行の下にサブラインが開き、そこで `残す`（既定）／`削除` を選ぶ。**`削除` を選ぶ行為そのものが安全確認の上書き**であり、どこにも残らないコミットを持つブランチはこの明示がなければ消えない。

**実行すると何が起きるかは、実行前に必ず読める——ただし語る場所はカテゴリで分かれる。** 行の右クラスタは状態（3 軸の事実）だけを語り、動作の予告は載らない。

- **安全群の見出し**が群の動作宣言を持つ（「安全 — worktree を削除（対象によってはローカルブランチも削除）」）。prunable 行がブランチに触らない例外は「対象によっては」の含みが吸収し、実態は行の `prunable · 実体なし` チップとフッタの内訳から読める。
- **フッタの実行ボタン**が実行の総量を語る。ブランチも消える行が選ばれているときは「worktree N 件とローカルブランチ M 件を削除」の内訳付き、0 件なら worktree 数だけ（0 件の内訳は出さない）。
- **確認群のサブライン**が行別の動作選択（`残す`／`削除`）を持つ。

**サブラインはその行の詳細であって、ブランチの選択欄ではない。** ブランチの `残す`／`削除` はそこに載る中身の 1 つで、失われるものの内訳と、ラベルの枠に載らなかった語も同じ場所に並ぶ。だから detached の行——rebase の停止中は必ずこの形になる——でも、書くことがあれば開く。書くことが何も無ければ開かない。

**立った事実は、その行の状態で必ず画面から到達できる。** ラベルに載るか、サブラインに載るか。どちらの経路も持たない語を作らないことが、削除を撃つ前に読める情報の下限を決めている。

ブランチの削除は**⌘Enter で確定した時点の先端であるときだけ**実行する（確定後に積まれたコミットは残る）。worktree の削除は、直前に作業ツリーの汚れと停止中の git 操作を取り直して確かめてから実行する。

削除自体は強制削除で呼ぶ。submodule を持つ worktree は通常の削除が無条件に拒否されるためで、拒否を握り潰しているのではなく——強制が外す「汚れている」「submodule を持つ」の 2 つのうち、汚れは直前に Orbe 自身が確認済み、submodule は per-worktree のチェックアウトが消えるだけで実体は共有ディレクトリに残る。

### 削除の進行と失敗

削除は 1 件ずつ直列に進み、**選んだ行だけが実行順に並ぶ**（未選択の行は畳んで見えなくなる）。**行頭のチェックがそのまま進捗になる**——完了・実行中・待機が同じ位置で入れ替わり、行の meta 列には何が起きたかが出る。

**途中で失敗しても中断せず全件試みる。** 削除は取り消せないので、止めても部分実行済みの状態は残る——ユーザーが頼んだ残りを止める理由がない。

Esc は**まだ撃っていない残りを止める**。実行中の 1 件は完走させる（`git worktree remove` を途中で殺すと管理ディレクトリが半端に残り、「消えかけの worktree」という新しい状態が生まれる）。実行済みは戻らない。

**失敗しても成功した行を消さない。** 削除中と一部失敗は同じ行集合の別の時点であり、どの行が・なぜ落ちたのかを消えた行の跡地から推測させない。失敗した行はその場に赤で残り、理由（どの段階で落ちたか）と git の生の出力、そして再試行とタブで開く導線をその行の中に持つ。Enter は失敗した行だけを**⌘Enter で確定した依頼のまま**撃ち直す（同じ依頼を使うので、ユーザーが見て承認した根拠と実行される内容が一致する。それでも危険にならないのは、ブランチ削除が先端の照合を、worktree 削除が直前の確認を毎回その場で通るから）。worktree が消えてブランチだけが残った行は、残りのブランチ削除だけを撃ち直す。

**終端は失敗の有無で分かれる。** 1 件も失敗しなければ一覧へ戻り、掃除の結果が worktree の欄と `clean` 行の候補件数に反映された姿で見える。1 件でも失敗すればその画面に留まり、Esc でパレットを閉じる。中断も同じ終端を通る。

**共有 exclude の後始末はしない。** worktree の作成が `$GIT_COMMON_DIR/info/exclude` へ除外を追記した場合（作成先が作業ツリー内に落ちる設定のときだけ）、その行は削除後も残る。1 本の除外行が親ディレクトリを指して複数の worktree をまとめて覆うことがあるため、消すには残った worktree との突き合わせが要る。存在しないパスの除外は無害で、同じ場所に作り直せばそのまま再利用される。
