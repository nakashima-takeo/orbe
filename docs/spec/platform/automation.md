# 自動化

Slack の自分宛のメッセージや GitHub のレビュー依頼のように、外から届くものを人が見張らなくても、取って・絞って・判断した結果が手元に届くための仕組み。自動化は「いつ回すか」「何を取るか」「どう処理するか」「結果をどこへ出すか」を持ち、Orbe が[裏で](background.md)予定どおり取得し、前の回に無かった項目だけを処理の段に流し、最後の段の出力を出力先へ渡す。今ある出力先はタスク候補だけで、タスク候補の自動化は、[タスク](tasks.md)にすべきものを最後の段が返した候補として検証して覚える。出力先がタスク候補の自動化は「タスクの自動追加」とも呼ぶ。自動化を作り・直すのは AI（MCP・`orb automation`）で、候補をタスクにする・捨てるのは人の判断として Orbe の中に残す。コード・制御 API・MCP・`orb` では、この仕組みを automation、候補を proposal と呼ぶ。

## 定義

自動化は使い回さない短い整数の ID と、次の形の定義で決まる。定義は常に丸ごと置き換わる。

```
トリガー → 取得元（任意）→ 処理の段 0 個以上 → 出力先
```

- **名前**: 「出どころ: 何を取るか」の 1 行。規則はタスクのタイトルと同じ。
- **トリガー**: 裏の仕組みの「○分ごと」か「毎日の時刻」。
- **取得元**: やり方と性質を持つ。
  - やり方は、シェルのコマンド（`/bin/sh -c`・任意の作業ディレクトリ）か、軽い agent（CLI・モデル〔省略可〕・使ってよい MCP のツール 1 つ以上・依頼文）。コマンドは 1 項目 1 行の JSON を自分で出す。agent には Orbe が同じ出力の形を指示する。
  - 取得元の agent が使えるのは、名指しした MCP のツール（完全名 `mcp__<サーバー>__<ツール>`）だけ。組み込みのツール・サーバー単位（`mcp__<サーバー>`）・ワイルドカードは理由付きで断る——外から届いた文面を読む役に、文面に仕込まれた指示で書き込みをさせないため。この絞り込みは、名指ししたツールが読み取りのツールであることが前提で、Orbe は名前の形しか確かめない。書き込みのツール（送信・更新・削除）や Orbe 自身のツールを名指しすれば絞り込みの外になるので、MCP・CLI の説明で AI に「出どころを読むツールだけを名指しする」と伝える。ただし取得元は利用者の MCP サーバーを名前で使うので利用者の claude の設定を読み、利用者が claude で常に許可したツールは Orbe からは締め出せない。
  - 性質は「**今の集合**」（取得結果がその時点の全体。例: 自分が担当の未完了課題）・「**新着の流れ**」（取得結果は新着だけ。例: 自分宛の新しい DM）・「**毎回全件**」（前回の取得結果との差分を掛けない）のどれか。枠の差分を掛けるかと、候補の下げ方がこれで決まる（→ [候補の保ち方](#候補の保ち方)）。出どころの種類を Orbe は知らないので、AI が選ぶ必須の項目。
- **処理の段**: 名前（1 行）と、コマンドか agent（CLI・モデル〔省略可〕・指示文）。段は JSON の行を受けて JSON の行を出し、状態を持たない。段の agent はツールを持たない閉じた形でだけ走る——外から届いた文面を読む役に、何かをさせる手段を渡さないため。
- **出力先**: 最後の段の出力の形と、届け方・確定のしかたを決める。今あるのは**タスク候補**だけで、取得元（今の集合か新着の流れ）と段 1 つ以上が要る。

モデルを省略すると、最後の段は sonnet、それ以外の段と取得元は haiku で走る。保存は省略のまま持ち、走らせるとき・画面に出すとき・書き換えの比較で同じ規則で解く——段の並びを変えたら既定も追従するため。

agent は裏で回せる CLI だけを受ける（claude。codex・agy は理由付きで拒否する → [background](background.md#非対話の-agent)）。

取得の出力 1 行が 1 項目で、`id`（その出どころの中で変わらない ID）・`link`（http か https の URL）・`body`（本文）・`time`（ISO 8601）を持つ。この形はどの取得元でも同じ。`id` は自動化の中での同一性で、段を通しても項目をたどる鍵になり、同じリンクに新しい動きがあったときに判定へ回し直すためにも使う。`link` は自動化をまたぐ同一性。

止めることができ、止めるのは予定だけ。止めた自動化も「今すぐ」は受ける——有効にする前に試し打ちできるように。

## 1 回の流れ

1 回は次の流れで、全体が番人の 1 回になる。1 回が終わるまで同じ自動化の次の回は始まらず、走っている間の「今すぐ」は断る。状態を読み書きするのは Orbe の枠と出力先だけで、段は状態を持たない。

1. **取得元**を走らせる。
2. **枠の差分**: 取れた項目のうち、この自動化の前回の取得結果に `id` が無いもの。全件見直しの回と毎回全件の取得元では掛けない。
3. **出力先の取り込み**: 差分の後の項目に、出力先が自分の条件を掛ける。タスク候補の条件は、同じリンクの候補が（どの状態でも、どの自動化のものでも）無いことと、同じ回に同じリンクが複数あれば最初の 1 件だけ。ここまでで残った項目が**新しい項目**。
4. 新しい項目が無ければ段を起こさず、成功として確定する。あれば**段**を 1 つずつ回す。最初の段には新しい項目を 1 行 1 項目の JSON で渡し、各段の出力のうち JSON オブジェクトとして読めた行をそのまま次の段へ渡す。中間の段が 1 行も残さなければ、そこで止めて成功として確定する。
5. **出力先が読む・届ける**: 最後の段の出力を出力先が読み、届ける。届けは時間がかかってよく、失敗しうる（タスク候補はすぐ終わる）。
6. **確定**する。その時点の状態に当て直し、前回の取得結果・全件見直しの印・前回成功の目印・出力先の状態（候補と下げ）・回の記録を 1 度に保存する。

段への渡し方は、コマンドの段には標準入力で、agent の段には Orbe の固定の枠の依頼文で渡す。中間の agent の段の枠は、役割・ツールが無いこと・今の日時とタイムゾーン・利用者の指示文・入力行と、出力の決まり（1 行に 1 オブジェクト・渡す項目の `id` を保つ・残らなければ何も出さない）を載せる。最後の段の依頼文は出力先が組む（→ [判定の入出力](#判定の入出力)）。

確定はその時点の状態への当て直しで、回の途中に起きたこと（他の自動化の確定・人のさばき）を上書きしない。同じリンクを 2 つの自動化が同時に判定していたら、後から確定した側の候補は理由付きで捨てる。判定が「対応済み」とした候補も、その時点でまだ人の判断待ちのものだけを対応済みにする。

途中では何も保存しない。Orbe が回の途中で終わったら最後に回った時刻は進んでいないので、次の起動で過ぎた回として 1 回だけやり直す。

## 項目の同一性

項目は取得元の行の `id` でたどる。Orbe は段の間で行に印を付けない——コマンドの段（jq など）では保てず、段に状態を持たせないため。代わりに、タスク候補の出力先が今回の新しい項目の `id` に当て直して確かめる。

- 最後の段に渡す行のうち、`id` が今回の新しい項目のものでない行は、理由付きで捨てる。1 行以上あって全部が捨てられたら、回の失敗にする。
- 最後の段の候補（`propose`）の `id` も、今回の新しい項目のものだけを受ける。
- 候補のリンクと本文は、いつも取得元の項目から取る。段が作った文やリンクを候補に入れないため。

段の途中で `id` が落ちた回を成功と読むと、項目が「見たもの」になって二度と流れない。そのため失敗にして、前回の取得結果を進めない。

## 前回成功の目印

確定（成功）した回の開始時刻を、自動化ごとに覚える。最後に回った時刻（番人の数え始め。失敗した回でも進む）とは別物。

新着の流れの取得元にだけ、値があれば常に渡す（全件見直しの回や、書き換えた直後の回も）。渡し方は、agent の取得元なら依頼文に「この時刻以降を取る。前の分が混ざってもよい（Orbe が既に見たものを除く）」の 1 文を足し、コマンドの取得元なら環境変数 `ORBE_SINCE`（ISO 8601。UTC・ミリ秒・`Z`）を子の環境に置く。目印の無い回は文も変数も置かない。

- 開始時刻にするのは、回の途中に届いた項目を次の回で取りこぼさないため。重なった分は `id` の差分で消える。
- 遅れて見える出どころは、取得元の側で余白を取ればよい。余白の適量は出どころごとに違い、Orbe が 1 つの値に決められないため。取得元が毎回同じ余白を取れば、余白の分は必ず前回の取得結果に入っているので、二重にはならない。
- 書き換えた直後の回にも渡すので、見直されるのは前回成功以降に届いた分だけ。外すと、さばいて既に忘れた候補が取得に戻り、二重に出る。
- 失敗した回では進まない。

## 候補の保ち方

**候補はリンク単位で、すべての自動化を通じて 1 つ**。状態は「人の判断待ち」「タスクにした」「捨てた」「判定が対応済みとした」の 4 つ。

候補が忘れられるのは、**どの自動化もその候補を持たなくなったとき**だけで、そのとき人の判断待ちだったものは「下げた」として回の記録に数える。候補を持てるのは出力先がタスク候補の自動化だけで、持つのは、前回の取得結果にそのリンクがあるとき、または新着の流れの自動化が自分で出してまだ人の判断待ちのとき。別の出力先の自動化が同じリンクを取っても、候補を抱え込まない。

- **今の集合**: 取得から消えたリンクは、その時点の全体から外れた（課題が閉じた・自分の担当でなくなった）ので、持たなくなる。人の判断待ちなら Orbe が下げる。
- **新着の流れ**: 元の項目が次の回に取れないのは対応済みの意味ではないので、人の判断待ちのうちは取得から消えても持ち続け、判定に見せ続ける。判定が対応済みとした・人がさばいた後は、取得に無ければ忘れる。

タスクにした・捨てた・対応済みの候補も、忘れるまでは覚えていて同じリンクを再び候補にしない。消えた後で同じリンクが再び現れれば、もう一度判定に回る。止めた自動化も持つ——止めただけで候補は消えない。自動化を消すと、その自動化だけが持っていた候補は忘れる。

覚え続けるのは前回の取得結果だけ。新しい項目・候補の下げ・重なり・棚の持ち主がすべて同じ集合で言えるので、取得済みを際限なく溜めない。

## 棚と重なり

候補を見せる場所は自動化ごとの棚で、**棚に出す自動化**は読むときに決める——候補を出した自動化がまだ候補を持っていればそれ、いなければ持っている自動化のうち ID が最小のもの。保存しないのは、持ち主の取得結果からリンクが消えて別の自動化だけが取るようになったときに、保存した持ち主がずれるため。

出力先がタスク候補の自動化には「同じ出力先の他の自動化と前回の取得結果のリンクが何件重なっているか」が相手ごとに出る。保存せず前回の取得結果から導く。2 つの自動化が同じものを取っているとき、候補は 1 つで済むが、範囲を切り直す手がかりになる。

## 失敗した回

失敗した回は、回の記録と「最後に回った時刻」だけを進め、前回の取得結果も候補も前回成功の目印も動かさない——失敗を「0 件取れた」と読み違えて候補を一斉に下げないため。代わりに、壊れたままの自動化は回るたびに失敗を記録し続け、AI が記録の理由を読んで直す。

取得元の失敗は次のいずれか。

- コマンドの終了コードが 0 でない、出力が UTF-8 でない。
- agent が最終応答を返さずに終わった・失敗を報告した。指定した MCP のツールが始まりの時点で揃わなかった（モデルを呼ぶ前に止まる → [background](background.md#非対話の-agent)）。
- 出力に `{"error": "…"}` の行（`id` を持たず文字列の `error` を持つ）がある。コマンドでも同じ。
- 1 行以上あって全部が形違い。

段の失敗は次のいずれか。段が失敗した回も前回の取得結果を進めないので、同じ項目は次の回でまた段に回る。

- コマンドの終了コードが 0 でない、出力が UTF-8 でない。
- agent が最終応答を返さずに終わった・失敗を報告した。
- 中間の段の出力が 1 行以上あって、全部が JSON オブジェクトでない。
- 最後の段に渡す行が 1 行以上あって、`id` が今回の新しい項目のものが 1 つも無い（→ [項目の同一性](#項目の同一性)）。

最後の段の形の違う行は、捨てて理由を残すだけで失敗にしない。最後の段が文章だけを返した回は「候補なし」で確定する。出力先へ届けるのに失敗した回も、回の失敗にする。

取得元がツールを使えたうえでツールの結果がエラーになり、`{"error":…}` を出さずに空を返した場合は「0 件」と区別できず、候補が下がりうる。

## 判定の入出力

タスク候補の出力先が、最後の段に渡すものと受けるもの。最後の段が agent なら、出力先が Orbe の固定の枠で依頼文を組む。役割・今日の日付と時刻とタイムゾーン（期限を決めるため）・利用者の指示文・新しい項目（確かめた入力行）・人の判断待ちの候補（リンク・タイトル・期限）・出力の形を載せる。載せる候補は最後の段を始める時点で取り、この回の取得結果にあるものと、新着の流れならこの自動化が出して判断待ちのままのもの——新着の流れでは、対応済みの知らせが元の項目とは別の新しい項目として届くため。最後の段がコマンドなら、入力行を標準入力で渡すだけで、判断待ちの候補は渡らない（`resolve` は出せない）。

出力は 1 行 1 つの JSON で、2 種類だけを受ける。

- `{"propose": "<項目の id>", "title": "…", "due": "YYYY-MM-DD"}` … 今回の新しい項目への候補。1 項目に 1 つ。タイトルはタスクのタイトルの規則、期限は暦にある日付（省略可）。
- `{"resolve": "<リンク>"}` … 今回渡した人の判断待ちの候補を対応済みにする。

それ以外の行——JSON オブジェクトでない（段の記録に数える）・形が違う・知らない項目や候補を指す・タイトルや期限が不正・同じ項目への 2 つ目の候補——は捨て、理由を回の記録に残す。形を利用者の指示文に任せないのは、自動化ごとに形が割れて検証できなくなるため。

取得元の agent にも固定の枠を当てる——渡したツールだけで依頼文どおりに取り、1 項目 1 行の JSON だけを出し、ツールが失敗・使えないときは `{"error":…}` の 1 行だけを出す。

初回や書き換え直後は取れた全件が段に載るので、依頼文が大きくなる。裏の 1 回の上限（最終応答の大きさ・経過時間）を超えれば段の失敗として記録され、次の回でまた全件を段に回す。

## 回の記録

各回について、始まりと終わり・きっかけ（予定か今すぐ）・取得元・新しい項目の数・各段・出力先の記録・失敗ならその理由を、新しい順に 20 件まで残す。失敗した回は、届いたところまでを持つ。AI は記録を読んで、取得の範囲や指示文を直す。

- 取得元と段の記録は揃った形で、実行したコマンド行・終わり方・数・捨てた行の数と最初の数件の理由を持つ。数は、取得元なら項目として読めた数、段なら JSON の行として読めた数。段は名前も持つ。
- 出力先の記録は確定した回だけが持つ（段を起こさなかった回も、下げた数があるので持つ）。タスク候補は、受けた候補の数・対応済みにした数・下げた数・捨てた行（`propose`・`resolve` として読めなかった行と、確かめ・確定で捨てた行）。

## 書き換えの扱い

- **何をするかの書き換え**（取得元のやり方・段の手段とモデル〔省略は解いた値で比べる〕と指示文かコマンド・出力先）: 走っている回を止めてその結果を捨て、次の回は枠の差分を掛けずに見直す。既に候補のあるリンクは見直さない（二重には出ない）。何をするかが変わったので、走っている回は意味を失う。
- **名前・トリガー・取得の性質・段の名前だけの書き換え・止める／再開**: 走っている回を止めず、予定だけを差し替える。段の名前を変えただけ、モデルを省略から同じ値の明示に変えただけで、全件見直しの費用を払わせないため。取得の性質を変えて誰も持たなくなった候補は、その場で忘れる（回の記録には数えない）。数え始め（最後に回った時刻）は動かないので、長く止めていた自動化を再開すると過ぎた回として 1 回すぐ回る——再開したらまず最新を取る（[background](background.md#予定と次の時刻) の「過ぎた回は 1 回だけ」と同じ規則）。
- **削除**: 走っている回を止め、結果は捨てる。

## 候補をタスクにする

人の判断待ちの候補だけをさばける。

- **タスクにする**: 候補のタイトルと期限・未着手のタスクを、[Home](workspace.md#home) に付けて、画面から足したタスクと同じ位置（[その優先度の未着手の先頭](tasks.md#一覧は-1-本の列)）に足し、詳細欄にリンクと取得した本文を入れる。本文は外の文面なので、agent への最初の入力には載らない——Home のタスクを [`start_task`](../control/api.md) で始めても、最初の入力はタスクの ID・タイトルと頼み（`prompt`）だけで、詳細は agent が MCP で読む（ツール結果の席）。自動化の候補はリポジトリに属さない仕事が主で、Home に付けば秘書がそこから始められるため。人が受けて足すタスクなので、入力欄から足したタスクと同じく未着手の上の方で目に入る。追加が拒否されたら候補は変わらない。
- **捨てる**。

さばいた候補は人の判断待ちから外れ、後から届いた判定でも上書きされない。人の判断待ちでない候補をさばこうとすると、値の不正とは別の失敗（判断待ちでない）として断る——判定の確定や下げと行き違っただけの操作を、画面が誤りとして出さないため。この 2 つは Orbe の画面（⌘⇧X の[自動追加タブ](../palette/automation.md)）の口で、AI には出さない。タスクにする操作はタスク一覧と自動化の 2 つのファイルへ書くので、間で落ちるとタスクができたのに候補が判断待ちのまま残りうる。

## 保存

自動化の定義・前回の取得結果・全件見直しの印・最後に回った時刻・前回成功の目印・回の記録・候補を、state ディレクトリの `automations.json` 1 つに置き、変更のたびに即座に保存する。1 回の確定は 1 度の書き込み。後から足すフィールドは欠落を許容し、在るのに使えない原本（読めない・構造破損・非互換 version・定義の不正・ID やリンクの重複）は [persistence](persistence.md) の規律で退避してから空で始める。

起動時にすべての自動化を番人へ載せる（止めた自動化は予定なしで）。数え始めは最後に回った時刻、まだ回っていなければ作った時刻。

## 操作の口

[制御 API](../control/api.md) の 6 動詞（`list_automations`・`set_automation`・`run_automation`・`pause_automation`・`delete_automation`・`list_automation_proposals`）を MCP にも出し、`orb automation`（[cli](../control/cli.md)）からも同じ形で叩ける。自動化も候補もイベントにはならない。

外の口は、定義と回の記録を保存と同じ形で読み書きする。定義は `definition` の欄に入れ子で置き、Orbe が持つ状態（止めているか・次の時刻・回の記録など）と同じ階層に混ぜない。AI は一覧の `definition` を取って直し、そのまま `set_automation` に送る。一覧は省略したモデルを省略のまま返す——解いた値で埋めて返すと、書き戻したときにモデルが固定され、段を並べ替えても既定が追従しなくなるため。外の形と保存の形が同じなので、保存の形を変えると外の形も変わる。出力先ごとの状態（タスク候補なら、棚の候補の数と重なり）は、その出力先の自動化にだけ付ける。

人の画面は 2 つ: ⌘⇧X の[自動追加タブ](../palette/automation.md)と、Home の[ボード](../chrome/board.md#自動追加の部品)。どちらからも止める ⇄ 再開・今すぐ実行・削除ができ、キー・キーの表示・断りは 1 つの定義を共有する。定義を足す・書き換えるのは AI の口だけ。どの口も同じ唯一の正を変えるので、片方の画面での操作はもう片方にすぐ映る。

人が自動化を作る・直すときの口は、Home のボード。[依頼の欄](../chrome/board.md#依頼の欄)に打った文は自動化の依頼として、一覧で選んで ⌘↵ を押すとその自動化の直しとして（[直しを依頼](../chrome/board.md#直しを依頼)）、その場で[秘書](../agent/secretary.md)に届き、秘書が `set_automation` で書く。人は定義の項目を自分で埋めず、やりたいことを言うだけで済む。
