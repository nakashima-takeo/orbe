# 自動化

Slack の自分宛のメッセージや GitHub のレビュー依頼のように、外から届くものを人が見張らなくても、取って・絞って・判断した結果が手元に届くための仕組み。自動化は「いつ回すか」「何を取るか」「どう処理するか」「結果をどこへ出すか」を持ち、Orbe が[裏で](background.md)予定どおり取得し、前の回に無かった項目だけを処理の段に流し、最後の段の出力を出力先へ渡す。出力先は**タスク候補**・**コマンド**・**報告**の 3 つ。タスク候補の自動化は、[タスク](tasks.md)にすべきものを最後の段が返した候補として検証して覚える。コマンドの自動化は、届いた行を標準入力に渡してコマンドを走らせる（例: 毎晩 23 時に `~/bin/daily-note.sh` を実行する）。報告の自動化は、最後の段が書いた文章をその回の結果として残す（例: 毎日 18 時に開いている PR を要約する）。どの自動化にも通知の設定を付けられ、出した回・失敗した回をメニューバーか macOS の通知センターで知らせる。出力先がタスク候補の自動化は「タスクの自動追加」とも呼ぶ。自動化を作り・直すのは AI（MCP・`orb automation`）で、候補をタスクにする・捨てるのは人の判断として Orbe の中に残す。コード・制御 API・MCP・`orb` では、この仕組みを automation、候補を proposal と呼ぶ。

## 定義

自動化は使い回さない短い整数の ID と、次の形の定義で決まる。定義は常に丸ごと置き換わる。

```
トリガー → 取得元（任意）→ 処理の段 0 個以上 → 出力先
（通知: 出力先と並ぶ設定）
```

- **名前**: 「出どころ: 何を取るか」の 1 行。取得元が無ければ、何をするかの 1 行（例: 日報の下書き）。規則はタスクのタイトルと同じ。
- **トリガー**: 裏の仕組みの「○分ごと」か cron 式（[background](background.md#予定と次の時刻)。Mac のタイムゾーンで数える）。「○分ごと」は過ぎていれば起きたときに 1 回回り、cron 式は過ぎた時刻を回さず次の時刻を待つ。新着の流れはどちらでも次の回が前回成功以降を取るので、過ぎた回が飛んでも項目は落ちない。
- **取得元**: やり方と性質を持つ。要るかは出力先が決める（タスク候補は必須、コマンドと報告は任意）。
  - やり方は、シェルのコマンド（`/bin/sh -c`・任意の作業ディレクトリ）か、軽い agent（CLI・モデル〔省略可〕・使ってよい MCP のツール 1 つ以上・依頼文）。コマンドは 1 項目 1 行の JSON を自分で出す。agent には Orbe が同じ出力の形を指示する。
  - 取得元の agent が使えるのは、名指しした MCP のツール（完全名 `mcp__<サーバー>__<ツール>`）だけ。組み込みのツール・サーバー単位（`mcp__<サーバー>`）・ワイルドカードは理由付きで断る——外から届いた文面を読む役に、文面に仕込まれた指示で書き込みをさせないため。この絞り込みは、名指ししたツールが読み取りのツールであることが前提で、Orbe は名前の形しか確かめない。書き込みのツール（送信・更新・削除）や Orbe 自身のツールを名指しすれば絞り込みの外になるので、MCP・CLI の説明で AI に「出どころを読むツールだけを名指しする」と伝える。ただし取得元は利用者の MCP サーバーを名前で使うので利用者の claude の設定を読み、利用者が claude で常に許可したツールは Orbe からは締め出せない。
  - 性質は「**今の集合**」（取得結果がその時点の全体。例: 自分が担当の未完了課題）・「**新着の流れ**」（取得結果は新着だけ。例: 自分宛の新しい DM）・「**毎回全件**」（前回の取得結果との差分を掛けない）のどれか。枠の差分を掛けるかと、候補の下げ方がこれで決まる（→ [候補の保ち方](#候補の保ち方)）。出どころの種類を Orbe は知らないので、AI が選ぶ必須の項目。
- **処理の段**: 名前（1 行）と、コマンドか agent（CLI・モデル〔省略可〕・指示文）。段は JSON の行を受けて JSON の行を出し、状態を持たない。段の agent はツールを持たない閉じた形でだけ走る——外から届いた文面を読む役に、何かをさせる手段を渡さないため。段と出力先のコマンドは利用者のコマンドで、この閉じた形の外にある（→ [1 回の流れ](#1-回の流れ)）。
- **出力先**: 最後の段の出力の形と、届け方・確定のしかたを決める。
  - **タスク候補**: 取得元（今の集合か新着の流れ）と段 1 つ以上が要る。
  - **コマンド**: シェルのコマンド（`/bin/sh -c`・任意の作業ディレクトリ）と上限（`timeoutMinutes`。1〜60 分、省略は 2 分）。取得元も段も任意で、取得の性質は 3 種とも受ける。上限は経過時間と出力の無い時間の両方に当て、出力量と標準エラーの上限は裏のコマンドの既定のまま。標準出力は読まない（標準出力が 1 MiB・標準エラーが 64 KiB を超えれば打ち切られて回が失敗する。MCP・CLI の説明で AI に、多く出すものは `/dev/null` へ向けるよう伝える）。
  - **報告**: 定義に何も足さない。段が 1 つ以上要る（文章を書くのは最後の段の役）。取得元は任意で、取得の性質は 3 種とも受ける。
- **通知**: 出した回・失敗した回を知らせる先。メニューバー（`menuBar`）か通知センター（`notificationCenter`）の 1 つで、省略すると知らせない。どの出力先にも付くので、出力先の中身ではなく定義に置き、何をするかには入らない（→ [回の知らせ](#回の知らせ)）。

モデルを省略すると、最後の段は sonnet、それ以外の段と取得元は haiku で走る。保存は省略のまま持ち、走らせるとき・画面に出すとき・書き換えの比較で同じ規則で解く——段の並びを変えたら既定も追従するため。

agent は裏で回せる CLI だけを受ける（claude。codex・agy は理由付きで拒否する → [background](background.md#非対話の-agent)）。

取得の出力 1 行が 1 項目で、`id`（その出どころの中で変わらない ID）・`link`（http か https の URL）・`body`（本文）・`time`（ISO 8601）を持つ。この形はどの取得元でも同じ。`id` は自動化の中での同一性で、段を通しても項目をたどる鍵になり、同じリンクに新しい動きがあったときに判定へ回し直すためにも使う。`link` は自動化をまたぐ同一性。

止めることができ、止めるのは予定だけ。止めた自動化も「今すぐ」は受ける——有効にする前に試し打ちできるように。

## 1 回の流れ

1 回は次の流れで、全体が番人の 1 回になる。1 回が終わるまで同じ自動化の次の回は始まらず、走っている間の「今すぐ」は断る。状態を読み書きするのは Orbe の枠と出力先だけで、段は状態を持たない。回の始まりは Orbe が回を始めた時刻、終わりは確定か失敗の時刻（走らせたものの時刻ではない）。取得元も段も無い回でも始まりが決まり、番人は次の予定まで待つ。

1. **取得元**を走らせる。取得元が無ければ 2・3 を飛ばし、行の無いまま 4 へ進む。
2. **枠の差分**: 取れた項目のうち、この自動化の前回の取得結果に `id` が無いもの。全件見直しの回と毎回全件の取得元では掛けない。
3. **出力先の取り込み**: 差分の後の項目に、出力先が自分の条件を掛ける。タスク候補の条件は、同じリンクの候補が（どの状態でも、どの自動化のものでも）無いことと、同じ回に同じリンクが複数あれば最初の 1 件だけ。ここまでで残った項目が**新しい項目**。
4. 取得元のある回で新しい項目が無ければ段を起こさず、出力先へも届けずに成功として確定する。それ以外は新しい項目を 1 行 1 項目の JSON にし、**段**を 1 つずつ回す。最初の段にはこの行を渡し（取得元が無ければ空の入力）、各段の出力のうち JSON オブジェクトとして読めた行をそのまま次の段へ渡す。中間の段が 1 行も残さなければ、そこで止めて成功として確定する。段が 0 個なら、この行がそのまま出力先へ向かう。
5. **出力先が確かめる**: 出力先へ向かう最後の入力（段があれば最後の段の入力、無ければ出力先が読む行）が決まったとき、出力先が行を確かめる。1 行以上あって全部が外されたら回の失敗にする（外すのはタスク候補だけ → [項目の同一性](#項目の同一性)）。
6. **出力先が読む・届ける**: 最後の段の出力（段が無ければ 5 を経た行）を出力先が読み、届ける。届けは時間がかかってよく、失敗しうる（タスク候補はすぐ終わる）。何を受けるか・いつ走るか・どの出力を失敗とみなすかは出力先が決める（→ [出力先のコマンド](#出力先のコマンド)）。
7. **確定**する。その時点の状態に当て直し、前回の取得結果・全件見直しの印・前回成功の目印・出力先の状態（候補と下げ）・回の記録を 1 度に保存する。

段への渡し方は、コマンドの段には標準入力で、agent の段には Orbe の固定の枠の依頼文で渡す。中間の agent の段の枠は、役割・ツールが無いこと・今の日時とタイムゾーン・利用者の指示文・入力行（無ければ「(none)」）と、出力の決まり（1 行に 1 オブジェクト・渡す項目の `id` を保つ・残らなければ何も出さない）を載せる。最後の段の依頼文は出力先が組み、最後の段の出力をどう読むかも出力先が決める（タスク候補 → [判定の入出力](#判定の入出力)。コマンドは中間の段と同じ枠で、JSON の行として読む。報告 → [出力先の報告](#出力先の報告)）。

段と出力先のコマンドが受ける行は、外から届いた文面か、それをもとに段が作ったもので、文面に仕込まれた指示で作り変えられることがある。Orbe は行の中身を確かめない。そのため MCP・CLI の説明で AI に、コマンドは行の値をシェルとして評価せず、agent（`claude -p` など）にも渡さず、agent に読ませたいなら段に置く（段の agent は Orbe がツールを持たない形で走らせる）と、段と出力先のコマンドの両方が読む位置に一度だけ伝える。

### 出力先のコマンド

コマンドは、出力先に届いた行を 1 行 1 オブジェクトで標準入力に受け、[回の ID](#回の-id) を環境変数 `ORBE_RUN_ID` で受ける。段が 0 個なら、届く行は取得元の項目の形。

| 状況 | 動き |
|---|---|
| 最後の段が行を出したのに、JSON オブジェクトとして読める行が 1 つも無い | 回の失敗（`every line of the output of the last step was malformed`）。中間の段の「全部が形違いなら失敗」と同じ規則——コマンドにとって最後の段は実質的に中間の段だから |
| 届いた行が 1 行以上 | 走らせる |
| 取得元も段も無い | トリガーのたびに空の標準入力で走らせる |
| 取得元か段があり、届いた行が 0（新着の無い回・段で全部落ちた回） | 走らせずに成功 |
| 0 以外で終わった・上限で打ち切られた・始められなかった | 回の失敗。理由は `the sink command ended: <終わり方>: <標準エラーの抜粋>`。出力先の記録を持つ（出力先で落ちた回） |

失敗した回の項目は、次の回にもう一度流れる。その回には新しい項目も混ざるので、二重実行は回の ID ではなく行に残る項目の `id` で防ぐ——段が `id` を保つ必要があり、MCP・CLI の説明で AI に伝える。

### 出力先の報告

報告は、最後の段の出力を JSON の行として読まず、文章のまま受ける。届けはすぐ終わり、状態も持たない。

- 最後の段が agent なら、依頼文の枠に役割（人に読ませる短い報告を書く）・今の日時とタイムゾーン・利用者の指示文・入力行と、出力の決まり（地の文だけでコードフェンスを使わない・指示文の言語で書く・1 行目はボードの見出しと通知に出る要約・全体は短く 2,000 字以内・言うことが無ければ何も出さない）を載せる。最後の段がコマンドなら、標準出力がそのまま報告になる（JSON を出す決まりを負わない）。
- 前後の空白を除き、2,000 字を超えれば 2,000 字で切って「…」を付ける（回の記録は 20 回残るため）。最後の段の記録の数は、報告があれば 1、無ければ 0。

| 状況 | 出力先の記録 | ボードの区分 |
|---|---|---|
| 最後の段が文章を出した | 報告の文 | 出した |
| 最後の段が何も出さない（空白だけ） | 文の無い報告（「報告なし」の成功） | 何も出さなかった |
| 新着なし・途中の段が 0 行 | なし | 何も出さなかった |
| 段の失敗 | なし | 失敗 |

最後の段の出力を読んだ回はいつも報告の記録を持つので、記録だけで「報告なし」と「途中ですべて除外」を言い分けられる——今の定義（段の数・出力先）を見ずに読めるので、書き換えた後も過去の回を読み違えない。

確定はその時点の状態への当て直しで、回の途中に起きたこと（他の自動化の確定・人のさばき）を上書きしない。同じリンクを 2 つの自動化が同時に判定していたら、後から確定した側の候補は理由付きで捨てる。判定が「対応済み」とした候補も、その時点でまだ人の判断待ちのものだけを対応済みにする。

途中では何も保存しない。Orbe が回の途中で終わったら最後に回った時刻は進んでいないので、次の起動で過ぎた回として 1 回だけやり直す。

## 項目の同一性

項目は取得元の行の `id` でたどる。Orbe は段の間で行に印を付けない——コマンドの段（jq など）では保てず、段に状態を持たせないため。代わりに、タスク候補の出力先が今回の新しい項目の `id` に当て直して確かめる。この確かめはタスク候補の規則で、コマンドの出力先は行をそのまま受ける（段で `id` を落としても回は成功し、項目は「見たもの」になる）。

- 最後の段に渡す行のうち、`id` が今回の新しい項目のものでない行は、理由付きで捨てる。1 行以上あって全部が捨てられたら、回の失敗にする。
- 最後の段の候補（`propose`）の `id` も、今回の新しい項目のものだけを受ける。
- 候補のリンクと本文は、いつも取得元の項目から取る。段が作った文やリンクを候補に入れないため。

段の途中で `id` が落ちた回を成功と読むと、項目が「見たもの」になって二度と流れない。そのため失敗にして、前回の取得結果を進めない。

## 回の ID

回を始めるとき、自動化 ID と数え始め（最後に回った時刻か、作った時刻）から作る中身に意味の無い文字列（例 `3-1728810000000`）。新しい状態は持たず、数え始めは保存の精度に通してから使う——再起動の後に読み直した値と同じ ID にするため。渡すのは出力先のコマンドだけで、回の記録には載せない。

数え始めが進むのは回が記録されたとき（成功でも失敗でも）だけなので、次の 3 つは同じ値になり、記録された回の次は新しい値になる。

- 確定前に Orbe が終わった回のやり直し（再起動をまたいでも）。
- 書き換え・削除で止めた後の回。
- 確定前に終わった後の「今すぐ」。

コマンドは ID を**終わりに**記録すれば、同じ回を二重に実行しない。始めに記録する作りだと、止めた回の後の回を飛ばしうる。

## 前回成功の目印

確定（成功）した回の開始時刻を、自動化ごとに覚える。最後に回った時刻（番人の数え始め。失敗した回でも進む）とは別物。

新着の流れの取得元にだけ、値があれば常に渡す（全件見直しの回や、書き換えた直後の回も）。渡し方は、agent の取得元なら依頼文に「この時刻以降を取る。前の分が混ざってもよい（Orbe が既に見たものを除く）」の 1 文を足し、コマンドの取得元なら環境変数 `ORBE_SINCE`（ISO 8601。UTC・ミリ秒・`Z`）を子の環境に置く。目印の無い回は文も変数も置かない。

- 開始時刻にするのは、回の途中に届いた項目を次の回で取りこぼさないため。重なった分は `id` の差分で消える。
- 遅れて見える出どころは、取得元の側で余白を取ればよい。余白の適量は出どころごとに違い、Orbe が 1 つの値に決められないため。取得元が毎回同じ余白を取れば、余白の分は必ず前回の取得結果に入っているので、二重にはならない。
- 書き換えた直後の回にも渡すので、見直されるのは前回成功以降に届いた分だけ。外すと、さばいて既に忘れた候補が取得に戻り、二重に出る。
- 失敗した回では進まない。

## 候補の保ち方

**候補はリンク単位で、すべての自動化を通じて 1 つ**。状態は「人の判断待ち」「タスクにした」「捨てた」「判定が対応済みとした」の 4 つ。

候補は判定が決めた**付け先の workspace** を持てる（任意）。持つのは起動をまたいで変わらない内部の ID で、[タスクの workspace](tasks.md) の参照と同じ値・同じ規則——解けない参照（その workspace が消えた）は「無い」と同じに扱う。付け先は候補をタスクにしたときの行き先を決めるだけで、候補の同一性・下げ・棚には関わらない。

候補が忘れられるのは、**どの自動化もその候補を持たなくなったとき**だけで、そのとき人の判断待ちだったものは「下げた」として回の記録に数える。候補を持てるのは出力先がタスク候補の自動化だけで、持つのは、前回の取得結果にそのリンクがあるとき、または新着の流れの自動化が自分で出してまだ人の判断待ちのとき。別の出力先の自動化が同じリンクを取っても、候補を抱え込まない。

- **今の集合**: 取得から消えたリンクは、その時点の全体から外れた（課題が閉じた・自分の担当でなくなった）ので、持たなくなる。人の判断待ちなら Orbe が下げる。
- **新着の流れ**: 元の項目が次の回に取れないのは対応済みの意味ではないので、人の判断待ちのうちは取得から消えても持ち続け、判定に見せ続ける。判定が対応済みとした・人がさばいた後は、取得に無ければ忘れる。

タスクにした・捨てた・対応済みの候補も、忘れるまでは覚えていて同じリンクを再び候補にしない。消えた後で同じリンクが再び現れれば、もう一度判定に回る。止めた自動化も持つ——止めただけで候補は消えない。自動化を消すと、その自動化だけが持っていた候補は忘れる。

覚え続けるのは前回の取得結果だけ。新しい項目・候補の下げ・重なり・棚の持ち主がすべて同じ集合で言えるので、取得済みを際限なく溜めない。

## 棚と重なり

候補を見せる場所は自動化ごとの棚で、**棚に出す自動化**は読むときに決める——候補を出した自動化がまだ候補を持っていればそれ、いなければ持っている自動化のうち ID が最小のもの。保存しないのは、持ち主の取得結果からリンクが消えて別の自動化だけが取るようになったときに、保存した持ち主がずれるため。

出力先がタスク候補の自動化には「同じ出力先の他の自動化と前回の取得結果のリンクが何件重なっているか」が相手ごとに出る。保存せず前回の取得結果から導く。2 つの自動化が同じものを取っているとき、候補は 1 つで済むが、範囲を切り直す手がかりになる。

## 失敗した回

失敗した回は、回の記録と「最後に回った時刻」だけを進め、前回の取得結果も候補も前回成功の目印も動かさない——失敗を「0 件取れた」と読み違えて候補を一斉に下げないため。代わりに、壊れたままの自動化は回るたびに失敗を記録し続け、AI が記録の理由を読んで直す。

取得元の失敗は次のいずれか。

- コマンドの終了コードが 0 でない、出力が UTF-8 でない。
- agent が最終応答を返さずに終わった・失敗を報告した。指定した MCP のツールが始まりの時点で揃わなかった（モデルを呼ぶ前に止まる → [background](background.md#非対話の-agent)）。
- 出力に `{"error": "…"}` の行（`id` を持たず文字列の `error` を持つ）がある。コマンドでも同じ。
- 1 行以上あって全部が形違い。

段の失敗は次のいずれか。段が失敗した回も前回の取得結果を進めないので、同じ項目は次の回でまた段に回る。

- コマンドの終了コードが 0 でない、出力が UTF-8 でない。
- agent が最終応答を返さずに終わった・失敗を報告した。
- 中間の段の出力が 1 行以上あって、全部が JSON オブジェクトでない。
- 最後の段に渡す行が 1 行以上あって、`id` が今回の新しい項目のものが 1 つも無い（→ [項目の同一性](#項目の同一性)）。

出力先がタスク候補なら、最後の段の形の違う行は、捨てて理由を残すだけで失敗にしない。最後の段が文章だけを返した回は「候補なし」で確定する。出力先がコマンドなら、最後の段の出力が全行とも形違いの回と、コマンドが 0 以外で終わった・上限で打ち切られた回が失敗（→ [出力先のコマンド](#出力先のコマンド)）。報告なら、最後の段の出力はどんな文章でも報告になり、形の違いで失敗しない。失敗した回のうち出力先の記録を持つのは出力先で落ちた回だけ（コマンドが 0 以外で終わった・上限で打ち切られた・始められなかった回）で、記録の有無で段で落ちた回と見分ける。標準エラーの抜粋は失敗の理由に入る。

取得元がツールを使えたうえでツールの結果がエラーになり、`{"error":…}` を出さずに空を返した場合は「0 件」と区別できず、候補が下がりうる。

## 判定の入出力

タスク候補の出力先が、最後の段に渡すものと受けるもの。最後の段が agent なら、出力先が Orbe の固定の枠で依頼文を組む。役割・今日の日付と時刻とタイムゾーン（期限を決めるため）・利用者の指示文・新しい項目（確かめた入力行）・人の判断待ちの候補（リンク・タイトル・期限）・付け先にできる workspace の一覧・出力の形を載せる。載せる候補は最後の段を始める時点で取り、この回の取得結果にあるものと、新着の流れならこの自動化が出して判断待ちのままのもの——新着の流れでは、対応済みの知らせが元の項目とは別の新しい項目として届くため。workspace の一覧は Home を除く今の workspace（サイドバーの順）で、1 つずつ起動ごとの ID・名前・root を載せる。無ければ「(none)」と載せ、付け先を書けないことが分かるようにする。最後の段がコマンドなら、入力行を標準入力で渡すだけで、判断待ちの候補も workspace の一覧も渡らない（`resolve` は出せない。付け先は `orb ws list --json` の ID を走るたびに引けば書ける——ID は起動ごとに変わるので、コマンドに書き込めない。そこに載る Home の ID は付け先なしとして受ける）。

判断待ちの候補と workspace の一覧は、1 回の中で最後の段を始める時点に 1 度だけ取り、依頼文と出力の読み取りに同じものを使う——回の途中に候補がさばかれたり、workspace が増えたり消えたり改名されたりしても、判定が見たものと照らし合わせるものが食い違わない。起動ごとの ID はその回の中でしか使わず、保存しない。

出力は 1 行 1 つの JSON で、2 種類だけを受ける。

- `{"propose": "<項目の id>", "title": "…", "due": "YYYY-MM-DD", "workspace": <workspace の ID>}` … 今回の新しい項目への候補。1 項目に 1 つ。タイトルはタスクのタイトルの規則、期限は暦にある日付（省略可）。`workspace` は付け先で、一覧にある起動ごとの ID（省略可）。Orbe はこれを内部の ID に直して候補に覚える。Home の ID か省略なら付け先なし（Home に付く）。
- `{"resolve": "<リンク>"}` … 今回渡した人の判断待ちの候補を対応済みにする。

それ以外の行——JSON オブジェクトでない（段の記録に数える）・形が違う（`workspace` が整数でないものを含む）・知らない項目や候補を指す・タイトルや期限が不正・一覧にも Home にも無い workspace を指す・同じ項目への 2 つ目の候補——は捨て、理由を回の記録に残す。捨てた行の項目は候補にならず、「見たもの」になる。形を利用者の指示文に任せないのは、自動化ごとに形が割れて検証できなくなるため。

付け先は判定が項目ごとに決める。依頼文は「項目が一覧のどれかにはっきり属するとき（利用者の指示か、リポジトリなど項目そのものから分かるとき）だけ書き、迷えば省く。省けば Home に付く」と指示する。「いつも X に付ける」は指示文に書けば判定が従う。定義に既定の付け先を持たせないのは、定義の保存の形と外の形を同じに保つため——内部の ID は外に出せず、起動ごとの ID は保存できず、名前や root は改名・移動で黙って外れる。1 つの自動化が複数のリポジトリにまたがる項目を出すこともある。Orbe がリンクから付け先を推さないのは、出どころの種類を知らないため。付け先は判定の LLM の解釈に頼るので、外の文面に仕込まれた指示で変わりうるが、効き目は人の持つ workspace のどれに付くかに限られ、何も実行されない。人は ↵ の前に詳細で付け先を見る。

取得元の agent にも固定の枠を当てる——渡したツールだけで依頼文どおりに取り、1 項目 1 行の JSON だけを出し、ツールが失敗・使えないときは `{"error":…}` の 1 行だけを出す。

初回や書き換え直後は取れた全件が段に載るので、依頼文が大きくなる。裏の 1 回の上限（最終応答の大きさ・経過時間）を超えれば段の失敗として記録され、次の回でまた全件を段に回す。

## 回の記録

各回について、始まりと終わり・きっかけ（予定か今すぐ）・取得元・新しい項目の数・各段・最後の段の数を出力先が数えたか・出力先の記録・失敗ならその理由を、新しい順に 20 件まで残す。失敗した回は、届いたところまでを持つ。AI は記録を読んで、取得の範囲や指示文を直す。

- 取得元と段の記録は揃った形で、実行したコマンド行・終わり方・数・捨てた行の数と最初の数件の理由を持つ。数は、取得元なら項目として読めた数、段なら JSON の行として読めた数で、最後の段は出力先が数える（報告は報告があれば 1、無ければ 0）。段は名前も持つ。
- 記録の最後の段の数を出力先が数えたかを持つ。数えるのは出力先が最後の段の出力を読めた回だけで、途中の段が 0 行を出して止めた回・段で落ちた回は数えていない——記録の最後の段が定義の最後の段とは限らないため。
- 出力先の記録は、確定した回のうち出力先が記録を返した回と、出力先で落ちた回が持つ。失敗した回では、出力先の記録があることが出力先で落ちた印になる。
  - タスク候補は段を起こさなかった回も下げた数があるので必ず持ち、受けた候補の数・対応済みにした数・下げた数・捨てた行（`propose`・`resolve` として読めなかった行と、確かめ・確定で捨てた行）。
  - コマンドは走らせた回だけ（落ちた回も）が持ち、コマンド行・終わり方・標準入力に渡した行の数。
  - 報告は最後の段の出力を読んだ回だけが持ち、報告の文（言うことが無かった回は無い）。

## 回の知らせ

走らせ役は回を記録するたびに（成功でも失敗でも）自動化の ID だけを窓へ知らせ、窓がその時点の定義と最新の回から知らせるかを決める——回の途中で通知の設定を書き換えても、記録した時点の設定が効く。止めた回（書き換え・削除）は記録しないので知らせない。

| 通知 | 最新の回の区分 | その行を見ている | 結果 |
|---|---|---|---|
| 無し | どれでも | どちらでも | 知らせない |
| 有り | 何も出さなかった | どちらでも | 知らせない |
| 有り | 出した | いいえ | 通知先の面（ピルなら強調色の点）と完了の音 |
| 有り | 失敗（前の回は失敗でない・最初の回） | いいえ | 通知先の面（ピルなら赤の点）と人の操作を待つ音 |
| 有り | 失敗（前の回も失敗） | どちらでも | 知らせない |
| 有り | 出した・失敗 | はい | 知らせない |

- 区分（出した・何も出さなかった・失敗）と本文は[ボード](../chrome/board.md)の読み替えから取る。本文は実行履歴の最新の行の 1 行目（「2件を追加」「完了」「失敗：…」、報告なら 1 行目）。ピルが指す先はボードの行なので、行とピルを同じ文で語る。
- 何も出さなかった回（新着なし・すべて除外・報告なし）は知らせない。10 分ごとの自動化でも、何も無い回にピルは出ない。
- 失敗は続く間の最初の回だけ知らせ、出した回か何も出さなかった回を挟んで再び失敗したらまた知らせる。認証切れのように直るまで失敗し続ける自動化が回ごとに鳴ると、ピルと音を見なくなるため。続く失敗はボードの失敗の色で見える。
- 見ているとは、窓がキーで、パレットが無く、前面の workspace が Home でボードを選び、ボードの自動化の一覧でその自動化の行を選んでいること（行が見えているだけでは入れない）。
- 長さ・音の設定は Home の workspace の実効設定を読む（押した先が Home なので、発信元の workspace の値という読み方に揃う）。
- ピルの姿・押した先は [menubar](../chrome/menubar.md)、音は [sound](../agent/sound.md)。知らせたかどうかは回の記録に残さない（窓の状態にも依り、回の事実ではないため）。

### 通知センター

通知先が通知センターの知らせは、知らせるかの判断（上の表）をメニューバーと共有し、出す面だけが違う。

| その時点の OS の許可 | 面 | 許可を求めるか |
|---|---|---|
| 許可済み・仮の許可 | 通知センター（出せなかったらピル） | — |
| 未確認 | ピル | 求める（答えは待たない） |
| 拒否・通知センターを使えない起動 | ピル | — |

- 許可は覚えず、知らせるたびに OS に問う。背面の間にシステム設定で切られても、次の回から効く。許可の状態は画面に出さない（ピルに出たことで分かる）。
- 未確認の回はピルに出し、答えを待たない。問いは通知の形で出て放っておかれることがあり、待つとその間の知らせがどこにも届かず、後から古い結果が出るため。通知センターに出るのは許可した後の回から。
- 許可を求めるのは、知らせる直前（許可が無いとき）と、制御 API で定義を通知センターに書き換えた直後の 2 つ。どちらも未確認のときだけ OS が問う——人が AI に頼んだその場で問いが出る。
- 通知の題は自動化の名前、本文は結果の 1 行（ピルと同じ文）。通知そのものは無音で、音は Orbe の通知音（[sound](../agent/sound.md)）だけが鳴る。音の設定は Orbe の設定だけで決まる。
- 通知は自動化ごとに 1 つ（識別子 `automation.<id>`）。新しい回が前の通知を差し替え、通知センターに溜まらない。過去の回はボードの実行履歴で読む。自動化を消すと（制御 API・ボード・⌘⇧X のどこから消しても）、その通知を通知センターから取り下げる。通知先を替えても、出ている通知は取り下げない。
- Orbe が前面でもバナーを出す（見ている回はそもそも知らせないため）。
- 押すと Orbe を前面にして、ピルを押したときと同じく Home のボードでその自動化の行を選ぶ（[menubar](../chrome/menubar.md) の閉じ方と同じ行き先・同じ制限）。Orbe が止まっている間に押された通知も、起動して受け取る。
- 通知センターを使うのはアプリのバンドルとして動くときだけで、`swift run`・テストでは使えない起動として常にピルに出す。許可は bundle ID ごと（[channel](channel.md)）。

## 書き換えの扱い

- **何をするかの書き換え**（取得元のやり方・段の手段とモデル〔省略は解いた値で比べる〕と指示文かコマンド・出力先〔出力先のコマンドの上限は省略を 2 と解いて比べる〕）: 走っている回を止めてその結果を捨てる。何をするかが変わったので、走っている回は意味を失う。
- **書き換えの後の見直し**は出力先が決め、全件見直しの印は書き換えのたびに新しい出力先で決め直す。
  - タスク候補: 次の回は枠の差分を掛けずに見直す。既に候補のあるリンクは見直さない（二重には出ない）。
  - コマンド: 見直さない。既にコマンドに渡した項目は渡し直さない——見直すと、指示文を 1 文字直しただけで今の集合の全件がコマンドに渡り直し、副作用（投稿・送信など）が二重に起きる。タスク候補の見直しで立っていた印も、コマンドへ替えた時点で下ろす。諦めること: 段の絞り込みを緩めても、以前に落ちてまだ取得に残っている項目は流れ直さない。
  - 報告: 見直さない。報告は前回から何があったかを言う役で、見直すと指示文を直しただけで今の集合の全件が報告に載り直し、通知も出る。毎回全体をまとめたい報告は、取得の性質を毎回全件にすれば書ける。
- **名前・トリガー・取得の性質・段の名前・通知だけの書き換え・止める／再開**: 走っている回を止めず、予定だけを差し替える。段の名前を変えただけ、モデルを省略から同じ値の明示に変えただけで、全件見直しの費用を払わせないため。取得の性質を変えて誰も持たなくなった候補は、その場で忘れる（回の記録には数えない）。数え始め（最後に回った時刻）は動かないので、長く止めていた「○分ごと」の自動化を再開すると過ぎた回として 1 回すぐ回る——再開したらまず最新を取る。cron 式の自動化は止めていた間の時刻を回さず、次の時刻を待つ（どちらも [background](background.md#予定と次の時刻) の過ぎた回の規則と同じ）。
- **削除**: 走っている回を止め、結果は捨てる。

[採用・見送りの累計](#採用見送りの累計)は、どの書き換えでも 0 に戻らない。出力先をタスク候補でないものに書き換えると累計は消え、タスク候補に戻すと 0 から数え直す——累計は「この自動化の出す候補が役に立っているか」を読む数で、候補を出さない自動化にはその問いが無いため。自動化を消すと累計も消える。

## 候補をタスクにする

人の判断待ちの候補だけをさばける。

- **タスクにする**: 候補のタイトルと期限・未着手のタスクを、候補の付け先が今もあればその workspace に、無い（付け先を持たない・消えた）なら [Home](workspace.md#home) に付けて足し（並びは[タスク](tasks.md#一覧の並び)の規則）、詳細欄にリンクと取得した本文を入れる。付け先は項目を見た判定が決め、決まらなければリポジトリに属さない仕事の居場所の Home に付く——Home で動く claude がそこから始められる。付け先はさばく時点の workspace で解く——候補を出した後や画面を開いた後に付け先が消されても、行き場の無いタスクを作らない。本文は外の文面なので、agent への最初の入力には載らない——タスクを [`start_task`](../control/api.md) で始めても、最初の入力はタスクの ID・タイトルと頼み（`prompt`）だけで、詳細は agent が MCP で読む（ツール結果の席）。追加が拒否されたら候補は変わらない。
- **捨てる**。

さばいた候補は人の判断待ちから外れ、後から届いた判定でも上書きされない。人の判断待ちでない候補をさばこうとすると、値の不正とは別の失敗（判断待ちでない）として断る——判定の確定や下げと行き違っただけの操作を、画面が誤りとして出さないため。この 2 つは Orbe の画面（⌘⇧X の[提案タブ](../palette/automation.md)）の口で、AI には出さない。タスクにする操作はタスク一覧と自動化の 2 つのファイルへ書くので、間で落ちるとタスクができたのに候補が判断待ちのまま残りうる（累計は候補の状態と一緒に書くので、この 2 つは食い違わない）。

### 採用・見送りの累計

出力先がタスク候補の自動化は、人がその自動化の出した候補をタスクにした数（採用）と捨てた数（見送り）を持つ。自動化の出す候補が役に立っているかを読むための数で、さばくたびに 1 増え、減らない。候補は誰も持たなくなると忘れる（取得済みを際限なく溜めない）ので、候補から数え直さず、さばいたときに数えて持つ——候補を忘れても累計は減らない。

- 数えるのは候補を**出した**自動化。棚を移った候補を別の自動化の棚でさばいても、出した自動化に数える。
- 数えるのは人の判断だけ。判定が対応済みにした候補・Orbe が下げた候補は数えない。
- 出した自動化が消えた後、または出した自動化の出力先がタスク候補でなくなった後にさばいた候補は、どこにも数えない（さばくことはできる）。
- 追加が拒否された「タスクにする」は数えない。

## 保存

自動化の定義・出力先ごとに溜める状態（タスク候補なら採用・見送りの累計。コマンドと報告は持たず、キーも書かない）・前回の取得結果・全件見直しの印・最後に回った時刻・前回成功の目印・回の記録・候補を、state ディレクトリの `automations.json` 1 つに置き、変更のたびに即座に保存する。1 回の確定は 1 度の書き込み。出力先ごとに溜める状態は中身だけを書き、どの出力先の状態かは定義の出力先で決める（出力先と状態が食い違う保存は書けない）。書いていなければその出力先の初めの状態（累計なら 0）として読む。後から足すフィールドは欠落を許容し、在るのに使えない原本（読めない・構造破損・非互換 version・定義の不正・ID やリンクの重複）は [persistence](persistence.md) の規律で退避してから空で始める。

起動時にすべての自動化を番人へ載せる（止めた自動化は予定なしで）。数え始めは最後に回った時刻、まだ回っていなければ作った時刻。

## 操作の口

[制御 API](../control/api.md) の 6 動詞（`list_automations`・`set_automation`・`run_automation`・`pause_automation`・`delete_automation`・`list_automation_proposals`）を MCP にも出し、`orb automation`（[cli](../control/cli.md)）からも同じ形で叩ける。自動化も候補もイベントにはならない。

外の口は、定義と回の記録を保存と同じ形で読み書きする。定義は `definition` の欄に入れ子で置き、Orbe が持つ状態（止めているか・次の時刻・回の記録など）と同じ階層に混ぜない。AI は一覧の `definition` を取って直し、そのまま `set_automation` に送る。一覧は省略したモデルを省略のまま返す——解いた値で埋めて返すと、書き戻したときにモデルが固定され、段を並べ替えても既定が追従しなくなるため。外の形と保存の形が同じなので、保存の形を変えると外の形も変わる。出力先ごとの状態（タスク候補なら、棚の候補の数と重なり）は、その出力先の自動化にだけ付ける。

人の画面は 2 つ: ⌘⇧X の[提案タブ](../palette/automation.md)と、Home の[ボード](../chrome/board.md#自動化の部品)。どちらからも停止 ⇄ 再開・今すぐ実行・削除ができ、キー・キーの表示・断りは 1 つの定義を共有する。定義を足す・書き換えるのは AI の口だけ。どの口も同じ唯一の正を変えるので、片方の画面での操作はもう片方にすぐ映る。

人が自動化を作る・直すときの口は、Home のボード。[依頼の欄](../chrome/board.md#依頼の欄)に打った文は自動化の依頼として、一覧で選んで ⌘↵ を押すとその自動化の直しとして（[修正を依頼](../chrome/board.md#修正を依頼)）、Home に起きた claude のタブへ移り（[秘書](../agent/secretary.md)）、その claude が `set_automation` で書く。人は定義の項目を自分で埋めず、やりたいことを言うだけで済む。
