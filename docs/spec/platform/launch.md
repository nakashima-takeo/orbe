# 起動経路

Orbe を起こしてよい経路を 1 つに絞る関門。Finder / Dock / `open` — つまり macOS の LaunchServices を通った起動だけを通し、`.app` の実行体をシェルからコマンドとして直接叩かれた起動は、GUI を上げずにメッセージを出して終了する。

## なぜ関門が要るか

Orbe は 1 ウィンドウで複数 workspace を扱う設計で、複数ウィンドウを想定していない。普段それが保たれているのは Orbe 自身の働きではなく、**LaunchServices が「同じアプリはもう動いている」と気づいて既存を前面に出してくれている**からである。この面倒見は LaunchServices を通ったときにだけ働く。実行体のパスを直接 exec すると、カーネルから見えるのは 1 個のバイナリでしかなく、`.app` であることも同じものが動いていることも関知されない。2 つ目のプロセスがそのまま立ち上がる。

そして 2 つ目が立つと、[制御 API](../control/api.md) の socket を後発が奪い、先発インスタンスが制御チャネルから不達になる。画面に Orbe は見えているのに `orb` の全コマンドが「起動していない」と答える状態で、復旧は本体の再起動しかない。**ウィンドウが 1 枚増えるだけでは済まず、制御プレーンが落ちる。**

直接 exec は事故として実在する。ghostty の shell integration がバンドルの `Contents/MacOS` をペインの `PATH` へ載せ、macOS の既定ファイルシステムは大小文字を区別しないため、`orb` の打ち間違いである `orbe` が GUI 実行体そのものに解決する。制御 API はエージェントを第一級の利用者に据えており、`orb` を打たせる場面そのものが typo の発生源になる。

Orbe は CLI 引数を 1 つも解釈しない。埋め込んでいる libghostty は `--help` / `--version` を認識するが、それを実行する経路を Orbe は通していないため、**引数は認識されたうえで捨てられ、何を渡しても GUI が起動する**。`orbe --help` は使い方を出さず、出力ゼロのままウィンドウが増える。引数を付けても止まらないので、関門が無ければ typo を止める場所がどこにも無い。

## 判定

判定は**引数の有無ではなく起動経路**で行う。LaunchServices はアプリを起こすとき Info.plist の `LSEnvironment` を読んで環境変数を注入するが、直接 exec は Info.plist を一切見ない。この差がそのまま経路の判別になる。Orbe は `ORBE_LAUNCH_SOURCE` をこの印として使う。

引数で判定しないのは、LaunchServices や AppKit がアプリへ渡す引数（`-psn_` や `-NS` 系）を除外し続ける必要が出るうえ、**引数なしの `orbe` を取り逃す**ため。`orb` の typo は引数を伴わない形でも起きる。

| 起動 | 判定 |
|---|---|
| LaunchServices 経由（Finder / Dock / `open`） | 通す |
| `ORBE_STATE_DIR` あり（検証用の隔離インスタンス） | 通す |
| `.app` バンドルでない（`swift run` の開発起動） | 通す |
| 上記以外（`.app` をコマンドとして直接 exec） | **落とす** |

`ORBE_STATE_DIR` を通すのは、隔離インスタンスは直接 exec がその起こし方そのものだから（→ [persistence](persistence.md)）。空文字は未設定と同じ扱いで、関門は開かない。`.app` でない起動を通すのは、開発ビルドが LaunchServices を通りようがないため。

落とすときは stderr へ**次に打つべきコマンドを名指しして**非 0 で終える。黙って終了すると、制御 API が返す `Orbe not running` と同じく「Orbe が起動していないのでは」という、原因から最も遠い方向へ読み手を誘導する。この関門を踏むのは `orb` を打とうとして外した場合が主なので、`orb` の存在を示すことが復帰の最短路になる。

## 印をペインへ継承させない

起動経路の印は、**読んだ時点でプロセスの環境から落とす**。

ペインに渡る環境変数は spawn 時のプロセス環境そのものなので、印を残したまま先へ進めるとペインがそれを継承する。すると Orbe のペインの中で打った `orbe` が「LaunchServices 経由の正規起動」に見え、関門を素通りする。**関門が最も要る現場でだけ判定が反転する**という壊れ方で、Finder からの起動も外部ターミナルからの直接 exec も正しく動くため、通常の動作確認では露見しない。

この掃除は関門の付帯処理ではなく、関門が成立するための条件である。読み取りと掃除は 1 つの操作として扱い、読めば必ず消える形にしておく。

なお ghostty も同じ理由で、自身の起動経路の印を子プロセスの環境から落としている。ターミナルの中で自分の名前が打たれることへの備えという点で事情は共通で、通したい（ghostty には CLI がある）か落としたい（Orbe に CLI は無い）かだけが逆になる。

## 境界

関門が受け持つのは「コマンドとして叩かれた」経路だけで、二重起動そのものを禁じる仕組みではない。隔離インスタンスの中でさらに `orbe` を打つ場合や、`open -n` で明示的に 2 つ目を要求する場合は通る。複数インスタンスの共存自体は、state を分ければ成立する設計になっている（→ [persistence](persistence.md) / [channel](channel.md)）。
