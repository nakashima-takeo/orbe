# GitHub の読み書き

Orbe が GitHub に触る操作——[worktree パレット](../palette/worktree.md)の clean が読むブランチの PR、[タスク画面](../palette/tasks.md)の PR の自動の結び付け・結び付いた項目の値・GitHub タブ——と、PR の中身の読み取り・変更ファイルの確認済みの書き込み・PR のレビューのやりとりの読み取りと書き込み・ブランチが GitHub に在るかの問い合わせの口は、すべて gh CLI の子プロセスとして走る。どの面にも共通する規則——GitHub に届くかの判定、手元のブランチが GitHub のどのブランチか、失敗の分け方、ページの読み方——をここに置く。個々の面が「どう見せるか」は各面の spec が持つ。

gh は git と同じログインシェル由来の PATH で探し、子プロセスにも同じ PATH を渡す（[shell-path](shell-path.md)）。gh が見つかったことだけを覚え、見つからなかったことは覚えない——起動直後のまだ整っていない PATH で外した結果を覚えると、PATH が整った後も「gh が無い」のままになる。問い合わせと書き込みは github.com を名指しする。ただし、リポジトリを名指ししない 2 つの問い合わせ——⌘T の clean のブランチの PR と、GitHub タブの既定のリポジトリ——は、gh が作業ディレクトリの remote から選ぶリポジトリのホストへ送る（既定のリポジトリは、答えが GitHub のリポジトリでなければ「見つからない」にする）。1 回の呼び出しは、読みなら 15 秒、書き込みなら 60 秒で打ち切る（ネット待ちのハングを引きずらない）。書き込みを長く待つのは、打ち切った書き込みは GitHub に届いたかが分からなくなるため。件数の多い読みは、1 ページを 1 回の呼び出しにしてアプリがカーソルを持つ——gh にページ送りを任せると 1 回の呼び出しが全ページになり、打ち切りがページごとに効かなくなる。owner・リポジトリ名・カーソル・パスは文字列のまま渡し、整数として渡すのは番号と件数だけ（数字だけのリポジトリ名 `gabrielecirulli/2048` を整数に変えると、型が合わずに失敗し続ける）。

## 可否の事前判定

GitHub に問い合わせる前に、`notGitHub`（GitHub のリポジトリでない）／`ghMissing`（gh が無い）／`ghUnauthed`（gh に認証情報が無い）／`ready` に分ける。見るのはローカルの事実だけで、**ネットに触らない**——認証情報が手元に在るかを、トークンを GitHub で確かめずに読む（読むのは、問い合わせと書き込みが名指しする github.com の認証情報）。トークンを GitHub で確かめる形にすると、疎通できないだけのときを「未認証」と誤分類する。今 GitHub に届くかは事前判定の責務ではなく、届かなければそれぞれの問い合わせが失敗（下記）として返る。

## GitHub のリポジトリか

remote の URL のホストが github.com か ssh.github.com（443 番の SSH）か、SSH の書き方で `github.com-` で始まるか `.github.com` で終わるホスト別名（`git@github.com-work:o/r`・`git@work.github.com:o/r`。複数アカウントの ssh config の慣習）なら GitHub。`github.company.com` のような GitHub Enterprise は GitHub として扱わない——問い合わせは github.com へ送るので、別のホストの owner/name を github.com で読み書きしないため。可否の事前判定（origin で決める）・remote の台帳・GitHub タブの既定のリポジトリが、この 1 つの規則を読む。`owner/name` は URL のパスの最後の 2 段から読む。GitHub の名前は大小文字を区別しないので、比べるときは小文字に揃える。

## remote の台帳とブランチの同一性

**remote の台帳**は、remote ごとに GitHub のどのリポジトリかを持つ。使う側が remote の一覧（git）と正式名の答えから、そのつど導く。remote の名前と fetch の URL（`insteadOf` 展開後）は git の機械向けの出口（名前の一覧と remote ごとの URL）から読む——人が読む表示は行末に装飾が付く（部分クローンではフィルタ名）ので、部分クローンでも通常の clone と同じに読めるのは機械向けの出口だけ。1 本でも URL を読めなければ、一覧全体を読めなかったとする（欠けた一覧を「その remote は無い」と読ませない）。

URL から読んだ `owner/name` は、remote ごとに GitHub に問い合わせて正式名に揃える——GitHub は改名後も古い名前から新しい名前を返すので、origin の URL が改名前のままでも PR の head と同じリポジトリと分かる。正式名の問い合わせでは、問い合わせたリポジトリが fork なら親のリポジトリの正式名も一緒に得る（今のアカウントから見えない親は無いとして扱う）。問い合わせは 1 つずつ送る（1 つの「存在しない」で他の remote の答えまで失わないため）。答えはリポジトリ（`git-common-dir`）単位でプロセス内に持ち、正式名が答えられた名前は問い合わせ直さない。

**remote ごとの値は「正式名」「GitHub でない」「確かめられない」の 3 つ。** 確かめられないのは、GitHub が正式名を返さない（存在しない・今のアカウントから見えない private——GitHub は両者を区別せずに答える——・問い合わせの失敗）、GitHub の URL からリポジトリ名を読めない、remote の一覧を読めない、のとき。答えを一度も得ていない GitHub の remote がある間は、台帳は未確定。**「確かめられない」は「GitHub でない」と読まない**——台帳を使う側は 3 つを分けて扱う（clean がこれを取り違えると何が起きるかは [worktree パレット](../palette/worktree.md#データ供給プログレッシブ)）。

**ブランチの同一性**は、ローカルブランチが GitHub のどのリポジトリのどのブランチかを表し、push 先の remote のリポジトリとローカル名の組で決まる。PR の head は自分が push したブランチなので、git が push 先として解決する remote（`branch.<名前>.pushRemote` → `remote.pushDefault` → `branch.<名前>.remote`。解決順は git が持ち、Orbe は `for-each-ref` の push 先の remote 名を読む）がそのリポジトリになる——base（`origin/main`）を追跡して作った作業ブランチも、base から出た無関係な PR（main→release のリリース PR 等）と取り違えられない。ブランチ名がローカル名なのは、既定の `push.default=simple` で push されるのがローカル名だから。push 先が無いブランチとローカルブランチを追跡するブランチ（`.`）は origin とみなし、origin も無ければ「GitHub でない」。台帳に無い名前の push 先（URL を直接書いた remote・存在しない remote）は origin とみなさず「確かめられない」にする——git が origin 以外へ push すると言っているブランチを、origin の同名ブランチと取り違えないため。push 先とみなす remote（origin）は、⌘T が鮮度を信頼する remote（同じく origin。[worktree パレット](../palette/worktree.md#消してコミットが世界に残るかの判定)）とは別の定義として持つ——前者は同一性の関心、後者は鮮度の関心で、片方を変えてももう片方は変わらない。

## ブランチの PR

ブランチの PR は、ブランチ名を `--head` で名指しして `--state all` で 1 往復に open / closed の両方を取る。直近 N 件の一覧の窓は使わない——古くにマージされた PR も古くから開いたままの PR も、窓から溢れると取りこぼす。1 往復では gh の上限まで（作成日時の新しい順に 100 件）取る——往復の手間は件数に依らないので絞る動機が無く、絞ると `--head` に混ざる他人の fork の同名ブランチの PR で埋まって自分の PR が窓から落ちうる。`--head` は remote 側でブランチが消えていても PR を返す。

`--head` はブランチ名でしか絞れないので、**head がブランチの同一性と等しい PR だけ**をそのブランチの PR とする（他人の fork の同名ブランチの PR を入れない）。head のリポジトリは owner と名前から組む——古い版の gh は `nameWithOwner` を返さないが、それでも同じ head になる。

答えはブランチ単位で返り、失敗もそのブランチに閉じる——1 本の失敗で全体を捨てると、取れたブランチの事実まで一緒に消える。複数のブランチは固定本数（4 本）のレーンへ静的に配って並列に送る（直列だとブランチの数だけ往復が積み上がり、並列の数を抑えないと GitHub の secondary rate limit に触れる）。⌘T の clean が取れたブランチの PR は、リポジトリ単位でプロセス内に持つ（⌘T の clean が、次に開いたときに先に判定する材料と、取得に失敗したときの前回結果に使う）。この後の「リポジトリとブランチ名からブランチの PR を引く段」は、問い合わせ先が違う（push 先と親）ので、このキャッシュに書かない。

**リポジトリとブランチ名からブランチの PR を引く段**を、⌘⇧X の PR の自動の結び付けと、エディターの worktree の今の PR（→ [pull-request](../editor/pull-request.md)）が通る。エディターが引くのは、エディターの面が見えている間の、PR を引き直すきっかけ（見ている者が現れた・ブランチ名の変化・ネット操作の終わり・追跡 ref の値の変化・Orbe が前面に戻った・再読込）のときで、時機の規則は [pull-request](../editor/pull-request.md#見ている者と読み直すきっかけ) が持つ。答えは、リポジトリ単位で台帳（可否が `ready` でなければ求めない）、ブランチごとに次のどちらか。

- **引けない**: GitHub のどのブランチかが決まらない。理由は gh が無い・gh に認証情報が無い・GitHub でない・確かめられない。
- **GitHub のブランチと決まった**: 同一性と、「PR の一覧（作成日時の新しい順）か、問い合わせの失敗（失敗の種類つき）」。

PR を問い合わせるのは、同一性が GitHub のブランチと決まったものだけ。同一性が無いのに PR の一覧がある、という組は答えに現れない。

ブランチの PR を引く段は、PR を引くリポジトリを `-R` で名指しする。引くのは、同一性のリポジトリ（push 先）と、それが fork ならその親のリポジトリ——fork から親へ出した PR も、fork の中の PR も、そのブランチの PR になる。gh の既定（作業ディレクトリの remote から選ぶリポジトリ）に任せると、remote の名前の付け方で引ける PR が変わる。問い合わせはブランチごとに、fork でなければ 1 回、fork なら 2 回。どちらかの問い合わせが失敗すれば、そのブランチの答えは問い合わせの失敗（push 先の失敗を先に採る）——引けた側の PR だけを答えにすると、もう片方にある PR を「無い」と読ませる。2 つの答えは、head の照合の後で作成日時の新しい順にまとめる。

どの PR を選ぶかは使う側が決める。⌘T の clean はこの段を通らず、同じ規則（ブランチの同一性と head の照合）を自前の段取りで使う——ブランチごとの着地のたびに描き直し、前回の答えで先に描くため。⌘T の clean は PR を引くリポジトリを名指しせず、gh の既定に任せる（問い合わせはブランチごとに 1 回）。そのため、fork だけを remote に持つクローンでは、fork から親へ出した PR を見ない（限界）——親でマージされた PR からマージ済みを推し量れないので、その worktree は安全群の候補に出ない側に倒れる。親のリポジトリでレビュー中の PR を持つブランチの worktree が、ディレクトリを手で消された（prunable）行として安全群に入ることはあるが、prunable の行は登録を消すだけでブランチに触らない（→ [worktree](../palette/worktree.md)）ので、失うものは無い。また、親のリポジトリでレビュー中の PR を持つブランチでも、同じブランチから fork の中へ出してマージ済みの PR があると、⌘T の clean はマージ済みと推し量るので、その worktree は安全群に入り、clean でそのローカルブランチが消える（コミットは fork に残る。限界）。

ブランチの同一性からは、そのブランチから PR を作るページの URL `https://github.com/<owner>/<name>/pull/new/<ブランチ>` を組める（push の後に GitHub が案内するのと同じ URL）。PR を向ける先のリポジトリとブランチは、開いたページで GitHub が既定を選び、利用者がそこで変えられる。

## ブランチが GitHub に在るか

ブランチの同一性（リポジトリの正式名とブランチ名）のブランチが GitHub に在るかを、GraphQL でリポジトリの ref を名指しして 1 回問い合わせる。答えは「在る」「無い」「失敗」の 3 つ。リポジトリが今のアカウントから見えないときは、ブランチの有無を確かめられないので「無い」ではなく失敗にする。エディターの作成の入口が、PR の画面を出している間、材料が古いときだけ問い合わせる（→ [pull-request](../editor/pull-request.md#作成の入口の材料)）。

## 失敗の種類

gh の呼び出しが失敗したときは、失敗を次の 5 つに分ける。文言は持たない——種類を返し、文言への変換は面の側が持つ。

| 種類 | 読み方 |
|---|---|
| 未ログイン | gh の終了コードが「認証が要る」（4）か、エラー文が `gh auth login` への案内・HTTP 401 を言う |
| レート制限 | GraphQL のレスポンスの `errors` の種類が `RATE_LIMITED` か、エラー文が rate limit を言う（secondary rate limit を含む） |
| ネット不通 | エラー文が接続の失敗を言う（名前解決に失敗したときの `error connecting to`、接続できなかったときの `dial tcp` など） |
| タイムアウト | 1 回の呼び出しが上限を越えて打ち切られた |
| それ以外 | gh のエラー文の要点（`gh:`・`GraphQL:`・`HTTP ` で始まる行。無ければ最後の行）をそのまま持つ。エラー文が無い（レスポンスを読めない・gh が見つからない）なら空 |

gh も GitHub も「届かない」「認証が拒まれた」を機械向けの形で出さないので、エラー文の字面で読む。字面は gh の版で変わりうるが、当たらなければ「それ以外」としてエラー文の要点が残るので、分類が外れても理由は読める。

gh が 0 以外で終わっても、標準出力は捨てずに失敗の種類と一緒に返す——GraphQL の問い合わせが一部だけ失敗すると、gh は 0 以外で終わるが、通った分の `data` は標準出力に載る。

## PR の中身

PR 1 件の中身——ID・番号・題・URL・ドラフトか・状態・説明（書かれた Markdown のまま）・作者・両ブランチ名・両端のコミット（PR が比べる基準のベース側のコミットと PR の先頭のコミット。基準のベース側のコミットは、ベースブランチに push があっても追従せず（GitHub の振る舞いとして確かめていない。限界）、マージベースでもない）・コミットの総数・コミットの一覧（題の 1 行目つき）・変更ファイルの一覧（パス・変化の種類・確認済みか）——を、リポジトリ名と番号で GraphQL に問い合わせて読む。

- **変更ファイルは全件、コミットは新しい側から 250 件まで読む。** どちらも 100 件ずつのページで、最後のページまで読む。GitHub は PR のコミットを新しい側（PR の先頭を含む側）の 250 件までしか返さないので、それより多い PR では古い側が欠ける。欠けたことはコミットの総数と一覧の件数の差で分かる。
- **一時点のものとして揃える。** ページの間に push やベースブランチの付け替えが入ると、2 つの時点の一覧が混ざる。そこでどのページでも両端のコミットを一緒に読み、基準のベース側のコミットか PR の先頭のコミットが 1 ページ目と違えば最初から読み直す。読み直しは 1 回までで、なお違えば失敗にする。失敗の種類は「それ以外」で、要点は空（gh がエラーを出していないため）。
- **途中のページの失敗は全体の失敗。** 半分の一覧を返さない（欠けた一覧を全件と読ませない）。
- **確認済み**は GitHub の Files changed の Viewed。Viewed が付いたファイルだけを確認済みとする。付いていないファイルと、付けた後の push で外れたファイルは確認済みでない。
- **変化の種類**は GitHub の答え（追加・変更・削除・rename・コピー・種類の変更）をそのまま持つ。Orbe が知らない種類（GitHub が今後足すもの）は「変更」として読む（一覧ごと読めなくしない）。

## 確認済みの書き込み

変更ファイルの確認済みを、パスの集まりでまとめて付ける・外す。パスごとの書き込みを別名で並べて 1 回の問い合わせに入れ（パスは問い合わせの文に書かず、変数として渡す）、件数が多ければ 50 件ごとの回に分けて順に送る。一部だけ通ることがあるので、答えは「通ったパスの集まり」と「失敗の種類（通らなかったパスがあれば）」——呼び出し側は通らなかったパスだけを元に戻せる。通ったかはレスポンスの `data` にその別名の値が載ったかで読む。失敗した回より後の回は送らない。送らなかったパスも通らなかったパスに数える。

## レビューのやりとり

PR 1 件のレビューのやりとり——自分が PR の作者か・読んだ時点の PR の先頭のコミット・自分の未送信のレビュー（在るか、そのコメントの数）・行に付いたスレッドの一覧——を、リポジトリ名と番号で GraphQL に問い合わせて読む。GitHub は未送信のレビューを書いた本人にしか返さないので、読めるのは自分のもの（多くて 1 つ）だけとし、作者で絞らずに読む。

- **スレッド**は、GitHub の ID・パス・付いた行の範囲・解決済みか・自分が返信・解決・解決の取り消しをできるか・コメントの一覧（書いた人・本文・時刻・未送信か）を持つ。行の範囲は、終わりの行と側（古い側か新しい側か）と、複数行のコメントなら始まりの行と側で、行はその側の版の行（新しい側は PR の先頭のコミットの版、古い側はマージベースの版）。始まりの側が Orbe の知らない値なら、始まりを持たない（1 行のスレッドとして読む）。古い版に付いた（outdated の）スレッドと、ファイル単位のスレッドと、Orbe が知らない側（古い側・新しい側のどちらでもない）のスレッドは、行を持たない——outdated のスレッドは行の値が残っていても置かない（GitHub の diff でも古い版の行のスレッドとして扱われる）。知らない側のスレッドも、一覧ごと読めなくはしない。
- **スレッドは全件読み、1 スレッドのコメントは古い順に 100 件まで読む**（それより多いコメントは読まない。限界）。スレッドは 100 件ずつのページで最後のページまで読む。
- **一時点のものとして揃える。** どのページでも PR の先頭のコミットを一緒に読み、1 ページ目と違えば最初から読み直す。読み直しは 1 回までで、なお違えば失敗（「それ以外」で、要点は空）。途中のページの失敗は全体の失敗。

## レビューへの書き込み

レビューへの書き込みは、行への新しいスレッド・スレッドへの返信・解決と、その取り消し・レビューの送信（承認・コメント・変更を依頼）の 4 つ。解決とその取り消しと送信のほかは、自分の未送信のレビューに積む——送信するまで他の人に見えない。

- **本文は argv に載せない。** クエリと変数を 1 つの JSON にまとめて標準入力で渡す——本文がプロセスの一覧から見えず、値の型は JSON が持つので、値ごとに gh のフィールド指定の `-f`（文字列のまま）と `-F`（`@` で始まる値をファイルとして読み、`true`・`null`・数字を読み替える）を選び分けずに済む。本文に改行・引用符・`@`・先頭のハイフン・絵文字があっても、長くても、そのまま届く。渡さない値（空の全体へのコメント）は null にせず、変数と入力の欄ごと省く。
- **新しいスレッドの行**は、終わりの行と側を GitHub の行と側の欄に、複数行のコメント（範囲）なら始まりの行と側を始まりの行と側の欄に渡す。1 行のスレッドは始まりの欄を渡さない（変数も入力の欄も省く）。未送信のレビューの有無のどちらの書き込みでも同じ。
- **未送信のレビューは、在ればその ID を名指しする。** 無いときの新しいスレッドは、レビューの作成と最初のスレッドを 1 回の呼び出しで送り、レビューを、行を数えた diff の先頭のコミットに結ぶ（結ばないと、送った時点の PR の先頭のコミットの diff の行として読まれ、その間に push があると別の行に付く）——スレッドの追加がエラーになったとき（diff の外の行など）に、空の未送信のレビューを GitHub に残さない。未送信のレビューが在るときの新しいスレッドは、GitHub の入力にコミットの欄が無いので結ばない（行は GitHub が決めるコミットの diff の行として読まれる）。未送信のレビューを作るときは送信の種類を渡さない（渡すと、作った時点で送信になる）。無いときの返信は、レビューを、利用者が見ていたレビューのやりとりを読んだ時点の先頭のコミットに結んで作ってから返信する（Orbe が作る未送信のレビューは、どれも見ていた先頭に結ぶ。作成が通って返信がエラーになると、空の未送信のレビューが残る。次の書き込みがそれを使う）。無いときの送信は、作成と送信を 1 回で送り、レビューを、利用者が見ていたレビューのやりとりを読んだ時点の先頭のコミットに結ぶ——Orbe が新しい push を知らない間に送った承認・変更の依頼を、利用者の見ていないコミットに付けない（ずれを断るのは PR の状態の受け付け → [pull-request](../editor/pull-request.md#レビューのやりとり)）。未送信のレビューが在るときの送信は、入力にコミットの欄が無いので結ばない。
- **「解決して返信」は返信 → 解決の順**で、返信が通らなければ解決を送らない。
- **答え**は「書き込みの後の自分の未送信のレビュー（分かった限り）」と「失敗の種類（通らなかった呼び出しがあれば）」と「返信が通ったか（解決して返信で、解決だけが通らなかったときを見分ける）」。失敗した呼び出しより後の呼び出しは送らない。通ったかは、レスポンスの `data` に書き込みの値が載ったかで読む。GitHub がエラーを返した書き込みは、gh のエラー文の要点を持つ「それ以外」になる。タイムアウトした書き込みは、GitHub に届いたかが分からないまま失敗として返る（読み直せば、届いていたかが分かる → [PR の状態](../editor/pull-request.md#レビューのやりとり)）。ただし未送信のレビューが無いときの送信（コメントの無い承認・変更の依頼など）は、届いても読み直しに何も現れないので、タイムアウトすると届いたかが分からないまま残る（限界。読み直しは送ったレビューを読まない）。
