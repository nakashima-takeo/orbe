# GitHub の読み書き

Orbe が GitHub に触る操作——[worktree パレット](../palette/worktree.md)の clean が読むブランチの PR、[タスク画面](../palette/tasks.md)の PR の自動の結び付け・結び付いた項目の値・GitHub タブ、PR の中身と変更ファイルの確認済み——はすべて gh CLI の子プロセスとして走る。どの面にも共通する規則——GitHub に届くかの判定、手元のブランチが GitHub のどのブランチか、失敗の分け方、ページの読み方——をここに置く。個々の面が「どう見せるか」は各面の spec が持つ。

gh は git と同じログインシェル由来の PATH で探し、子プロセスにも同じ PATH を渡す（[shell-path](shell-path.md)）。gh が見つかったことだけを覚え、見つからなかったことは覚えない——起動直後のまだ整っていない PATH で外した結果を覚えると、PATH が整った後も「gh が無い」のままになる。問い合わせと書き込みはどれも github.com を名指しする。1 回の呼び出しは 15 秒で打ち切る（ネット待ちのハングを引きずらない）。件数の多い読みは、1 ページを 1 回の呼び出しにしてアプリがカーソルを持つ——gh にページ送りを任せると 1 回が全ページになり、上限がページごとに効かなくなる。owner・リポジトリ名・カーソル・パスは文字列のまま渡し、整数として渡すのは番号と件数だけ（数字だけのリポジトリ名 `gabrielecirulli/2048` を整数に変えると、型が合わずに失敗し続ける）。

## 可否の事前判定

GitHub に問い合わせる前に、`notGitHub`（GitHub のリポジトリでない）／`ghMissing`（gh が無い）／`ghUnauthed`（gh に認証情報が無い）／`ready` に分ける。見るのはローカルの事実だけで、**ネットに触らない**——認証情報が手元に在るかを、トークンを GitHub で確かめずに読む（github.com の認証を名指しする）。トークンを GitHub で確かめる形にすると、疎通できないだけのときを「未認証」と誤分類する。今 GitHub に届くかは事前判定の責務ではなく、届かなければそれぞれの問い合わせが失敗（下記）として返る。

## GitHub のリポジトリか

remote の URL のホストが github.com か ssh.github.com（443 番の SSH）か、SSH の書き方で `github.com-` で始まるか `.github.com` で終わるホスト別名（`git@github.com-work:o/r`・`git@work.github.com:o/r`。複数アカウントの ssh config の慣習）なら GitHub。`github.company.com` のような GitHub Enterprise は GitHub として扱わない——問い合わせは github.com へ送るので、別のホストの owner/name を github.com で読み書きしないため。可否の事前判定（origin で決める）・remote の台帳・GitHub タブの既定のリポジトリが、この 1 つの規則を読む。`owner/name` は URL のパスの最後の 2 段から読む。GitHub の名前は大小文字を区別しないので、比べるときは小文字に揃える。

## remote の台帳とブランチの同一性

**remote の台帳**は、remote ごとに GitHub のどのリポジトリかを持つ。使う側が remote の一覧（git）と正式名の答えから、そのつど導く。remote の名前と fetch の URL（`insteadOf` 展開後）は git の機械向けの出口（名前の一覧と remote ごとの URL）から読む——人が読む表示は行末に装飾が付く（部分クローンではフィルタ名）ので、部分クローンでも通常の clone と同じに読めるのは機械向けの出口だけ。1 本でも URL を読めなければ、一覧全体を読めなかったとする（欠けた一覧を「その remote は無い」と読ませない）。

URL から読んだ `owner/name` は、remote ごとに GitHub に問い合わせて正式名に揃える——GitHub は改名後も古い名前から新しい名前を返すので、origin の URL が改名前のままでも PR の head と同じリポジトリと分かる。問い合わせは 1 つずつ送る（1 つの「存在しない」で他の remote の答えまで失わないため）。答えはリポジトリ（`git-common-dir`）単位でプロセス内に持ち、正式名が答えられた名前は問い合わせ直さない。

**remote ごとの値は「正式名」「GitHub でない」「確かめられない」の 3 つ。** 確かめられないのは、GitHub が正式名を返さない（存在しない・今のアカウントから見えない private——GitHub は両者を区別せずに答える——・問い合わせの失敗）、GitHub の URL からリポジトリ名を読めない、remote の一覧を読めない、のとき。答えを一度も得ていない GitHub の remote がある間は、台帳は未確定。**「確かめられない」は「GitHub でない」と読まない**——読み手は 3 つを網羅して分ける（clean がこれを取り違えると何が起きるかは [worktree パレット](../palette/worktree.md#データ供給プログレッシブ)）。

**ブランチの同一性**は、ローカルブランチが GitHub のどのリポジトリのどのブランチかで、push 先の remote のリポジトリとローカル名の組で決まる。PR の head は自分が push したブランチなので、git が push 先として解決する remote（`branch.<名前>.pushRemote` → `remote.pushDefault` → `branch.<名前>.remote`。解決順は git が持ち、Orbe は `for-each-ref` の push 先の remote 名を読む）がそのリポジトリになる——base（`origin/main`）を追跡して作った作業ブランチも、base から出た無関係な PR（main→release のリリース PR 等）と取り違えられない。ブランチ名がローカル名なのは、既定の `push.default=simple` で push されるのがローカル名だから。push 先が無い行とローカルブランチを追跡する行（`.`）は origin とみなし、origin も無ければ「GitHub でない」。台帳に無い名前の push 先（URL を直接書いた remote・存在しない remote）は origin とみなさず「確かめられない」にする——git が origin 以外へ push すると言っている行を、origin の同名ブランチと取り違えないため。push 先とみなす remote（origin）は、fetch を信頼する remote の定義とは別に持つ——前者は同一性の関心、後者は鮮度の関心で、片方を変えてももう片方は変わらない。

## ブランチの PR

ブランチの PR は、ブランチ名を `--head` で名指しして `--state all` で 1 往復に open / closed の両方を取る。直近 N 件の一覧の窓は使わない——古くにマージされた PR も古くから開いたままの PR も、窓から溢れると取りこぼす。1 往復では gh の上限まで（作成日時の新しい順に 100 件）取る——往復の手間は件数に依らないので絞る動機が無く、絞ると `--head` に混ざる他人の fork の同名ブランチの PR で埋まって自分の PR が窓から落ちうる。`--head` は remote 側でブランチが消えていても PR を返す。

`--head` はブランチ名でしか絞れないので、**head がブランチの同一性と等しい PR だけ**をそのブランチの PR とする（他人の fork の同名ブランチの PR を入れない）。head のリポジトリは owner と名前から組む——古い版の gh は `nameWithOwner` を返さないが、それでも同じ head になる。

答えはブランチ単位で返り、失敗もそのブランチに閉じる——1 本の失敗で全体を捨てると、取れたブランチの事実まで一緒に消える。複数のブランチは固定本数（4 本）のレーンへ静的に配って並列に送る（直列だとブランチの本数ぶんの往復が積み上がり、本数を抑えないと GitHub の secondary rate limit に触れる）。取れたブランチの PR は、リポジトリ単位でプロセス内に持つ（⌘T の clean が、次に開いたときに先に判定する材料に使う）。

**リポジトリとブランチ名からブランチの PR を引く段**は 1 つで、⌘⇧X の PR の自動の結び付けと、今のブランチの PR を知りたい面が同じ段を通る。手順は、ローカルブランチ・origin が GitHub か・remote の一覧を並行して読む → 可否の事前判定 → 正式名 → 台帳 → ブランチの同一性 → 同一性が GitHub のブランチと決まったものだけ PR を問い合わせる → head の照合。答えは、リポジトリ単位で可否と台帳（可否が `ready` でなければ台帳は求めない）、ブランチごとに同一性と「PR の一覧（作成日時の新しい順）か、引けない理由」。理由は gh が無い・gh に認証情報が無い・GitHub でない・確かめられない・問い合わせの失敗（失敗の種類つき）。どの PR を選ぶかは使う側が決める。

ブランチから PR を作るページは `https://github.com/<owner>/<name>/pull/new/<ブランチ>`（同一性から組む。push の後に GitHub が案内するのと同じ URL）。PR を向ける先のリポジトリとブランチは、開いたページで GitHub が既定を選び、利用者がそこで変えられる。

## 失敗の種類

gh を呼んで GitHub がエラーを返した・届かなかったときは、失敗を次の 5 つに分ける。文言は持たない——種類を返し、文言への変換は面の側が持つ。

| 種類 | 読み方 |
|---|---|
| 未ログイン | gh の終了コードが「認証が要る」（4）か、エラー文が `gh auth login` への案内・HTTP 401 を言う |
| レート制限 | GraphQL のレスポンスの `errors` の種類が `RATE_LIMITED` か、エラー文が rate limit を言う（secondary rate limit を含む） |
| ネット不通 | エラー文が接続の失敗を言う（名前解決の失敗の `error connecting to`・`dial tcp` など） |
| タイムアウト | 1 回の呼び出しが上限を越えて打ち切った |
| それ以外 | gh のエラー文の要点（`gh:`・`GraphQL:`・`HTTP ` で始まる行。無ければ最後の行）をそのまま持つ。gh が何も言わなかった（レスポンスを読めない・gh が見つからない）なら空 |

gh も GitHub も「届かない」「認証が拒まれた」を機械向けの形で出さないので、エラー文の字面で読む。字面は gh の版で変わりうるが、当たらなければ「それ以外」としてエラー文がそのまま残るので、分類が外れても理由は読める。

gh の 1 回の結果は、終了コード・標準出力・分類した失敗の組で返り、成否は読む側が決める——GraphQL は一部だけ失敗すると、gh が 0 以外で終わっても通った分の `data` を標準出力に載せるので、成否を 1 つに潰すと通った分を読めない。

## PR の中身

PR 1 件の中身——ID・番号・題・URL・ドラフトか・状態・説明（書かれた Markdown のまま）・作者・両ブランチ名・両端のコミット（ベースブランチの先頭と PR の先頭。マージベースではない）・コミットの一覧（題の 1 行目つき）・変更ファイルの一覧（パス・変化の種類・確認済みか）——を、リポジトリ名と番号で GraphQL に問い合わせて読む。

- **全件を読む。** コミットと変更ファイルは 100 件ずつのページで、最後のページまで読む。
- **一時点のものとして揃える。** ページの間に push やベースブランチの付け替えが入ると、2 つの時点の一覧が混ざる。そこでどのページでも両端のコミットを一緒に読み、1 ページ目と違えば最初から読み直す。読み直しは 1 回までで、なお違えば失敗にする（gh は何も言っていないので、要点の空の「それ以外」）。
- **途中のページの失敗は全体の失敗。** 半分の一覧を返さない（「N/M 確認済み」の M が少なく出る）。
- **確認済み**は GitHub の Files changed の Viewed。「確認済み」だけを真にし、「未確認」と「確認済みだったが後の push で外れた」は偽。
- **変化の種類**は GitHub の答え（追加・変更・削除・rename・コピー・種類の変更）をそのまま持つ。GitHub が後から足した種類は「変更」として読む（一覧ごと読めなくしない）。

## 確認済みの書き込み

変更ファイルの確認済みを、パスの集まりでまとめて付ける・外す。パスごとの書き込みをエイリアスで並べて 1 回の問い合わせに入れ（パスは問い合わせの文に書かず、変数として渡す）、件数が多ければ 50 件ごとの回に分けて順に送る。一部だけ通ることがあるので、答えは「通ったパスの集まり」と「失敗の種類（通らなかったパスがあれば）」——呼び出し側は通らなかったパスだけを元に戻せる。通ったかはレスポンスの `data` にそのエイリアスの値が載ったかで読む。失敗した回より後の回は送らない（通らなかったパスに入る）。
