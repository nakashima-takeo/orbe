# 受信

Slack の自分宛のメッセージや GitHub のレビュー依頼のように、外から届くものを人が見張らなくても、[タスク](tasks.md)にすべきものが提案として手元に溜まるための仕組み。受信は「何を取るか」「どう判定するか」「いつ回すか」を持ち、Orbe が[裏で](background.md)予定どおり取得し、前の回に無かった項目だけを判定の agent に見せ、返ってきた提案を検証して覚える。受信を作り・直すのは AI（MCP・`orb intake`）で、提案をタスクにする・捨てるのは人の判断として Orbe の中に残す。

## 定義

受信は使い回さない短い整数の ID と、次の 4 つで決まる。4 つは常に揃って置き換わり、片方だけを書き換える形は無い。

- **名前**: 「出どころ: 何を取るか」の 1 行。規則はタスクのタイトルと同じ。
- **取得**: やり方と性質を持つ。
  - やり方は、シェルのコマンド（`/bin/sh -c`・任意の作業ディレクトリ）か、軽い agent（CLI・モデル・使ってよい MCP のツール 1 つ以上・依頼文）。コマンドは 1 項目 1 行の JSON を自分で出す。agent には Orbe が同じ出力の形を指示する。
  - 取得役の agent が使えるのは、名指しした MCP のツール（完全名 `mcp__<サーバー>__<ツール>`）だけ。組み込みのツール・サーバー単位（`mcp__<サーバー>`）・ワイルドカードは理由付きで断る——外から届いた文面を読む役に、文面に仕込まれた指示で書き込みをさせないため。ただし取得役は利用者の MCP サーバーを名前で使うので利用者の claude の設定を読み、利用者が claude で常に許可したツールは Orbe からは締め出せない。
  - 性質は「**今の集合**」（取得結果がその時点の全体。例: 自分が担当の未完了課題）か「**新着の流れ**」（取得結果は新着だけ。例: 自分宛の新しい DM）。提案の下げ方がこれで決まる（→ [提案の保ち方](#提案の保ち方)）。出どころの種類を Orbe は知らないので、AI が選ぶ必須の項目。
- **判定**: agent（CLI・モデル・指示文）。ツールを持たない閉じた形でだけ走る——外から届いた文面を読む役に、何かをさせる手段を渡さないため。指示文が決めるのは「どんな項目をタスクにするか・タイトルと期限の付け方」で、入出力の形は Orbe が決める。
- **いつ**: 裏の仕組みの「○分ごと」か「毎日の時刻」。

agent は裏で回せる CLI だけを受ける（claude。codex・agy は理由付きで拒否する → [background](background.md#非対話の-agent)）。

取得の出力 1 行が 1 項目で、`id`（その出どころの中で変わらない ID）・`link`（http か https の URL）・`body`（本文）・`time`（ISO 8601）を持つ。`id` は受信の中での同一性で、同じリンクに新しい動きがあったときに判定へ回し直すために使う。`link` は受信をまたぐ同一性。

止めることができ、止めるのは予定だけ。止めた受信も「今すぐ」は受ける——有効にする前に試し打ちできるように。

## 1 回の流れ

1 回は「取得 → 新しい項目の抽出 → 判定 → 確定」で、全体が番人の 1 回になる。1 回が終わるまで同じ受信の次の回は始まらず、走っている間の「今すぐ」は断る。

1. **取得**する。
2. 取れた項目から**新しい項目**を選ぶ。新しい項目とは、この受信の前回の取得結果に `id` が無く、かつ同じリンクの提案が（どの状態でも、どの受信のものでも）無いもの。同じ回に同じリンクが複数あれば最初の 1 件だけ。
3. 新しい項目が無ければ判定を起こさない。あれば**判定**の agent に新しい項目だけを見せる。
4. **確定**する。その時点の状態に当て直し、前回の取得結果・提案・下げ・回の記録を 1 度に保存する。

確定はその時点の状態への当て直しで、回の途中に起きたこと（他の受信の確定・人のさばき）を上書きしない。同じリンクを 2 つの受信が同時に判定していたら、後から確定した側の提案は理由付きで捨てる。判定が「対応済み」とした提案も、その時点でまだ人の判断待ちのものだけを対応済みにする。

途中では何も保存しない。Orbe が回の途中で終わったら最後に回った時刻は進んでいないので、次の起動で過ぎた回として 1 回だけやり直す。

## 提案の保ち方

**提案はリンク単位で、全受信を通じて 1 つ**。状態は「人の判断待ち」「タスクにした」「捨てた」「判定が対応済みとした」の 4 つ。

提案が忘れられるのは、**どの受信もその提案を持たなくなったとき**だけで、そのとき人の判断待ちだったものは「下げた」として回の記録に数える。受信が提案を持つのは、前回の取得結果にそのリンクがあるとき、または新着の流れの受信が自分で出してまだ人の判断待ちのとき。

- **今の集合**: 取得から消えたリンクは、その時点の全体から外れた（課題が閉じた・自分の担当でなくなった）ので、持たなくなる。人の判断待ちなら Orbe が下げる。
- **新着の流れ**: 元の項目が次の回に取れないのは対応済みの意味ではないので、人の判断待ちのうちは取得から消えても持ち続け、判定に見せ続ける。判定が対応済みとした・人がさばいた後は、取得に無ければ忘れる。

タスクにした・捨てた・対応済みの提案も、忘れるまでは覚えていて同じリンクを再び提案しない。消えた後で同じリンクが再び現れれば、もう一度判定に回る。止めた受信も持つ——止めただけで提案は消えない。受信を消すと、その受信だけが持っていた提案は忘れる。

覚え続けるのは前回の取得結果だけ。新しい項目・提案の下げ・重なり・棚の持ち主がすべて同じ集合で言えるので、取得済みを際限なく溜めない。

## 棚と重なり

提案を見せる場所は受信ごとの棚で、**棚に出す受信**は読むときに決める——提案した受信がまだ提案を持っていればそれ、いなければ持っている受信のうち ID が最小のもの。保存しないのは、持ち主の取得結果からリンクが消えて別の受信だけが取るようになったときに、保存した持ち主がずれるため。

受信には「他の受信と前回の取得結果のリンクが何件重なっているか」が相手ごとに出る。保存せず前回の取得結果から導く。2 つの受信が同じものを取っているとき、提案は 1 つで済むが、範囲を切り直す手がかりになる。

## 失敗した回

失敗した回は、回の記録と「最後に回った時刻」だけを進め、前回の取得結果も提案も動かさない——失敗を「0 件取れた」と読み違えて提案を一斉に下げないため。代わりに、壊れたままの受信は回るたびに失敗を記録し続け、AI が記録の理由を読んで直す。

取得の失敗は次のいずれか。

- コマンドの終了コードが 0 でない、出力が UTF-8 でない。
- agent が最終応答を返さずに終わった・失敗を報告した。指定した MCP のツールが始まりの時点で揃わなかった（モデルを呼ぶ前に止まる → [background](background.md#非対話の-agent)）。
- 出力に `{"error": "…"}` の行（`id` を持たず文字列の `error` を持つ）がある。コマンドでも同じ。
- 1 行以上あって全部が形違い。

判定の失敗は、agent が最終応答を返さずに終わった・失敗を報告したとき。判定が失敗した回も前回の取得結果を進めないので、同じ項目は次の回でまた判定に回る。形の違う行が混じるだけなら失敗ではなく、その行を捨てる。

取得役がツールを使えたうえでツールの結果がエラーになり、`{"error":…}` を出さずに空を返した場合は「0 件」と区別できず、提案が下がりうる。

## 判定の入出力

判定に渡す依頼文は Orbe の固定の枠で、役割・今日の日付と時刻とタイムゾーン（期限を決めるため）・利用者の指示文・新しい項目・人の判断待ちの提案（リンク・タイトル・期限）・出力の形を載せる。載せる提案は、この回の取得結果にあるものと、新着の流れならこの受信が出して判断待ちのままのもの——新着の流れでは、対応済みの知らせが元の項目とは別の新しい項目として届くため。

出力は 1 行 1 つの JSON で、2 種類だけを受ける。

- `{"propose": "<項目の id>", "title": "…", "due": "YYYY-MM-DD"}` … 今回渡した新しい項目への提案。1 項目に 1 つ。タイトルはタスクのタイトルの規則、期限は暦にある日付（省略可）。
- `{"resolve": "<リンク>"}` … 今回渡した人の判断待ちの提案を対応済みにする。

それ以外の行——形が違う・知らない項目や提案を指す・タイトルや期限が不正・同じ項目への 2 つ目の提案——は捨て、理由を回の記録に残す。形を利用者の指示文に任せないのは、受信ごとに形が割れて検証できなくなるため。

取得役の agent にも固定の枠を当てる——渡したツールだけで依頼文どおりに取り、1 項目 1 行の JSON だけを出し、ツールが失敗・使えないときは `{"error":…}` の 1 行だけを出す。

初回や書き換え直後は取れた全件が判定に載るので、依頼文が大きくなる。裏の 1 回の上限（最終応答の大きさ・経過時間）を超えれば判定の失敗として記録され、次の回でまた全件を判定する。

## 回の記録

各回について、始まりと終わり・きっかけ（予定か今すぐ）・取得（実行したコマンド行・終わり方・取れた数・捨てた行の数と最初の数件の理由）・新しい項目の数・判定（同じく。提案の数と対応済みの数。判定を起こさなかった回は無い）・下げた数・失敗ならその理由を、新しい順に 20 件まで残す。AI は記録を読んで、取得の範囲や指示文を直す。

## 書き換えの扱い

- **取得のやり方か判定の書き換え**: 走っている回を止めてその結果を捨て、次の回は取れた全件を新しい判定で見直す。既に提案のあるリンクは見直さない（二重には出ない）。何をするかが変わったので、走っている回は意味を失う。
- **名前・いつ・取得の性質だけの書き換え・止める／再開**: 走っている回を止めず、予定だけを差し替える。取得の性質を変えて誰も持たなくなった提案は、その場で忘れる（回の記録には数えない）。数え始め（最後に回った時刻）は動かないので、長く止めていた受信を再開すると過ぎた回として 1 回すぐ回る——再開したらまず最新を取る（[background](background.md#予定と次の時刻) の「過ぎた回は 1 回だけ」と同じ規則）。
- **削除**: 走っている回を止め、結果は捨てる。

## 提案をタスクにする

人の判断待ちの提案だけをさばける。

- **タスクにする**: 提案のタイトルと期限・未着手のタスクを、[Home](workspace.md#home) に付けて、画面から足したタスクと同じ位置（[その優先度の未着手の先頭](tasks.md#一覧は-1-本の列)）に足し、詳細欄にリンクと取得した本文を入れる。本文は外の文面なので、agent への最初の入力には載らない——Home のタスクを [`start_task`](../control/api.md) で始めても、最初の入力はタスクの ID・タイトルと頼み（`prompt`）だけで、詳細は agent が MCP で読む（ツール結果の席）。受信の提案はリポジトリに属さない仕事が主で、Home に付けば秘書がそこから始められるため。人が受けて足すタスクなので、入力欄から足したタスクと同じく未着手の上の方で目に入る。追加が拒否されたら提案は変わらない。
- **捨てる**。

さばいた提案は人の判断待ちから外れ、後から届いた判定でも上書きされない。人の判断待ちでない提案をさばこうとすると、値の不正とは別の失敗（判断待ちでない）として断る——判定の確定や下げと行き違っただけの操作を、画面が誤りとして出さないため。この 2 つは Orbe の画面（⌘⇧X の[受信タブ](../palette/intake.md)）の口で、AI には出さない。タスクにする操作はタスク一覧と受信の 2 つのファイルへ書くので、間で落ちるとタスクができたのに提案が判断待ちのまま残りうる。

## 保存

受信の定義・前回の取得結果・全件見直しの印・最後に回った時刻・回の記録・提案を、state ディレクトリの `intakes.json` 1 つに置き、変更のたびに即座に保存する。1 回の確定は 1 度の書き込み。後から足すフィールドは欠落を許容し、在るのに使えない原本（読めない・構造破損・非互換 version・定義の不正・ID やリンクの重複）は [persistence](persistence.md) の規律で退避してから空で始める。

起動時に全受信を番人へ載せる（止めた受信は予定なしで）。数え始めは最後に回った時刻、まだ回っていなければ作った時刻。

## 操作の口

[制御 API](../control/api.md) の 6 動詞（`list_intakes`・`set_intake`・`run_intake`・`pause_intake`・`delete_intake`・`list_intake_proposals`）を MCP にも出し、`orb intake`（[cli](../control/cli.md)）からも同じ形で叩ける。受信も提案もイベントにはならない。
