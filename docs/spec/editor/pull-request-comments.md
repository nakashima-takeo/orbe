# PR のコメント

PR の diff（→ [diff](diff.md#pr-の-diff)）の中で、GitHub のレビューのスレッドを読み、返信し、解決し、新しいコメントを書く。ブラウザの GitHub へ移らずに、変更を見ている行のその場で議論を進めるため。読み書きの規則（スレッドと未送信のレビューの読み方、書き込みの順序と読み直し）は PR の状態（→ [pull-request](pull-request.md#レビューのやりとり)）と [GitHub の読み書き](../platform/github.md#レビューのやりとり) が持ち、ここは diff の中の見せ方と操作を持つ。返信と新しいコメントの書きかけも PR の状態が持ち、diff はそれを欄に出す（→ [書きかけの残り方](#書きかけの残り方)）。未送信のコメントをまとめて送るのは、PR の画面の上のバーの「レビュー」のボタンから開くポップアップ（→ [pull-request-review](pull-request-review.md)）。

コメントは PR の diff だけに出る。作業ツリー diff とステージ済み diff には、印もスレッドも出ない。

## スレッドを置く行

スレッドは、エディターの面の絵の差し込み（→ [code](code.md#テキスト面metal)）として、付いた行の下に置く。置くのは、diff が見せている PR の先頭のコミット（新しい側の版）で読んだスレッドだけ——PR に push があって diff を作り直している間や、読み直しが届くまでは、古い版の行のスレッドを新しい版の行に置かない（→ [pull-request](pull-request.md#レビューのやりとり)）。GitHub と手元で rename の判定が食い違うファイルの古い側の行のスレッドも置かない（古い側の行の対応が変わるため）。diff が見せている両端が PR の今の両端でない間（PR への push・ベースの付け替えを読んで、両端を求め直し、diff が新しい両端の本文を読み終えるまで）も、古い側の行のスレッドを前の並びに置かない（新しい側の行のスレッドは、読んだ先頭のコミットが diff と同じなら置く）。読み直しが届くまでの間も、前に決まった置き方の答えを、diff が見せている両端について使える間（→ [pull-request](pull-request.md#レビューのやりとり)）は、その両端と本文で最後に置いたスレッドがその行に残る（PR への push を読んでから diff が新しい版を見せるまで、スレッドが一瞬消えて戻らず、打っている返信欄も閉じない）。版を揃える読みをやめて置けないと決まったら（→ [pull-request](pull-request.md#レビューのやりとり)）、残していたスレッドも外す（返信の書きかけがあれば、書きかけの位置で行を追う）。

- **新しい側の行**のスレッドは、その文書の行の下（次の変更区間の削除行より上）。
- **古い側の行**のスレッドは、削除行に付いたものはその削除行の直下（削除行の塊の途中でも塊を割る）。インラインで文脈の行に付いたものは、対応する新しい側の行の下。
- 同じ行の複数のスレッドは、古い側と新しい側を問わず、最初のコメントの時刻の順に上から。新しいコメントの欄はその下。
- **並列**では、古い側の行のスレッドは左の面、新しい側の行のスレッドは右の面に置き、反対側の同じ段（短い側の詰め物の途中を含む）に相手と同じ高さの空きを置く。スレッドの高さが変わっても（返信欄の改行・折りたたみ・幅の変更）、左右の行は同じコマで揃う。

スレッドのある行は、追加・削除・文脈のどれでも地をスレッドのある行の地に替える（記号の ＋ / − は元のまま）。今の diff に置けないスレッド（古い版の行に付いた・ファイル単位・rename の判定が食い違うファイルの古い側の行に付いた。決まり → [pull-request](pull-request.md#レビューのやりとり)）は diff に出さず、そのうち未解決のものの件数をレビューのポップアップに出す（「現在の diff に表示できない未解決のスレッド N 件」→ [pull-request-review](pull-request-review.md#ポップアップの中身)）。返信の書きかけを持ったまま置けなくなったスレッドは残す（→ [書きかけの残り方](#書きかけの残り方)）。

## コメント追加の印と新しいコメントの欄

GitHub がコメントを受ける行——変更区間とその前後 3 行（→ [git](../platform/git.md)）——にポインタを乗せると、その行の右端に「＋」の印が出る。範囲の外の行・詰め物・スレッドの上には出ない。GitHub と手元で rename の判定が食い違うファイルでは、古い側の行に印を出さない（古い側の行の対応が変わるため）。

印を押すと、その行の下に新しいコメントの欄（入力欄と「レビューに追加」「取り消す」）が開き、焦点が入る。同じ行の印をもう一度押すと、開いている欄に焦点を入れる。送れる欄は行ごとに 1 つ。

- 「レビューに追加」か ⌘↵ で、その行に新しいスレッドを書く（未送信のレビューに積む）。通ればスレッドが読み直しで現れ、欄は閉じる。
- 「取り消す」で閉じる。空の欄から焦点が外れたときも閉じる。本文のある欄は Esc で閉じず、焦点を本文へ戻すだけ——書きかけを 1 回の Esc で失わないため。
- 欄の行の番号は、開いたときに diff が見せていた版の行。diff の両端（マージベースか PR の先頭のコミット）が替わると——PR への push、ベースの付け替え——欄の行を、diff が見せている版の行に決め直す。決め方は、欄を開いた版と diff が見せている版の、その側の本文どうしの行差分で、変わった区間の外の行は区間の増減の分だけずらし、変わった区間の中の行（書き換えられた・消された行）は「無くなった」とする。両端が替わるたびに、欄を開いた版から決め直す（前に決めた行から継ぎ足さない）。GitHub が push の後にスレッドの行を新しい版へ付け替え、変わった行のスレッドを現在の diff に出さないのと同じ考え方。行を決め、その行に印を出せるかを確かめ終えるまでは「レビューに追加」を押せない姿にし、⌘↵ も受け付けない。その間も、diff が新しい版を見せるまでは欄は前の行の下に出たままで、一瞬も消えない。欄の行を決めた両端が PR の今の両端でない間は書かず、最新の内容を読み込んでからやり直すよう告げる。
  - 決めた行に印を出せるなら、欄は書きかけごとその行の下へ移り、その行へ書く。
  - 行が無くなったとき・決めた行に印を出せないときは、欄を閉じずに書きかけを残す。欄は、行が無くなったときは変わった区間の新しい側の終わりの行（区間が新しい側に行を持たなければその前の行）の下に、決めた行に印を出せないときは決めた行の下に置き、「この行は現在の diff にありません」と出して「レビューに追加」と ⌘↵ を受け付けない。後の push でその行が元に戻れば、欄はその行の下に戻り、送れる姿に戻る。本文は打てて選べる（コピーできる）。欄は「取り消す」で閉じる。同じ行の印を押すと、その行に新しい欄が開く。

## スレッドの姿と操作

開いたスレッドは、頭（「行 N」・状態・「解決」か「解決を取り消す」・「折りたたむ」）、コメントの列（書いた人の頭文字の丸・書いた人・相対時刻（1 分ごとに進む）・未送信の札・本文）、返信の行（返信欄・「レビューに追加」・「解決して返信」）。頭の状態は、未送信のコメントがあれば「未送信」、解決済みなら「解決済み」、どちらでもなければ出さない。返信の行は GitHub が返信を許すスレッドだけに、「解決して返信」は解決できる未解決のスレッドだけに出る。

- **返信**: 返信欄に打ち、「レビューに追加」か ⌘↵ で未送信の返信が付く。↵ は改行で、欄は行の数だけ伸びる。欄が空の間は「レビューに追加」は押せない。空白と改行だけの欄は空とみなす（新しいコメントの欄も同じ）。
- **解決して返信**: 返信を付けて解決する。欄が空なら解決だけ。返信は未送信のレビューに積まれてレビューを送信するまでほかの人に見えず、解決はその場で反映される（GitHub のウェブの未送信のレビューでも同じ）。
- **解決・解決を取り消す**: 押した時点で GitHub に反映される（未送信のレビューに積まない）。
- **折りたたみ**: 畳んだスレッドは頭の帯だけで、「行 N」の後に最初のコメントの書いた人と本文の先頭 1 行を出し、「折りたたむ」は「展開」になる。初めて見る解決済みのスレッドは畳んで出す。利用者が開閉したスレッドは、その後の読み直しで解決が変わっても選んだ姿を保つ。畳んでも開いても、見えている先頭の行は動かない。

スレッドの字（頭・コメントの列・返信の行のどの字も。新しいコメントの欄と、書き込みの最中に欄の代わりに出る字も）は、エディターの本文と同じく、言語を持たない字として組む——利用者の環境の言語が日本語でも、和文の約物を詰めず、和文と英数字の間も空けない（→ [code](code.md) の「字の言語」）。字の字体も、エディターの本文の字と同じく、その字だけで決まり、同じ字は、行頭でも和文の後ろでも同じ字体で出る（→ [code](code.md) の「字の字体」）。次の条件をすべて満たす 1 行の文は、欄で書いていたときと投稿した後とで、どの字の位置も同じ——Markdown の書式（強調・コードなど）と方向を変える書式文字を含まない、左から右の字で始まる、投稿した後のコメントの幅に収まる（欄は段落をいつも左から右として並べ、書式文字を箱で見せるが、投稿した後は段落の向きを最初の向きを持つ字で決め、書式文字で並びを変える）。

本文は選んでコピーできる（段ごと）。リンク（行き先が web かメールのものだけ。本文に直接書いた http(s) の URL を含む）を押すと、既定のアプリ（ブラウザ・メール）で開く。ほかの行き先（手元のファイル・独自の scheme など）のリンクは字のまま出し、押せない——第三者の書いた本文から、手元のアプリやファイルを開かせないため。

## 本文の Markdown

本文は GitHub の Markdown のうち、段落・インラインコード・太字・斜体・取り消し線・リンク・コードブロック・箇条書きと番号・引用・見出しを描く。書いた字は GitHub と同じく置き換えない（`--` や `"` や `...` を別の約物にしない）。1 つの改行もそのまま改行として描く。斜体はシステムの字体の斜体で、和文は直立のまま。それ以外の記法（表・画像・HTML・suggestion のコードブロック・脚注の参照と定義など）は書かれた字のまま段落か字として出す——引用や箇条書きの中でも、入れ物の前置き（`>` と字下げ）を外した書かれた字で、描けない記法でも GitHub が見せる字は欠けない。脚注は GitHub の Markdown（cmark-gfm）が見せる形で出す——参照は書かれたラベルのまま、定義は本文の末尾に参照された順で、書かれた字のまま出る。参照されない定義と、同じラベルの 2 つ目の定義は出ない。

- 引用と箇条書きの入れ子は 8 段まで字下げする。それより深い段は、引用は 8 段目と同じ字下げで、箇条書きの項目は 8 段目から 1 段だけ下げて出す（印は 8 段目の字の位置に並び、項目の字に重ならない）。入れ子がどれほど深くても、本文を段にする仕事と stack の深さは入れ子の深さに依らない（深い引用の本文 1 つで落ちない）。
- 同じ引用の段と段の間は、引用の線が続く。隣り合う別の引用の間では途切れる。
- 箇条書きの印は項目の字下げの位置に描く。項目の最初の子が箇条書きなら、外側と内側の印を 1 行に並べる（GitHub と同じ）。番号は右揃えで、字下げはその箇条書きの最も広い番号に合わせる。
- コードブロックは、字下げの位置から本文の右端までの地に、上下左右 8 の余白で字を置く。PR のパネルの説明の 3 行は Markdown を描かない（→ [pull-request-panel](pull-request-panel.md)）。

本文の段を幅で組み、飾り（インラインコードの地・取り消し線・リンクの押せる場所・引用の線・コードブロックの地・箇条書きの印）まで置く仕事は、本文の長さに比例し、main で行わない。スレッドはコメントの本文ごとに、本文の幅で組んだ層を幅ごとに覚え、問われた幅の覚えがあればその層をそのまま絵に置く。無ければ裏で組み、その間は、同じ本文をほかの幅で組んだ層を置いた絵を出し、組み終えたら今の幅の絵に描き直す。初めて置いたスレッドは、本文の段を持たない絵（頭とコメントのメタの行と返信の行）を先に出し、組み終えたら本文の入った絵に替わる。ホバーや打鍵の描き直しは、頭・メタの行・返信の行の小さな層だけを作り直し、本文の層は同じ参照のまま置くので、面は本文を写し直さず、仕事は本文の長さに依らない。

## 書き込みの最中と結果

書き込み（返信・解決・解決の取り消し・新しいスレッド）は PR ごとの状態へ頼む（→ [pull-request](pull-request.md#レビューのやりとり)）。返信と新しいスレッドの本文は、PR の状態が持つ書きかけから送る。

- 書き込みの最中は、そのスレッド（新しいスレッドならその欄）のボタンと欄を、その PR の diff を開いているどこでも押せない姿にし、欄は打てない。2 回押しても書き込みは 1 回。
- 通れば書きかけが消え、その PR の diff を開いているどこでも欄が空になる（新しいコメントの欄は閉じる）。スレッドの姿は書き込みの後の読み直しで変わる——書いた直後に画面へ先に出さないのは、GitHub がエラーを返した書き込みを一瞬でも書けたように見せないため。
- 「解決して返信」で返信だけが通ったときは、欄が空になり、送った欄に解決の失敗の文が出る（返信は未送信のレビューに積まれている）。
- 通らなければ書きかけが残り、送った欄の返信の行の下にだけ失敗の文が出る（次の書き込みを始めたら消える）。時間切れは、GitHub に届いていたかもしれないので、反映されたかを GitHub で確かめるよう告げる。PR の中身とレビューのやりとりのどちらかがまだ読めていないとき・diff の新しい側のコミットがレビューのやりとりを読んだ時点の PR の先頭と違うとき・新しいコメントの欄の行を決めた diff の両端が PR の今の両端でないとき（古い両端を見せている diff の欄から送ったときを含む）は書かず、最新の内容を読み込んでからやり直すよう告げる。
- diff の PR が、diff の根の worktree の今の PR（→ [pull-request](pull-request.md#worktree-の今の-pr)）で open でない間——ブランチを切り替えた後、PR がマージ・クローズされた後——は、未送信のレビューに積む書き込み（新しいスレッド・返信・解決して返信）を書かず、PR のブランチの worktree か GitHub で送信するよう告げる。未送信のレビューを送れるのはその PR を出す PR の画面のレビューのポップアップだけで、積んでも Orbe から送る所が無いため。その場で反映される解決・解決の取り消しは書く。

## 書きかけの残り方

返信と新しいコメントの本文は、PR の状態が PR ごとに 1 つ持ち（欄の位置——側と行と、その行を数えた diff の版——と一緒に）、PR の diff の欄はそれを出す。PR の状態が持つ位置は、書きかけを作ったときの位置——新しいコメントなら欄を開いた位置、返信なら、そのときスレッドが置かれていた位置——で、作った後は変わらない。push の後にどの行に出るか・行が無くなったかは、開いている diff が、この位置から自分が見せている版でその都度決める。だから古い版を見せている diff があっても、ほかの diff の書きかけの位置は崩れず、同じ版を見せている diff どうしでは同じ行に出る。新しいコメントを送れるのは、PR の今の両端を見せている diff の欄からだけ。だから書きかけは、読み直し（PR への push を読む間を含む）・diff の並びの置き直し・インライン ⇄ 並列・別の画面への切り替えだけでなく、PR の画面で別の行の diff を開いて入れ替わっても、diff が閉じても、端末が別の worktree へ移って連が替わっても残り、その PR の diff でそのファイルを開き直すと、同じ欄に出る（新しいコメントは同じ行に欄が開く）。同じ PR の同じファイルの diff を 2 か所で開いていれば、片方で打った書きかけはもう片方にも出る。書きかけが消えるのは、送って通ったとき（→ [書き込みの最中と結果](#書き込みの最中と結果)）、欄を空にしたとき（空白と改行だけの本文は空とみなすので、空白と改行だけにしたときも）、新しいコメントの欄の「取り消す」を押したとき、アプリを終えたとき（永続しない）のどれか。欄に焦点があれば、push を読んで diff の面を作り直しても、本体の幅でインライン ⇄ 並列が替わって欄が別の面へ移っても（古い側の行の欄は、インラインでは右の面、並列では左の面にある）、焦点は欄に残り、続けて打てる。開いただけで何も打っていない欄も、見せ方が替わっただけでは閉じない。書きかけのある解決済みのスレッドは、開き直したときも開いて出す。

返信の書きかけを持つスレッドが今の diff に置けなくなったら（push で付いた行が変わった・rename の判定が食い違った）、新しいコメントの欄の行が無くなったときと同じく、diff が見せている版で、書きかけを作ったときにスレッドが置かれていた行から決めた行の下に残し、「このスレッドは現在の diff の行に付いていません」と出す（畳んでいれば開く）。返信・解決して返信・解決は送れる——どれも行を渡さないので、GitHub は受ける。GitHub からスレッドが消えたら（根のコメントが削除された・未送信のレビューが捨てられた）、返信の書きかけを持つスレッドは同じく残し、「このスレッドは GitHub から削除されました」と出して、送れない姿にする。どちらも、開き直した diff でも、2 か所で開いていても、その位置から決めた行と、最後に読めたスレッドの姿で出る。本文は打てて選べる（コピーできる）。書きかけを空にして焦点が外れたら、diff から消える。失敗の文、スレッドを畳んでいるかどうか、空白と改行だけの欄の本文（開いただけの新しいコメントの欄を含む）は、開いている diff ごとに持つ。だから PR の状態にある書きかけは、そのファイルの diff を開けば欄に出る（置ける行が無いときを除く → [限界](#限界)）。

## 限界

- 自分のコメントの編集と削除、リアクション、複数行にまたがるコメント、ファイル単位のコメント、行に付かない会話の一覧は持たない。
- キーだけで行に新しいコメントを付ける操作は無い（印を押す）。
- ほかの人の新しいコメントは、読み直しのきっかけ（見始め・Orbe の中のネット操作の終わり・追跡 ref の変化・自分の書き込みの後）まで出ない。定期的には問い合わせない。
- 1 スレッドのコメントは 100 件まで読む（超える分は出ない）。
- アバターは書いた人の login の頭文字で、画像は出さない。
- 表・画像・HTML・suggestion・脚注は描かない（書かれた字のまま出る）。脚注の出方が GitHub の画面と同じかは確かめていない（cmark-gfm の HTML の出し方に合わせている）。
- 未送信のレビューが前の先頭のコミットに結ばれている間（その先頭で未送信のコメントを積んだ後に push があった）に、新しい先頭で数えた行へ書いたとき、GitHub がどちらのコミットの diff の行として読むかは確かめていない（→ [GitHub の読み書き](../platform/github.md#レビューへの書き込み)）。
- 未送信のレビューが前の先頭のコミットに結ばれている間にレビューを送ると、承認・変更の依頼がどちらのコミットに付くかは確かめていない（送信の関門は、今の先頭で揃っていることだけを見る → [pull-request-review](pull-request-review.md#送れる条件と理由)）。
- GitHub と手元が別の元のパスを rename の元と判定したファイルでは、古い側のスレッドと印の行が GitHub の diff と違いうる（GitHub の変更ファイルの読みは元のパスを持たず、見分けられない）。
- 印を出す行は手元の git で求めるので、GitHub が diff を出さないファイル（大きすぎる・3,000 件を超える）や改行コードの変換がある場合は、印を出した行への書き込みを GitHub がエラーで返しうる。そのときは失敗の文が出て本文が残る。
- PR の diff が見せる本文は smudge filter と eol 変換を通した姿（→ [diff](diff.md#pr-の-diff)）だが、印を出す行とスレッドの行は格納された版の行で数える。smudge で行の数が変わるファイル（git-lfs で管理するテキストなど）では、見えている本文の行と印・スレッドの行が食い違い、印から書いたコメントは GitHub では格納された版の別の行に付く（エラーにならない）。そうしたファイルの PR の先頭のコミットの版を読むたびに、smudge が LFS の実体を取りに行く（利用者が頼んでいない通信で、資格情報のダイアログを抑える規則の外）。
- diff の両端が替わって（PR への push・ベースの付け替え）ファイルがその側の新しい版に無くなると、その側の行に開いていた欄と、返信の書きかけを持つその側の行のスレッドは、置ける行が無く、画面に出ない（書きかけは PR の状態に残るが、見えない）。
