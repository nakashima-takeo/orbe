# 自動化設計の判断基準

新規作成でも修正でも共通で適用する品質基準。

---

## 1. 取得（fetch）の設計基準

### 判断に足りる情報密度を確保する
- **タイトルや件名だけの取得を避ける。** タイトルしか渡さないと下流の判定や報告が推測頼みになり、的外れな候補と薄い理由を量産する。下流が追加調査なしで判断できる文脈（本文の要点・直近の返信やコメント・送り手・場所〔リポジトリやチャンネル〕・状態やラベル）を `body` に読みやすく構造化して含め、行の項目として `link` と `time` も揃える。
- **生ダンプを流さない。** HTML タグ・長大なログや diff 全文・巨大なネスト JSON・名前解決していないユーザー ID をそのまま詰め込むと、1 行 64 KiB・標準出力 1 MiB の上限に当たり、LLM の判断精度も落ちる。取得段階で不要な装飾を落とし、本文は判断に効く範囲へ安全に切り詰める。
- 候補にしたい行には必ず有効な http(s) URL の `link` を残す（`link` の無い行からは候補を作れない）。

### `coverage` と増分取得・決着シグナル
- **状態を持つ取得元は `currentSet` を選ぶ。** 取るたびにその時点の有効集合全体が返り、完了や解消で対象が消える取得元（未完了課題・レビュー待ち PR・未読トリアージ一覧など）は `currentSet` にする。対象が消えた瞬間にタスク画面の候補一覧からも自動で取り下げられ、対応済み判定の漏れが構造的に起きない。
- **イベント追記型だけ `newArrivals` を選ぶ。** 新着メッセージやログのように過去が消えない取得元は `newArrivals` にする。
  - コマンドによる取得では、環境変数 `ORBE_SINCE`（前回成功した回の開始時刻。初回は未設定）で取得期間を区切る。初回は全履歴を取らず直近の数時間〜数日に絞る。
  - 判定へ流す `newArrivals` 取得では、**決着を示す後続情報（スレッド返信・自分の応答・解決の連絡など）も同じ `link`（スレッド先頭の permalink など）で必ず取得する。** 後続を取らなければ、判定は既存候補を対応済みにできず、終わった候補が `retentionDays` を過ぎるまでタスク画面の候補一覧に残り続ける。

### ローカルスクリプト化の基準
次のいずれかに当たる取得や処理は、定義 JSON 内のワンライナーへ押し込めず、agent へも逃げず、読みやすいローカルスクリプト（Python や Shell 等）として切り出し `command` で実行する。

- 複数回の API 呼び出しや GraphQL による文脈補完（一覧取得＋本文・コメント・レビュー状態・スレッド返信の結合）
- ページング・`ORBE_SINCE` の時刻計算・カーソルや処理済み状態の保持
- HTML 除去・ユーザー ID の名前解決・対応済みの除外・64 KiB 未満への安全な切り詰め
- クォートや改行が絡み、ワンライナーでは保守・デバッグが困難な整形

**スクリプトの配置規則**:
- 特定リポジトリに属さない自動化スクリプトは、Orbe の Home（`list_workspaces` の結果で hasBoard が true になっている workspace の rootPath）配下の scripts フォルダに役割の分かるファイル名で置き、実行権限を付ける。コマンドノードの `workspace` に Home の ID、`directory` に "scripts" を指定し、`command` では相対パス（例: python3 ./github-reviews.py、./github-reviews.py）で呼ぶ（Home の実パスは環境ごとに異なりうるため絶対パスを直書きしない）。
- 特定リポジトリの作業を伴うコマンドだけ、そのリポジトリの `workspace` と相対パスの `directory` を使う。
- スクリプトにも定義にも秘密情報（トークン・パスワード）を直書きしない。CLI の既存認証・環境変数・OS のキーチェーン・既存の設定ファイルなどから読む。

## 2. 決定論的な処理と LLM の分離・グラフ設計

### コマンド優先の原則
- **構造フィールドで決まることはすべてコマンドで担う。** bot 除外・draft 除外・自分の承認済みや返信済みの除外・チャンネルやラベルの絞り込み・数値閾値のチェック・重複除去・スレッド単位の結合はコマンド（取得スクリプトまたは処理ノード）で行う。決定論的な処理に LLM を回すと費用が膨らみ、判断も揺らぐ。
- **agent は意味処理だけに置く。** 自然言語の意図解釈（本当に自分の対応が必要か、もう解決しているか）・行動が分かるタイトル付け・期限の読み取り・優先度付きの要約・自律的な外部ツール操作など、コードでは書けない仕事だけ agent に任せる。
- **意味判断が不要なら判定もコマンドにする。** 絞り込み済みの行が例外なく候補になり、定型タイトルと固定ルールで足りるなら判定をコマンドにする（ただしコマンド判定は、人の確認待ちになっている既存の候補一覧と workspace 一覧を受け取らないため、自動の対応済み化や文脈による紐付け先の推定が要るなら agent 判定を選ぶ）。

### 処理ノード（process）を挟む基準
- **後から変わりうる属性（ラベル・状態・担当）で絞る処理**: 処理ノード自身の `coverage` を `currentSet` にし、入力の `take` を `all` にする。`currentSet` の取得では行の内容が変わっても `take` が `new` の受け手に再配送されないため、`all` で毎回受けて絞り直すことで、後から条件を満たした行が下流へ届き、条件から外れた候補も自動で取り下げられる。
- **高ノイズ源の前段フィルタ・スレッド集約**: 大量の行を安く絞ってから上位モデルの判定へ渡す、または同じスレッドの複数行を 1 行の文脈付きレコードへまとめるために処理ノードを置く。
- **行の `id` と `link` の扱い**: 入力行をそのまま流す処理は元の `id` と `link` を保つ。新しい `id` で行を作り直す処理で、候補の自動取り下げや再掲防止を行いたいなら、その処理を `currentSet` にする（`newArrivals` で新しい `id` を作ると、元の取得から消えても `retentionDays` が過ぎるまで候補が残る。さらに `retentionDays` の経過で Orbe がその `id` の履歴を忘れた後に同じ `id` が再び出力されると、人が却下・タスク化した件まで再度候補として復活しうる。詳細は `set_automation` 説明の JUDGE）。下流へ渡る行の `id` には Orbe が「<ノード ID>:」の接頭辞を付けるため、行を受けるコマンドが外部 API へ外部サービス本来の ID を渡すときはその接頭辞を外す（同説明の ROWS）。
- **重複候補の統合**: 同じ対象が複数の取得元から届くなら、1 つの判定ノードへ入力を集める（同じ `link` なら候補は 1 件に揃う）。

### モデル・スケジュール・上限・通知の選び方
- **モデル選定**:
  - haiku: 高頻度の軽量分類・短文要約・CLI が使えずやむを得ず MCP で読むだけの取得。
  - sonnet: 文脈を読んで行動要否・決着・紐付け先を見極める判定（標準）、構造化された報告、外部ツールを伴う作業。
  - opus: 低頻度（日次・週次）で高度な統合判断や深い分析が明確に価値を生む報告・判定に限る。
- **スケジュールの設計**:
  - 取得元の更新速度と人の消費リズムを分けて設計する。人が朝 1 回しか見ないものを 10 分ごとに LLM 判定しない。取得だけ適切な間隔で回し、判定や報告は cron でまとめて処理する構成を優先する。
  - 取得が agent になる場合は実行のたびに LLM が起動するため、頻度を必要以上に高くしない。
- **上限と保持**:
  - 障害回復時に溜まった行の大量流入や、古い行が後から一斉に処理されるのを防ぐため、受け手には実データ量に見合った `maxItems` と `maxAgeHours` を書く。下流の判定や報告が長い対象期間（`maxAgeHours` 等）で参照する `newArrivals` の取得には、その期間をカバーする `retentionDays` を書く。
  - 重い取得や長い作業には、想定実行時間に十分な余裕を足した `timeoutMinutes` を書く（テスト実行の実測時間で補正する）。
- **通知（`notify`）**:
  - すぐ反応すべき高シグナルな自動化には `menuBar` か `notificationCenter` を提案し、高頻度・低緊急のものは省略する。通知がノイズになると自動化全体が見られなくなる。

## 3. 役割別の指示文（`instruction`）品質基準

曖昧な一般論（「重要なものをタスクにする」「わかりやすくまとめる」）を書かない。実データの観察結果に根ざした具体的な境界と出力の型を言い切りで書く。

### 判定（judge）の指示文
次の 6 要素（`newArrivals` 由来なら 7 要素）について具体的な基準を揃える。

1. **タスクにする条件**: 実データで見つかった「自分が手を動かす必要がある」具体パターン。
2. **タスクにしない条件**: 実データで見つかったノイズ（周知・自動通知・他者で完結済み・挨拶や了解のみ等）の明示。
3. **タイトルの規則**: タスク画面で見出しだけ見て次の行動が分かる 1 行（対象や送り手＋具体的な動詞）。元の件名の丸写しを避ける。
4. **理由の規則**: タイトルの言い換えではなく、誰が何を求めているか・何が詰まっているかを行の事実から 1〜2 文で書く。
5. **期限の規則**: 本文に明示または明確に示唆された期日があるときだけ現在日時から算出する。根拠が無ければ省略し、推測で付けない。
6. **紐付け先の規則**: `list_workspaces` で確かめた実在 workspace 名と対応ルールを明示する。明確に当てはまらなければ省略して Home にする。
7. **対応済みの条件（`newArrivals` の入力があるとき必須）**: 同じ `link` の新しい行に決着の証拠（送り手の取り下げ・解決報告・自分の対応完了返信など）があれば対応済みにすると明記する。

### 報告（report）の指示文
1. **1 行目を通知ヘッドラインとして設計する**: 1 行目はそのまま通知と一覧の要約になる。「朝のレポート」のような汎用見出しを禁じ、件数と最重要の要点 1 つを短く言い切る。
2. **「報告なし」の条件を明示する**: 伝えるべき変化や対象が 0 件の回は報告せず終了する（agent なら report_nothing を呼び、コマンドなら標準出力を空にする）よう明記し、無意味な「該当なし」通知を流さない。
3. **優先順とスキャン性**: 急ぎ・滞留・変化の大きいものを先頭に置き、項目ごとに判断材料とリンク・識別子を添える。

### 作業（work）の指示文
1. **操作境界の明示**: 変更してよい対象（特定のチャンネル・リポジトリ・条件）と、触ってはならない範囲を言い切る。
2. **冪等チェックの組み込み**: 失敗した回や、Orbe 側で実行結果が確定・記録される前に終了した回は次の回で再実行される。投稿や作成の前に既存状態を確認し、二重実行を防ぐ手順を含める。
3. **終了結果の使い分け**: 対象が無い回は「何もしない」と申告（report_nothing）し、ツール失敗や権限不足はエラーとして申告（report_error）して、成功を装わない。
4. **最小の `tools`**: 作業に必要な最小限のツールだけを指定する。

### 取得（agent を使う場合）の指示文
1. 取る範囲・検索条件・期間（現在日時と Orbe が渡す前回成功時刻の扱い）を具体的に書く。
2. 各項目の `id`（回をまたいで不変）・`link`（スレッドは先頭の permalink に統一）・`body`（送り手・場所・本文・最新返信を簡潔に整形）・`time`（ISO 8601）の組み立て方を明示する。
3. `newArrivals` で判定へ流すなら、決着判定に必要な後続メッセージ（スレッド返信・自分の応答等）も取る条件を必ず含める。

## 4. バックグラウンド実行環境の制約（事前につぶす罠）

- **agent は毎回空の一時ディレクトリで起動する**: プロジェクトスコープ・ローカルスコープにだけ登録された MCP サーバーはバックグラウンド実行では見つからず失敗する。MCP での取得・作業を設計する場合は、claude mcp list などでユーザー設定（user スコープ）に登録されているかを確かめ、さらにテスト実行で実際に起動・取得できることを実証する。
- **Bash の許可ルールだけで動く agent は作業ディレクトリ外のファイルを読めない**: MCP ツールを指定せず Bash の許可ルールだけで起動する agent では、作業ディレクトリ外のファイルを引数に取るコマンドを Claude が拒否する。ローカルファイルを読む仕事では、ファイルパスを引数に取らず内部でファイルを読む専用スクリプトでラップするか、コマンドノードで実行する。
- **MCP ツール指定時の設定読込**: MCP ツールを 1 つでも指定すると利用者の Claude 設定が読み込まれ、利用者が常時許可しているツールや hook の副作用まで実行時に効いてしまう。認証が MCP にしか無い場合を除き、取得はコマンドノードを優先する。
- **外部文面の安全境界**: 取得 agent には読み取り専用ツールだけを渡す（書き込みツールを渡すと外部文面に仕込まれた指示で悪用されうる）。行を受けるコマンドは行の値をシェル評価せず、claude -p 等の別 agent にも渡さない（agent に読ませたいなら処理ノードにする）。
- **副作用コマンドの二重実行防止**: 失敗した回の行は次の回で再送されるため、処理した行の `id` を状態ファイルへ記録しておき、処理済みの行は除外する。さらに、Orbe 側で実行結果が確定される前に異常終了して再実行された回では同じ値の環境変数 `ORBE_RUN_ID`（実行識別子）が渡されるため、`ORBE_RUN_ID` で回単位の二重実行を防ぐ場合は処理の完了時に状態ファイルへ記録する（`set_automation` 説明の REPORT, WORK, SIDE EFFECT）。
